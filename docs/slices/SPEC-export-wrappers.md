# Slice SPEC — "한 이름, 한 본문": export를 본문 + 얇은 래퍼로 나눈다

> **상태: 확정(accepted) · 구현 중** — 2026-09-01.
> **DP-W1~W5 사용자 확인 완료(권고안 그대로).** 결정:
>
> | DP | 결정 |
> |----|------|
> | **W1** | 본문 이름 **`ml_fn_<name>`** — 사용자 함수 이름은 생성 Rust에 함수로 등장하지 않는다 |
> | **W2** | 어댑터는 **본문 바로 뒤** |
> | **W3** | **`-> string!` export의 `try` 호출은 v1 제외** |
> | **W4** | **내부 이름 예약어 검사 제거** — 근거가 사라진다 |
> | **W5** | 크기 회귀는 **기록만**, 상한 없음 |
> **근거 수준:** §0이 **E2 실측**(오늘 컴파일되는 프로그램·생성 산출물), §2가 E0 + 확정 결정 인용.
> **선행:** #98(`try`) · #95(export 호출) · D18 · SPEC-fallible-calls DP-F5.
> **이 슬라이스는 C ABI를 바꾸지 않는다** — 생성 `.h`·`.pas`가 바이트 단위로 같아야 하고,
> **export 심볼 집합과 모듈 크기도 사실상 그대로여야 한다**(§3-C).
>
> ⚠ **이 저장소에서 가장 넓은 변경이다.** 모든 export의 방출 경로를 건드린다. 그래서
> 기능을 얹지 않고 **형태만 바꾸는** 슬라이스로 격리한다.

## 0. 왜 — 그리고 무엇을 없애는가

### 0.1 오늘의 문제: 한 함수가 두 몸을 가질 수 없다

`try`는 피호출자가 **`Result<T, i32>`를 반환**하기를 요구한다(DP-F6). export된 실패 가능 함수의
본문은 **C ABI로** 방출된다(`out_value`에 쓰고 status 반환). 둘은 같은 본문이 될 수 없으므로,
#98은 **export 피호출자를 금지**했다(DP-F5) — 기능이 아니라 **방출 구조 때문에** 생긴 제한이다.

측정한 결과(SPEC-fallible-calls §0.1): 규칙을 export로 승격하면 **호출자가 non-fallible이 되어**
검증이 권고 사항으로 격하된다. 지금은 그 반대 방향도 막혀 있다 — 호스트에도 노출하고 싶은 규칙은
**모듈 안에서 재사용할 수 없다.**

### 0.2 리팩터

```
오늘:   export fn f  →  #[no_mangle] pub extern "C" fn mlx_f(<C ABI>) { <본문> }
        fn g         →  fn g(<Rust>) { <본문> }

이후:   export fn f  →  fn ml_fn_f(<Rust>) { <본문> }
                        #[no_mangle] pub extern "C" fn mlx_f(<C ABI>) { <얇은 어댑터> }
        fn g         →  fn ml_fn_g(<Rust>) { <본문> }
```

**모든 Mathless 함수가 정확히 하나의 Rust 본문을 갖는다.** export라는 것은 그 위에 **C ABI 어댑터가
하나 더 붙는다**는 뜻일 뿐이다 — DP-C3가 처음부터 말하던 것("export는 밖에서도 보이는 함수일 뿐이다")이
이제 방출 구조에서도 참이 된다.

어댑터는 세 가지뿐이고 전부 짧다:

```rust
// 무오류
pub extern "C" fn mlx_f(a: f64) -> f64 { ml_fn_f(a) }

// D17 실패 가능 스칼라
pub extern "C" fn mlx_f(a: f64, out_value: *mut f64) -> i32 {
    match ml_fn_f(a) { Ok(v) => { unsafe { *out_value = v; } 0 } Err(e) => e }
}

// Q12 문자열 반환
pub extern "C" fn mlx_f(a: f64, ml_buf: *mut u8, ml_cap: i32, ml_needed: *mut i32) -> i32 {
    match ml_fn_f(a) { Ok(p) => ml_strout(p, ml_buf, ml_cap, ml_needed), Err(e) => e }
}
```

### 0.3 이 리팩터가 **없애는** 제한 두 개 (실측)

**(1) export 이름의 예약어 문제가 애초에 생기지 않는다.** 오늘 이것들은 **컴파일된다**(측정):

```
export fn type(x: i32)  → ok      export fn match(x: i32) → ok
export fn loop(x: i32)  → ok      export fn impl(x: i32)  → ok
```

`mlx_` 접두어가 가려 주기 때문이다. 본문에 **raw 사용자 이름**을 쓰면 이것들이 **깨진다** —
그래서 DP-W1은 본문도 접두어를 붙인다. **오늘 컴파일되는 프로그램은 계속 컴파일된다.**

**(2) 내부 함수 이름의 예약어 거부가 불필요해진다.** 오늘 `fn match(x: i32)`는
*"internal function 'match' is a reserved word in Rust"* 로 거부된다 — 내부 이름이 raw로
방출되기 때문이다. 본문이 전부 `ml_fn_`을 달면 **사용자 함수 이름은 생성 Rust에 한 번도 등장하지
않으므로** 그 거부가 근거를 잃는다. **제한이 하나 줄어든다**(DP-W4).

> 지역 변수는 여전히 raw로 방출되므로 그쪽 검사는 그대로다.

### 0.4 정직하게 — 이것은 기능 슬라이스가 아니다

**사용자가 오늘 못 하던 일 중 이 슬라이스가 직접 가능하게 하는 것은 하나뿐이다:** export된 실패
가능 함수를 모듈 안에서 `try`로 부르기(DP-F5). 나머지는 **구조 정리**다.

그래서 §3의 무게중심이 값이 아니라 **불변량**이다: export 집합·헤더·모듈 크기가 그대로인가.
"리팩터인데 아무것도 안 바뀌었다"를 **측정으로** 보여야 하는 슬라이스다.

## 1. 목표

```mathless
error E_BAD = 1

// 호스트에도 노출하고, 모듈 안에서도 재사용한다 — 오늘은 둘 중 하나만 된다
export fn check_qty(qty: i32) -> i32! {
  if qty < 1 { fail E_BAD }
  return qty
}

export fn unit_price(total: f64, qty: i32) -> f64! {
  let q = try check_qty(qty)          // ← 이 줄이 오늘은 거부된다
  return total / (q as f64)
}
```

생성 헤더는 **오늘과 완전히 같다**(두 함수 모두 export되고 시그니처도 그대로).

## 2. 계약 (Contracts)

### 2.1 모든 함수는 하나의 본문을 갖는다 (DP-W1)

이름은 **`ml_fn_<name>`**. `ml_`은 이미 사용자 식별자에서 예약돼 있으므로(#85) 충돌할 수 없고,
`ml_floor`·`ml_streq`·`ml_strout`·`ml_panic`·`ml_module_abi_version` 같은 기존 생성 이름과도
접두어가 달라 겹치지 않는다.

반환 형태는 오늘의 내부 함수 규칙 그대로다: 무오류는 `T`, 실패 가능은 `Result<T, i32>`.

### 2.2 export는 어댑터를 하나 더 얻는다

`#[no_mangle] pub extern "C" fn mlx_<name>(<C ABI>)` — **시그니처는 오늘과 한 글자도 다르지 않다.**
어댑터 본문은 §0.2의 세 형태 중 하나이며, **분기도 계산도 없다.**

선언된 `out` 파라미터는 어댑터와 본문 **양쪽에서 `*mut T`** 로 그대로 흐른다. 본문이 포인터를
받는 것은 오늘과 같고, `out`이 있는 함수를 `try`로 부를 수 없다는 제한도 그대로다(주소를 넘길
문법이 없다 — #95).

### 2.3 export를 `try`로 부를 수 있다 (DP-F5 해제)

`try`의 피호출자 제한에서 **`export` 조건만** 없어진다. 나머지는 그대로다: 피호출자는 실패 가능해야
하고, 호출자도 실패 가능해야 하며, `out` 파라미터가 있으면 부를 수 없다.

**재귀 금지는 그대로 적용된다.** `reject_recursion`은 모든 함수의 호출 그래프를 보므로
export→export 순환도 잡는다. §3-E가 측정한다.

### 2.4 C ABI·export 집합·크기는 불변이다

- **헤더와 `.pas`는 바이트 단위로 같다** — #98이 넣은 동일성 테스트가 이미 지킨다.
- **export 심볼 집합이 같다.** 본문에는 `#[no_mangle]`이 없으므로 export되지 않는다.
- **모듈 크기가 사실상 같다.** 어댑터는 LTO에서 인라인될 것으로 **기대**하지만, 그것은 가정이므로
  §3-C가 **재서 기록한다.** 커지면 커진 대로 적는다(§7 "측정 없이 쓰지 않는다").

## 3. 수용 기준 (측정 가능) — 무게중심은 **불변량**이다

- **A. 컴파일:** 모든 기존 예제가 그대로 빌드된다.
- **B. ABI 불변:** 모든 예제의 `.h`·`.pas`가 **리팩터 전후로 동일**. #98의 테스트를 확장해
  `.pas`까지 덮는다.
- **C. 보호 프록시 불변(핵심):** 예제별로 **export 집합이 동일**하고 **`.dll` 크기 차이를 기록**한다.
  절대 주장이 아니라 **전후 비교**다(#89의 교훈). import 집합도 대조 모듈과 비교한다.
- **D. 새 기능:** export된 실패 가능 함수를 `try`로 부르고 **값과 status를 오라클로 측정**.
  호스트도 같은 함수를 직접 부를 수 있음을 **같은 모듈에서** 확인한다.
- **E. 부정 케이스:** export→export 재귀 · export→내부→export 재귀 · `out` 파라미터 피호출자 ·
  non-fallible 호출자 · `try` 없는 fallible 호출.
- **F. 제한 해제 확인:** `export fn type`·`match`·`loop`·`impl`이 **계속** 컴파일된다(회귀 방지),
  그리고 `fn match`(내부)가 **이제** 컴파일된다(DP-W4).
- **G. 수용 D:** C 호스트가 §3-D의 모듈을 로드해 두 export를 모두 호출한다.
- **H. 생성 크레이트가 빌드된다:** `calls_build.rs`에 export 피호출자 케이스를 추가한다 —
  #95가 보여 줬듯 **방출된 텍스트만 보는 테스트는 그것이 유효한 Rust인지 볼 수 없다.**

## 4. 설계 결정 (DP — **전부 확인 완료 2026-09-01**, 근거는 남긴다)

| DP | 선택지 | **결정** | 근거 |
|----|--------|------|------|
| **W1 본문 이름** | raw `<name>` / **`ml_fn_<name>`** | **`ml_fn_<name>`** | raw를 쓰면 **오늘 컴파일되는 `export fn type`·`match`·`loop`·`impl`이 깨진다**(측정). 접두어를 붙이면 사용자 이름이 생성 Rust에 함수로 등장하지 않으므로, **제한이 늘지 않고 하나 줄어든다**(DP-W4). **반론(Grok):** rustc 에러와 백트레이스가 사용자가 쓰지 않은 `ml_fn_foo`를 인용한다 — 이 저장소가 이미 값을 치른 실패 방식이다. **완화:** 이름이 기계적으로 되돌려지고(`ml_fn_` 제거), 애초에 그 에러가 사용자에게 닿지 않게 하는 것이 §3-H와 `calls_build.rs`의 목적이다 |
| **W2 어댑터 위치** | 본문 바로 뒤 / 파일 끝에 모아서 | **본문 바로 뒤** | 생성 Rust를 읽을 때 한 함수의 두 조각이 붙어 있는 편이 낫다. 순서는 방출 결정일 뿐 의미가 없다 |
| **W3 `-> string!` export를 `try`로** | 허용 / **v1에서 제외** | **제외(v1)** | 기계장치는 공짜로 생기지만(본문이 `Result<*const u8, i32>`를 반환한다) **DP-T5**(반환값은 리터럴이나 파라미터만)와 문자열 지역 변수 금지가 함께 걸린다. `return try f(x)`만 성립하는데, 그 좁은 경우를 위해 DP-T5·DP-S2를 다시 여는 것은 이 슬라이스의 일이 아니다. **후속으로 분리** |
| **W4 내부 이름 예약어 검사** | 유지 / **제거** | **제거** | 근거가 사라진다 — 사용자 함수 이름이 생성 Rust에 등장하지 않는다. 유지하면 **이유 없는 제한**이 남는다. 지역 변수 쪽 검사는 그대로(여전히 raw로 방출된다) |
| **W5 크기 회귀 한도** | 무한 / **기록만** / 상한 강제 | **기록만** | 어댑터가 인라인될 것으로 기대하지만 **가정이다.** 상한을 지금 정하면 근거 없는 숫자가 된다. §3-C가 전후를 재서 STATUS에 남기고, **커지면 커진 대로 적는다** |

## 5. 범위 밖 / 위험

### 5.1 이 슬라이스는 언어를 넓히지 않는다

DP-F5 해제 하나를 빼면 **사용자가 쓸 수 있는 문장이 늘지 않는다.** 새 문법도, 새 타입도 없다.
그래서 §3이 값이 아니라 불변량을 재는 것이다.

### 5.2 가장 큰 위험은 **조용한 회귀**다

모든 export의 방출을 건드리므로, 어느 한 형태(무오류 / D17 스칼라 / Q12 문자열 / `out` 포함 /
`out` + 실패 가능)를 잘못 어댑팅하면 **컴파일되고 그럴듯한 값을 내고 틀린다** — 이 저장소가 여덟 번
만난 모양이다. **완화:** §3-B·C가 전후 동일성을 재고, 기존 오라클 테스트 전부(수용 A~D)가
어댑터를 관통해 다시 돈다. 새 값 테스트보다 **기존 테스트가 그대로 도는 것**이 이 슬라이스의
주된 안전망이다.

### 5.3 갚지 않는 부채

- **P6**(non-fallible 호출자의 에러 소멸) · **`&&` 단락 평가** · **Q14의 나머지 절반**
  (모듈 접두어 없는 `ML_ERR_`) — 전부 그대로.
- **DP-W3**의 `-> string!` `try` 호출.
