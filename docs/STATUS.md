## 2. 오늘 컴파일되는 언어

정본은 `docs/LANGUAGE.md`의 "현재 구현된 표면". 요약:

- **내장 함수**(#83) `floor`·`ceil`·`round`·`trunc` — `f64 -> f64`, **C `<math.h>`와 정확히 같다**
  (0 부호·NaN·inf 포함, 실제 C 호스트에서 대조). 키워드가 아니라 **내장 시그니처**라
  `let round = 0`은 계속 합법이고, 동명 함수 선언은 거부된다
- **문자열 입력**(#89) `export fn f(code: string) -> f64` — **파라미터 위치 전용**, 연산은
  **`==`·`!=` 뿐**, 의미는 **NUL까지의 바이트 동등성**. C는 `const char*`, Delphi는 `PAnsiChar`.
  비교가 **CRT를 부르지 않음을 측정**했다(import 집합이 문자열 없는 모듈과 동일)
- **문자열 반환**(#92) `-> string!` — Q12 프로토콜. 호스트가 버퍼와 용량을 주고 모듈이 채운다.
  **절단은 실패**(음수 status)이고 그때 버퍼는 **한 바이트도 쓰이지 않는다**. probe(`ml_cap = 0`,
  버퍼 NULL 가능)는 **항상 2회에 수렴**. 반환값의 재료는 리터럴·`string` 파라미터에 더해
  **연결 `+`**(#108) · `i32 as string` · `fixed(x, places)` · `byte_slice(...)`까지다
  — 자세한 범위는 바로 아래 문단들과 `docs/HOST_ABI.md`가 정본이다
- 타입 `f64` / `bool` / `i32` / `string`(파라미터 + `-> string!` 반환), 명시적 변환 `e as T`(암시적 혼합은 여전히 금지).
  **`as`는 단항보다 느슨하게 묶는다**(Rust 계열, #68) — `-x as f64` = `(-x) as f64`
- `export fn` / **`fn`(내부 함수)** + 호출식 — **재귀는 금지**(직접·상호)
- **`out` 파라미터**(#80) `export fn f(a: f64, out t: i32) -> f64` — 값을 여러 개 돌려주는 수단.
  C는 `T*`, Delphi는 `out p: T`. **쓰기 전용**, **정상 반환 경로마다 대입 강제**, `export fn` 전용.
  실패 가능 함수와 합칠 때 `out_value`가 **언제나 마지막**이다(DP-O1)
- **실패 가능 함수 호출**(#98·#99) `let x = try f(a)` · `x = try f(a)` · `return try f(a)` — 피호출자의
  status가 **그대로** 전파된다. **`try`는 문장 전용**이라 식 안에 못 들어간다. 호출자도 `-> T!`여야
  하고, v1의 피호출자는 **내부 `fn`만**이다. **C ABI 무변경**(테스트로 못박음)
- 실패 가능 함수 `-> T!` + `error NAME = N` + `fail NAME`(D17: i32 status + out-param).
  **`export fn`에만 붙는다**(#67) — D17은 호스트 경계 규약이고 내부 호출 규약은 없다
- `if`(**`else` 없음**) / `while` / `return`
- `let`(불변) / `let mut` + 대입문
- 단항 `-` `!`, 이항 `+ - * / %`, 비교, `&&` `||`.
  **`i32`의 `/`·`%`는 전역(total)**(#76) — `x / 0` = `x % 0` = `0`, `i32::MIN / -1`은 wrap.
  `%`는 i32 전용. 리터럴 `/ 0`은 컴파일 에러

- **문자열 연결**(#108) `a + b` — 양변이 **둘 다 `string`**일 때만. `"x" + n`은 거부되고
  `n as string`을 쓴다(DP-K1). **`i32 as string`**도 함께 들어왔다 — `i32::MIN`까지 정확하고,
  모듈이 만드는 바이트는 **ASCII `-`·`0`–`9`뿐**이다. 결과는 **호스트 버퍼에 직접** 만들어지므로
  `-> string!`의 **`return` 자리에만** 놓을 수 있다(이름을 붙일 수 없다 — 할당자가 없다)

**없는 것:** `f64 %`, `else`, `break`/`continue`, 복합 대입(`+=`), `for`,
**문자열의 길이·부분문자열·순서 비교·지역 변수**, **`f64 as string`**, 배열, struct,
호스트 함수 import, 재귀.

4. **DP-T2 — 확정된 표를 바꾸지 않기로 했다.** Annex K식 `buf[0]=0` 안전장치는 status를 무시한
   호스트를 지켜 주지만 Q12 표를 고치는 일이라 **기각**했다(규칙 8). 대가는 숨기지 않고
   `HOST_ABI.md`와 SPEC §2.8에 적었고, C 호스트 예제는 **호출 전에 버퍼를 반드시 초기화한다**(보통 `0`,
   바이트가 쓰였는지/안 쓰였는지를 봐야 하는 곳은 `0xAA`) —
   문서가 아니라 예제 코드가 습관을 보여 준다.

### 3a-4. ✅ 닫힘 — 문자열 **입력** 파라미터 (2026-08-31, SPEC #88 / 구현 #89)

`string` 파라미터 + `==`/`!=`. [`SPEC-string-input.md`](slices/SPEC-string-input.md).
DP-S1 = NUL 종료 `const char*`, DP-S2 = 불투명 바이트(둘 다 사용자 승인 = 권고안 그대로).

**§7을 또 돌려서 고른 것이 아니다** — Q12가 닫히며 열린 세 슬라이스 중 하나였고, 문자열이 필요한
방향을 다시 재 보니 **갈렸다**: 측정한 세 규칙(국가별 부가세율·카드 BIN·수출품 판정)이 **전부
문자열 IN · 스칼라 OUT**이었다. 그 방향은 **Q12를 쓰지 않는다**(빌린 인자라 할당이 없다).
문자열 **반환**이 Q12 프로토콜의 첫 사용자가 될 슬라이스이며, SPEC §5.1에서 분리했다.

**다음 세션이 알아야 할 것:**

1. **"import 집합 불변"을 처음으로 실제 측정했다.** 그러려면 PE 리더에 **import 테이블 읽기**가
   필요했고(`hosts/rust-oracle/src/pe.rs`), 그것도 `dumpbin /imports`와 교차 확인한다(11개 모듈).
   측정해 보니 **절대값으로는 주장할 수 없다**: 모든 cdylib이 DllMain 발판 때문에 CRT 시동 함수와
   `vcruntime140!memcpy`/`memset`을 이미 import한다(총 25개). 그래서 수용 C는 **문자열 없는 모듈을
   같은 방식으로 빌드해 집합이 정확히 같은지**를 본다. 앞으로 "import가 늘지 않는다"류 주장은
   이 비교 방식으로만 쓸 것.
2. **조용한 오답 후보가 하나 더 생겼고, 이번엔 막지 못한다.** Delphi `UnicodeString`을 `PAnsiChar`
   자리에 넘기면 **컴파일되고 크래시도 없고 아무 코드에도 맞지 않는다.** 모듈 쪽에서 막을 방법이
   없어(바이트만 보인다) 생성 `.pas` 주석과 `HOST_ABI.md`에 계약으로 적었다. `dcc64`가 없어
   **E1이며 E2로 확인할 수 없다** — Delphi가 붙는 날 가장 먼저 확인할 항목이다.
3. **codegen에서 `==`를 그냥 두면 포인터 주소를 비교한다.** `*const u8 == *const u8`은 Rust에서
   컴파일되고 주소를 비교한다 — 같은 바이트를 담은 호스트 문자열에 대해 조용히 `false`다.
   같은 모양이 다섯 번째다(§7). 여기서는 typeck이 아니라 **codegen이 가로챈다.**

### 3a-3. ✅ 닫힘 — 반올림 내장 함수 (2026-08-31, SPEC #82 / 구현 #83)

`floor`·`ceil`·`round`·`trunc`. [`SPEC-rounding.md`](slices/SPEC-rounding.md).

**§7을 세 라운드 더 돌린 결과다**(급여·주문·상환). 스칼라 로직은 **전부 컴파일됐고**, 벽은 둘이었다:
**배열**(두 번)과 **반올림**. 배열이 더 크지만 힙과 **Q12가 선행**하므로, 그동안 막을 수 있는 오답을
먼저 막았다.

**다음 세션이 알아야 할 것:**

1. **같은 모양이 세 번째였다.** `boxes(17,0)`(#76) · 죽은 out 파라미터(#80) · 반올림 포화(#83).
   셋 다 **컴파일되고 그럴듯한 숫자를 내고 틀렸다**, 그리고 셋 다 원인이 **`as`의 포화**였다.
   **비슷한 것이 또 있는지 볼 때 이 모양을 찾으면 된다.**
2. **`no_std`가 표준 라이브러리를 막는다.** `f64::floor`는 `std`에 있다. 앞으로 수학 연산을 더
   넣는다면 매번 같은 벽을 만나고, `libm`을 넣는 순간 **서드파티 0개**가 끝난다(§1).

### 3a-2. ✅ 닫힘 — 명시적 `out` 파라미터 (2026-08-31, SPEC #79 / 구현 #80)

값을 두 개 돌려줄 수단이 생겼다. [`SPEC-out-params.md`](slices/SPEC-out-params.md).

**§7의 방법이 §3b의 목록과 다른 답을 냈다 — 그게 이 항목의 요점이다.** 다음 슬라이스를 고르려고
업무 규칙 넷을 오늘의 언어로 써 봤더니 `else`·`break`·복합 대입은 **하나도 아프지 않았다**:
계층 수수료·등급 할인 + 공통 후처리·연체 상한·분할 납부가 전부 조기 `return`과 `let mut`로
자연스럽게 컴파일된다. 정작 막힌 것은 **값 두 개**였고, 그것도 **컴파일되면서** 막혔다 —
`out_tier: i32`가 값으로 받는 입력이라 아무 일도 하지 않았다.

**§3b의 목록을 다음 후보로 그냥 믿지 말 것.** 그 넷은 오늘도 목록에 있지만, 실제로 써 보면
우선순위가 아니다.

### 3a. ✅ 닫힘 — `i32` 나눗셈·나머지 (2026-08-31, SPEC #75 / 구현 #76)

`/`와 `%`가 들어왔고 **둘 다 전역(total)** 이다(DP-D1 = (b), 사용자 승인).
`x / 0` = `x % 0` = `0`, `i32::MIN / -1`은 wrap. 자세한 것은
[`SPEC-i32-division.md`](slices/SPEC-i32-division.md).

**다음 세션이 알아야 할 것 두 가지:**

1. **이 항목이 원래 적어 둔 정당화는 틀렸었다.** "정수 산술이 안 된다"고 했지만 실제로는
   `(a as f64 / b as f64) as i32`로 **되었고, 정상 값에서는 정확했다.** 진짜 구멍은 그 경로가
   `b == 0`을 **`2147483647`로** 바꾼다는 것이었다(측정). 표현력이 아니라 **실패의 소재**가 문제였다.
   → 교훈은 §7 그대로다: **후보를 나열하지 말고 업무 규칙을 실제로 써 볼 것.** 써 보지 않았다면
   이 슬라이스는 잘못된 근거로 설계됐을 것이다.
2. **`&&` 단락 평가 부채(§5-1)는 갚지 못했다.** 이 항목이 "트랩 가능한 첫 연산"을 기대했지만
   DP-D1이 전역으로 결정돼 **관측할 트랩이 없다.** §5-1은 그대로 열려 있다.

### 3b. 다음 후보

> ⚠ **이 절은 이력이다. 오늘의 근거는 §9-1이다(2026-09-02 재측정).** 아래 서술은 여러 세션에 걸쳐
> 쌓였고, 문자열 연결(§3a-9)처럼 이미 닫힌 항목을 아직 후보로 부르는 문장이 섞여 있다.
> **남은 두 후보(배열 IN · 고정 레이아웃 struct)의 판단은 §9-1을 보고 하라** — 그 표의 근거가
> 두 번 연속 틀렸기 때문에 다시 잰 것이다.

**§3a-2에서 실측했다 — 아래 첫 줄은 우선순위가 아니다.** `else`(`if c { } if !c { }`로 우회) ·
`break`/`continue`(플래그) · 복합 대입(`i = i + 1`) · `for`. 업무 규칙 넷을 오늘의 언어로 써 봤을 때
**하나도 이것들 때문에 막히지 않았다.** 목록에 남겨 두지만, 근거 없이 위에서부터 집지 말 것.

**실제로 남은 벽은 데이터다:** 문자열 · 배열 · struct. **(2026-09-01 정정)** 여기 오래 적혀 있던
"두 번의 3라운드에서 배열이 **네 번** 벽"은 과장이었다 — 추적 가능한 것은 §3a-3의 **두 번**뿐이고,
§3a-2의 벽은 배열이 아니라 `out` 파라미터였다. 같은 수치가 `DECISIONS.md` D16 안에도 들어가 있었고,
사용자 승인으로 함께 정정했다(D16의 **결론은 그대로**다 — 근거 문장의 과장만 걷어냈다).

그리고 **2026-09-01 실측이 배열의 성격을 바꿨다:** 업무 규칙 6개가 **전부 오늘 컴파일되고 옳은 값을
낸다.** 배열은 능력의 벽이 아니라 **결합도의 문제**이며, 수요는 대부분 **IN 방향**(4/6)이고 IN은
빌린 포인터+길이라 **Q12를 쓰지 않는다.**

✅ **그것을 막던 Q12는 2026-08-31에 닫혔다**(§4-11): **caller-allocates**, 절단은 **D17 음수 status**,
**모듈은 할당하지 않는다.** 규약은 `HOST_ABI.md`의 "가변 길이 데이터". **이제 막는 것이 없다.**

그리고 결정하면서 **범위가 갈렸다**: 셋 다 힙이 필요한 것이 아니었다. **고정 레이아웃 struct(스칼라
필드만)는 힙이 필요 없어 Q12 밖**이고 — `out` 파라미터와 같은 기계장치에 타입만 복합이다 —
Q12가 지배하는 것은 **가변 길이**(문자열·배열·문자열을 품은 struct)뿐이다.

그 밖의 큰 것들: **D16의 나머지**(context handle — 모듈 수명 상태) · **1단계 콜백**(호스트 함수
등록이 선행) · **두 번째 호스트(C#)**. ROADMAP Phase 2의 내용이며, 각각 자체 SPEC이 필요하다.

> **다음 세션에 권한다: 후보를 고르기 전에 §7대로 업무 규칙을 한 번 더 써 볼 것.**
> 이번 세션에 **세 번** 그렇게 했고 세 번 다 값을 했다 — §3a는 전제가 틀렸고, §3a-2는 순서가
> 틀렸고, §3a-3은 **목록에 아예 없던 것**을 찾아냈다 — 그때까지 내장 함수가 하나도 **없었다**는
> 사실(#83이 넷을 넣었다).
>
> **다만 다음 후보는 §7을 또 돌리지 않아도 안다.** 네 번의 벽이 이미 가리키고 있고, Q12도 닫혔다.
> 셋이 열려 있다: ① **고정 레이아웃 struct** — 가장 작다(`out` 파라미터의 타입만 복합으로 넓히는
> 일이고 Q12 밖이다) · ② **문자열** — Q12 규약을 처음 쓰는 슬라이스 · ③ **배열**.
>
> ✅✅ **②가 완전히 닫혔다(§3a-4 입력 #89, §3a-5 반환 #92).** 반환이 Q12 프로토콜을 실제로 썼고
> **결함은 나오지 않았다** — 배열은 이제 검증된 프로토콜을 물려받는다. 남은 것은 ① 고정 레이아웃
> struct · ③ 배열, 그리고 실측이 요구한 **문자열 연결·포맷**(R2·R6)이다.
>
> ✅ **②가 닫혔다(§3a-4, #89) — 그리고 위 한 줄은 틀렸었다.** 문자열이 통째로 Q12를 쓰는 게
> 아니라, **입력은 빌린 인자라 Q12 밖**이고 **반환만 Q12를 쓴다.** 실측한 세 규칙이 전부 입력
> 쪽이어서 입력만 먼저 닫았다. **남은 것은 셋이다:** ① 고정 레이아웃 struct(Q12 밖, 실측 수요 거의 0)
> · ③ 배열(실측 수요 최대) · ④ **문자열 반환** — ③과 ④가 Q12 프로토콜의 첫 사용자 자리를 다툰다.
> **더 작은 ④에서 프로토콜의 결함을 찾는 편이 싸다**(SPEC-string-input §1.3과 같은 논리).

이 목록은 요약일 뿐이다. 설계에는 있는데 아직 없는 것을 훑으려면 `grep -rn "⏳" docs/`가
출발점이다(§5b). **전수 목록은 아니다** — 2026-09-01 실측: 43개 히트 중 **14개는 공백이 아니고**
(일부는 수용 기준 표에서 인벤토리를 *언급*만 한다), 반대로 `out string`처럼 **컴파일러가 오늘
거부하는 공백에 ⏳가 달려 있지 않은** 경우도 있다. 이 문장이 과장으로 지적된 것이 **세 번째**다 —
이 grep은 후보를 찾는 데 쓰고, 없는 것의 정본으로 쓰지 않는다.

> **그 grep을 어떻게 읽는가 (2026-08-31에 고친 것).** 한 줄이 곧 한 항목은 아니다. 대부분은
> **ABI·런타임·보호**의 공백이고, **언어 표면의 공백은 `LANGUAGE.md`의 "아직 아님" 블록 하나로**
> 잡힌다(`else`·`break`/`continue`·`for`·복합 대입·문자열·struct·`f64 %` …). 그 블록에 ⏳를
> 달아 둔 이유가 이것이다 — 그전에는 grep에 **언어 공백이 하나도 안 나와서**, 여기 §3b를 따라
> grep으로 간 사람이 그때 §3a가 권하던 슬라이스조차 볼 수 없었다.

## 4. 사용자 결정 대기

측정은 끝났고 판단만 남은 것들이다. **혼자 정하지 않았다.**

**열린 것과 닫힌 것은 각 항목의 ✅ 표시가 말한다 — 여기 다시 세지 않는다.**
✅가 아닌 행만 훑으면 열린 것이 나온다.

> *(2026-09-22: 여기 성격별 분류와 "닫힌 것 = …" 목록이 있었고, **셋을 틀리게 세고 하나를
> 빠뜨렸다** — 2·3·4는 본문에 ✅ 닫힘인데 열린 것으로 묶여 있었고, 2026-09-16에 추가된 12번은
> 분류에 **아예 없었다**. 바로 아래 줄이 "번호는 고정한다"고 선언하는 목록인데도.
> 같은 상태를 **두 곳에 두면 한 곳만 갱신되는 순간 나머지가 거짓이 된다** — 이 저장소가
> LOC·export 개수·게이트 목록에서 반복해 겪은 그것이고, 고치는 방법은 다시 세는 것이 아니라
> **한 곳만 남기는 것**이다.)*

**번호는 고정한다.** 닫힌 항목도 지우지 않고 ✅로 남긴다 — 다른 문서와 PR이 "§4-6" 같은 번호로
가리키기 때문이다.

✅ **11번(Q12)이 닫혔다(2026-08-31). 열린 항목 중 슬라이스를 막는 것은 이제 없다.**
남은 것은 저장소 설정·법률·범위 결정이다.
*(2026-09-22 정정: 여기 2번을 유일한 예외로 드는 문장이 있었다 — 내부 함수 파라미터를 Pascal
예약어로 짓는 것이 막힌다고. **그것도 오늘 막히지 않는다**: 2번은 2026-09-02 사용자 결정으로
닫혔고 `compiler/src/reserved.rs:52`가 그 결정대로 Pascal을 `NameScope::Bindings`에서만 검사한다.
§4의 머리말이 **자기 본문이 닫았다고 적은 것을 미결로 소개**하고 있었다.)*

> **여기 있던 문장이 §3b와 정면으로 모순됐다(2026-08-31 정정).** "어떤 슬라이스도 막지 않는다"라고
> 적혀 있었는데, 같은 세션의 §3b는 "다음 슬라이스는 사용자 결정(Q12)이 선행한다"고 말한다. 둘 다

### 5-4. 생성 모듈의 패닉은 프로세스를 죽이지 않는다 — 스레드를 무한히 돈다

여러 문서가 `i32 /0`을 두고 "`no_std`+`panic=abort`니까 **호스트를 죽인다**"라고 적어 왔다.
**코드를 읽어 보니 틀렸다.** 생성 크레이트가 실제로 담는 것은:

| 무엇 | 어디 | 값 |
|---|---|---|
| no_std | `compiler/src/codegen.rs:39` | `#![no_std]` |
| 패닉 핸들러 | `compiler/src/codegen.rs:58` | `#[panic_handler] fn ml_panic(_: &core::panic::PanicInfo) -> ! { loop {} }` |
| 패닉 전략 | 생성 `Cargo.toml`(`codegen.rs:286`) | `[profile.release] panic = "abort"` |

`no_std`에서는 **`#[panic_handler]`가 곧 패닉 런타임**이다. `panic = "abort"`는 언와인딩 테이블을
없앨 뿐, `abort()`를 부르는 것이 아니다. 그래서 패닉은 `ml_panic`으로 들어가 **`loop {}`에 갇힌다** —
호출한 호스트 스레드가 그 자리에서 영원히 돈다. 프로세스는 살아 있고, 그 스레드만 죽지도 돌아오지도
않는다.

**둘 다 측정된 적이 없고, 오늘은 측정할 수도 없다.** 지금 언어의 어떤 연산도 패닉에 도달하지 못하기
때문이다: `f64` 0나눗셈은 `inf`, `as`는 포화, 정수 산술은 wrap(`-i32::MIN == i32::MIN`으로
**실측**됨 — SPEC-unary), `i32`의 `/`·`%`는 **가드를 달아**
방출된다(#76 — 제수가 0이면 0을 돌려주고 `i32::MIN / -1`은 `wrapping_div`로 간다).
`#[panic_handler]`는 오늘 `no_std`를 만족시키려고 있을 뿐 **도달 불가능한 코드**다.
따라서 위 서술의 근거 수준은 **E1(소스 판독 + Grok 교차확인)이며 E2가 아니다.**

> **정정(2026-09-23): wrap의 원인은 프로필 기본값이 아니다.** 이 문단은 원래 정수 산술이 wrap하는
> 이유로 *release 프로필이 `overflow-checks`를 끄기 때문*을 들었다. 같은 파일 **§9-55.4가 그것을
> DISCREPANCY로 판정했고**, 코드가 그 판정을 지지한다: `compiler/src/codegen.rs`가 `i32`의
> `+ - *`에 **`wrapping_add`/`_sub`/`_mul`을 명시적으로 방출한다.** 프로필 핀은 헬퍼용 벨트이지
> 산출물의 근거가 아니다 — 환경이 `CARGO_PROFILE_RELEASE_OVERFLOW_CHECKS=true`로 검사를 되살려도
> 방출된 식은 여전히 wrap한다. 결론(패닉에 도달하지 못한다)은 그대로다.

**이것이 §3a의 논거를 바꾼다.** 결과가 "프로세스 종료"가 아니라 "스레드 정지"이므로, `i32 /0`은
**재귀와 같은 등급이 아니라 `while`(§5-2)과 같은 등급**이다. 그리고 저장소는 `while`을 메커니즘이
아니라 `HOST_ABI.md`의 생존성 계약으로 처리했다. `i32 /0`을 그보다 강하게 다뤄야 한다면 그 근거는
"더 치명적이라서"가 아니라 **"런타임에 판정 가능해서"**여야 한다. 설계 선택지 자체는 그대로다.

      하류 게이트 없이** 골든 텍스트만 붙들고 있었다.
      > **그 문장은 오래전에 낡았는데 현재형으로 남아 있었다**(2026-09-12 실측): `MATHLESS_GATE_FPC`가
      > **모든 예제의 생성 유닛**을 CI에서 `-Mdelphi -Sew`로 컴파일하고(§9-11), `MATHLESS_GATE_FPC_HOST`가
      > 스테이징 Pascal 호스트를 빌드·실행하며(§9-19), `MATHLESS_GATE_DELPHI`가 **진짜 `dcc64`로**
      > 로컬에서 같은 일을 한다(§9-15·§9-20). `dcc64`가 없다는 전제 자체가 2026-09-07에 사라졌다.
      > **CI에 도는 Delphi 게이트는 여전히 없다** — 그 한 줄은 지금도 참이다(§9-20).

      지목했고, 코드로 재확인해 정확했다.

### 5-6. ✅ 갚음 — `i32 /`·`%`가 왼쪽 피연산자를 건너뛰었다 (발견 2026-09-23, 상환 2026-09-23)

> **`SPEC-division-guard-operands`가 갚았다**(SPEC #287 / 구현 #291).
> 오늘 `compiler/src/codegen.rs`가 내는 모양은 이것이고, `doc_claims.rs`의
> `the_recorded_division_debt_still_matches_what_codegen_emits`가 **이 코드 블록과 방출 텍스트가
> 같은 문자열인지**를 검사한다:
>
> ```rust
> { let __l = <lhs>; let __d = <rhs>; if __d == 0 { 0i32 } else { __l.wrapping_div(__d) } }
> ```
>
> 아래는 **발견 당시의 기록**이다. 지우지 않는 이유는 §5의 요점 그대로다 — 갚은 것도 조용히
> 사라지면 안 된다.

`#76`이 나눗셈·나머지를 **전역(total)** 으로 만들면서 0 제수를 `0i32`로 되돌린다. 그 보호막이
**왼쪽 피연산자를 `else` 안으로 밀어 넣었다** — 그때 `compiler/src/codegen.rs`가 내던 모양:

```rust
{ let __d = <rhs>; if __d == 0 { 0i32 } else { (<lhs>).wrapping_div(__d) } }
```

오늘 식 자리에서 조기 반환하는 표현은 **정확히 둘**이다 — 배열 인덱싱(`codegen.rs:771`)과
문자열 부분 비교(`:1017`, `ml_sublen`이 음수면 bail). 그중 **`i32` 값을 내는 것은 인덱싱뿐**이므로
`/`·`%`의 왼쪽에 올 수 있는 것도 인덱싱뿐이다. 그 경계 검사가 `<lhs>` 안에 있고, 그래서 제수가
0이면 **검사 자체가 실행되지 않는다.**

> *(이 문단은 처음에 인덱싱이 조기 반환하는 **유일한** 식이라고 적었다. Grok이 부분 비교를
> 지적했고 코드로 확인했다 — 결론의 범위는 그대로지만, 근거가 한 칸 좁아졌다.)*

**실측 — 실제로 빌드한 모듈을 로더로 호출했다.** `export fn pick(xs: [i32], i: i32, d: i32) -> i32!`,
본문은 `return xs[i] / d`, `xs`는 원소 3개:

| 호출 | status | 값 |
|---|---|---|
| `pick(i=1, d=2)` | `0` | `10` |
| `pick(i=999, d=2)` | **`-2`** | — |
| `pick(i=1, d=0)` | `0` | `0` |
| `pick(i=999, d=0)` | **`0`** | `0` |
| `pick(i=-1, d=0)` | **`0`** | `0` |

**대조군이 요점이다.** 같은 인덱스가 제수 2에서는 `ML_ST_INDEX_OUT_OF_RANGE`를 내고 제수 0에서는
내지 않는다. 호스트가 보는 것은 "성공했고 답은 0"이다 — §0.1이 지문 슬라이스를 열게 만든 바로 그
**그럴듯한 오답**의 모양이고, 이번에는 인터페이스가 아니라 **한 식 안에서** 생긴다.

**범위도 쟀다**(같은 방법, 방출된 Rust 확인):

| 자리 | 결과 |
|---|---|
| `xs[i] / d` · `xs[i] % d` | **영향받는다** — 경계 검사가 `else` 안 |
| `xs[i] * d` | 영향 없다 — `wrapping_mul`은 피연산자를 무조건 받는다 |
| `n / xs[i]`(오른쪽) | 영향 없다 — `__d`로 **먼저** 묶이므로 검사가 실행된다 |
| `try f(x) / d` | 해당 없다 — 파서가 거부한다(`try`는 식이 아니다) |

**고치지 않았다.** 무엇이 옳은지가 설계 질문이기 때문이다 — 왼쪽을 `__d` 앞으로 끌어올려
**항상 평가**할 것인가(단락 평가가 사라지고 `/0`의 전역성은 유지된다), 아니면 `/0`을 실패 가능
연산으로 되돌릴 것인가(DP-N4가 "정의된 결과"로 닫은 것을 다시 연다). **SPEC 없이 시작하지 않는다**
(`CLAUDE.md` 개발 방법론 1).

> **§5-1이 갚은 부채의 거울상이다.** 거기서는 범위 밖 인덱스가 `&&`의 단락 평가를 **보이게** 했고,
> 여기서는 `/`가 만든 단락 평가가 그 인덱스를 **안 보이게** 한다. 같은 관측 수단이 한 번은 계기,
> 한 번은 피해자다.
>
> **그리고 누군가 이미 적어 뒀다.** `SPEC-fallible-calls` §5.3이 *"`i32` 나눗셈의 오른쪽-먼저
> 평가 — §2.2가 도달 불가능하게 만들 뿐 고치지는 않는다. **식 위치를 여는 날 먼저 고쳐야 한다**"*
> 라고 2026-09-01에 남겼다. 맞는 예견이었는데 **문이 예상한 쪽에서 열리지 않았다** — `try`가
> 식 자리에 온 것이 아니라 `#200`의 배열 인덱싱이 왔다. §5-1과 정확히 같은 실패다: 부채가 무엇이
> 오면 달라지는지를 적어 뒀고, 그것이 왔을 때 그 줄을 다시 읽은 사람이 없었다.
>
> **Grok이 찾았다.** 이 세션의 다른 검증 라운드에서 묻지 않은 결함으로 지목했고, 방출된 Rust와
> 로드한 모듈 양쪽으로 재확인했다.

## 5b. 공개 준비 — 두 번 훑었다 (2026-08-30, #63·#64)

## 7. 작업 방식 (효과가 확인된 것)

- **다음 슬라이스는 실측으로 고른다.** 후보를 나열하지 말고 **실제 업무 규칙을 오늘의 언어로 써 보고**
  어디서 깨지는지 본다. "단가 × 수량이 안 된다"(곱셈을 루프로 흉내내야 했다)는 이렇게 나왔고,
  기능 목록을 비교하는 것보다 훨씬 나은 근거였다.
- **절차:** SPEC(`docs/slices/SPEC-*.md`) → **사용자 확인** → TDD(Red→Green) → **`grok_build_verify`** →
  PR → squash-merge. `main` 직접 커밋 금지. 머지 후 `docs/slices/README.md` 색인에 한 줄 추가.
- **Grok:** `grok_build_verify`는 필수 완료 게이트이고 **좁게** 써야 한다(2~3개 검증 가능한 주장 +
  분량 상한 + REVIEW ONLY). 넓은 프롬프트는 반복해서 타임아웃했다.
  > **축은 길이만이 아니다 (2026-09-11 관측).** AR1에서 `grok_build_verify`가 **300초에 두 번**
  > 타임아웃했는데, 둘 다 *반례를 찾아라*는 요청이었다 — 세 주장짜리 하나와, **한 질문으로 좁힌**
  > 것 하나. 좁히는 것만으로는 풀리지 않았다. 같은 코드를 두고 **한 함수를 읽고 판정 가능한 질문에
  > 답하라**로 바꾸자 **세 번 다 완료**됐다(폴백 거부 여부 · 2단 중첩 재귀 도달 여부 ·
  > `writes_before`의 내부 길이 인자가 버그인가). **탐색을 시키면 비싸고, 읽고 판정하게 하면 싸다.**
  > 그래서 verify에는 **닫힌 질문**을 주고, 반례 탐색이 필요하면 그것은 이쪽에서 프로그램을 써서
  > 실제로 돌려 보는 편이 빠르다(AR1은 적대적 프로그램 6개로 그렇게 했다). **다만 그 둘 중 어느
  > 것도 증명은 아니다** — 확인되는 것은 각 헬퍼가 주장대로 동작한다는 것까지다.
  `grok_build_plan`은 **설계·구성
  선택**에서 값을 했지만(그래서 `docs/slices/`와 단항→`&&` 순서가 정해졌다) 자주 비어서 돌아온다 —
  거기서 멈추지 않는다. **verify의 지적은 코드로 재확인한 뒤 반영한다** — 기존 동작을 새 회귀로
  오인한 사례가 있었다.
- **주장은 측정에 묶는다.** 없는 측정을 테스트로 만들지 않는다(§5-1이 그 예다).
- **"전부"라고 쓰기 전에 저장소 전체를 grep한다 — `*.rs`까지.** 2026-08-31 회고의 최대 발견이다.
  완전성 주장("여섯 곳 고쳤다", "잔존 없음", "이제 이 grep이 정본이다")이 **이미 열어 본 파일
  안에서만** 검증됐다. 그린 이후 정정 **6/18건**, 그중 **4건이 grep 한 번 거리**였다.
  #69는 문서 6곳을 고치고 "잔존 없음"이라 했지만 컴파일러가 그 뒤로 PR 3개 동안 사용자에게
  계속 틀린 말을 했고, #74가 통째로 그 재작업이다.
- **문서와 코드를 대조하는 것으로는 부족하다 — 실행해 봐야 한다.** 79건 감사가 "임시 트리를
  정리한다"는 과장을 놓쳤다. 코드를 읽어서는 알 수 없고, 임시 폴더를 **세어야** 안다(§5-5).
- **컴파일 여부가 아니라 값을 재라.** `mlc build`는 한 줄이지만 "그래서 얼마?"는 로더 15줄이다.
  그 비대칭 때문에 **"컴파일되고, 그럴듯하고, 틀린" 결함이 네 번 통과**했다(§3a-3, #85).
  ✅ **그 표준 도구가 2026-09-13에 생겼다(§9-49)** — `mlprobe`:

  ```
  cargo run -p mlc --bin mlprobe -- --src "export fn f(x: f64) -> f64 { return x * 2.0 }"
  ```

  스니펫 → 빌드 → 로드 → 호출 → **값 출력**까지 한 명령이다. 값을 재는 쪽이 이제 싸므로
  **비싼 쪽만 재던 비대칭이 없다.**
  *(2026-09-22 정정: 이 줄은 그 도구가 **없다는 전제**로 남아 있었다. §7은 다음 세션이 방법을
  고르는 절인데, 이 저장소에서 가장 값싼 실측 수단을 **여기서 배우지 못했다** — 언급이 §9-49에만
  있었다. 원문: *"표준 도구가 없으면 다음에도 싼 쪽만 재게 된다."*)*

- **넓은 변경에는 안전망을 먼저 세우고, 그 안전망을 먼저 적대적으로 검토하라.** export 래퍼
  리팩터(#101)에서 착수 전 분석이 **SPEC 자신의 수용 기준 두 개를 반증**했다 — 파일 크기는
  양자화돼 있어 신호가 못 되고, `.h`/`.pas` 동일성은 백엔드를 증명하지 않는다. 그 검토가 없었다면
  "전부 통과"가 아무것도 뜻하지 않는 하네스를 만들었을 것이다. **리팩터 뒤에 쓴 테스트는 그 변경이
  안전했다고 말해 줄 수 없다.**
- **골든 파일은 "넓은 변경"을 검토 가능하게 만드는 도구다.** 산출물 전체를 한 파일로 고정하면
  diffuse한 재작성이 **한 번 읽는 diff**가 된다. 불변량이 아니라 **검토 장치**로 쓴다.
- **텍스트를 고정하는 테스트는 그 텍스트가 유효한지 모른다.** #95에서 DP-C3를 주장하던 테스트가
  rustc를 안 불러 네 슬라이스 동안 초록이었다. 값이나 빌드로 재는 테스트가 하나는 있어야 한다.
- **팬아웃 실측은 착수 근거를 뒤집을 수 있다 — 그것이 팬아웃의 값이다.** 문자열 반환(#92)은
  "다음 벽"이라는 근거로 시작했는데, 업무 규칙 6개를 **실제로 빌드해 보니 4개가 이미 됐다.**
  슬라이스는 그대로 했지만 **근거를 바꿔서** 했고, SPEC §0이 그 정정을 남긴다. 착수 전에 §7을
  돌리는 비용은 SPEC 한 절이고, 돌리지 않는 비용은 **틀린 근거로 설계된 슬라이스**다.
- **프로토콜을 여는 슬라이스는 가장 작은 것으로 골라라.** Q12를 문자열로 먼저 쓴 이유였고
  (`SPEC-string-return.md` §0.2), 실제로 결함이 나오지 않아 **배열이 검증된 프로토콜을 물려받는다.**
  경계 테스트 도구(canary 버퍼)를 그 자리에서 만들어 두면 다음 슬라이스가 그대로 재사용한다.
- **보호 프록시는 절대값이 아니라 비교로 측정한다.** "import가 늘지 않는다"를 처음 실제로 재 봤더니
  (#89) 모든 cdylib이 DllMain 발판 때문에 CRT 시동 함수와 `vcruntime140!memcpy`를 **이미** import한다
  (25개). "CRT를 부르지 않는다"는 절대 주장은 그래서 **거짓이 된다** — 참인 주장은 "그 기능이
  집합을 늘리지 않는다"이고, 그것은 **같은 방식으로 빌드한 대조 모듈과의 집합 비교**로만 잰다.
  export 개수·크기도 같은 함정을 갖는다.

- **가드는 산출물을 지켜라 — 그것을 만드는 코드가 아니라.** 2026-09-03에 같은 실수를 세 번 했다:
  `header.rs`의 **소스 텍스트**를 매칭하는 가드를 쓰고 규칙을 지킨다고 믿었다. 실제로는
  ① 헬퍼를 남긴 채 호출부만 되돌리면 **회귀가 통과**하고, ② rustfmt 줄바꿈이나 이름 변경 같은
  **무해한 변경에 오탐**했다. 고치는 방법은 방출기를 호출해 **나온 텍스트**를 보는 것이다 —
  `emit_c_header`는 빌드가 필요 없으므로 `cfg(windows)`도 아니고 ubuntu 잡에서도 돈다.
  **나가는 것은 산출물이다.**
- **조건 뒤에 숨은 검사는 실패하지 않고 건너뛴다.** `if 방출물.contains(모양) { …검사… }`는
  모양이 바뀌는 순간 **조용히 통과**한다. 게이트가 필요하면 그 게이트 자체를 assert로 만든다.
  (Grok이 이 형태를 잡았다 — 가드를 쓴 바로 다음 검토에서.)
- **개명은 assert를 조용히 무력화한다.** Q14가 `ML_ERR_`를 `ML_<MODULE>_ERR_`로 바꾸자
  `!h.contains("ML_ERR_TRUNCATED")`는 **어떤 경로로도 실패할 수 없는 검사**가 됐다. 넓은 개명 뒤에는
  "이 assert가 아직 실패할 수 있나"를 따로 물어야 한다.
- **바닥값은 코퍼스에서 유도한다.** `>= 18`처럼 손으로 적은 하한은 코퍼스가 늘 때마다 **저절로
  헐거워진다** — 예제를 하나 더하자 여유가 1에서 2가 됐고 아무도 그렇게 결정하지 않았다.

### 7-1. 검증 절차 감사 (2026-09-03) — 왜 검증이 반복해서 헛돌았나

한 세션에서 결함 다섯 건이 나왔다. **어느 것도 테스트 어서션이 잡지 못했고, 어느 것도 Grok verify가
잡지 못했다**(그 세션의 verify 9회는 **전부 PASS**였다). 실제로 잡은 것은 이렇다:

| 결함 | 무엇이 잡았나 |
|---|---|
| `fmt --check \| tail && echo clean` (파이프 종료코드) | **CI** |
| `TempOut`을 `Module`보다 먼저 drop → 6개 누수 | **실행 전후 개수 세기** |
| `bool as string`의 잘못된 힌트 | **거부 목록 출력을 읽음** |
| 생성 헤더의 `/* */` 중첩 | **골든 diff를 읽음**(`contains()`는 전부 초록) |
| 체크 개수 105 vs 119 | **두 수치가 다른 것을 센다는 자각** |

**원인은 다섯 개가 아니라 넷이다.**

1. **프로젝트의 게이트를 그대로 쓰지 않고 편의 래퍼를 만들었다.** CI는 `cargo fmt --all --check`를
   그대로 부른다. 나는 출력을 줄이려고 `| tail -1 && echo clean`을 붙였고, `&&`는 **파이프라인의**
   종료 코드를 본다 — 즉 `tail`의 0. **게이트는 옳았고 내 래퍼가 틀렸다.**
   → **CI가 부르는 방식 그대로 부른다. 종료 코드를 읽는다.**
2. **verify는 내가 고른 주장만 검증한다.** 9회 PASS는 "9회 옳았다"이지 "9회 아무 문제 없었다"가
   아니다. 위 다섯 건 중 어느 것도 프롬프트에 없었다. → **verify는 2차 의견이지 독립 감사가 아니다.**
   감사를 원하면 **"내가 안 물어본 것 중 가장 위험한 것"을 따로 물어야 한다** — 실제로 그렇게 물었더니
   Grok이 §5-5.10을 찾아냈다.
3. **가드를 만든 사람과 믿은 사람이 같고, 그 사이에 아무 일도 없었다.** 일부러 깨 본 가드
   (복사본 갈라짐 테스트, 주석 중첩 스캐너)는 살아남았고, **깨 보지 않은 가드**(fmt 검사,
   `TempOut`의 경고)가 정확히 실패했다. → **가드는 일부러 깨서 실패를 본 뒤에만 가드다.**

   > **그런데 "깨 봤다"가 무엇을 증명하는지도 정해야 한다 (2026-09-23, #281 → #291).**
   > `the_recorded_division_debt_still_matches_what_codegen_emits`는 *"방출 모양을 바꾸는 사람이
   > 고쳐야 할 문단을 지목받는다"* 고 약속했고, 그것을 확인하려고 **조건을 뒤집어** 빨간 것을 봤다.
   > 반년 뒤 `SPEC-division-guard-operands`가 실제로 모양을 바꿨을 때 **가드는 조용히 통과했다** —
   > 조각 넷(`let __d =` · `if __d == 0 { 0i32 } else {` · `wrapping_div` · `wrapping_rem`)을
   > 고정했는데 새 모양에 넷 다 들어 있었기 때문이다.
   >
   > **규칙 둘이 따라온다.**
   > **① 심을 것은 지어낸 고장이 아니라 예상되는 변화다.** 가드가 *언젠가 X가 바뀔 것*이라
   > 존재한다면 심을 것은 **그 X의 변경**이다. "조건 뒤집기"는 아무도 하지 않을 변화다.
   > **② 조각이 아니라 모양 전체를 고정한다.** 조각 목록은 **어느 부분이 움직일지에 대한 추측**이고,
   > 문서가 생성 텍스트를 인용한다면 **두 문자열을 대조**해야 *"모양이 움직였다"* 와
   > *"이 테스트가 실패한다"* 가 같은 문장이 된다.

   > **딸린 비용 하나 (2026-09-16 실측).** 이 규칙을 **메모리 안전 가드**에 적용하면 확인 성공이
   > 곧 **프로세스 사망**이다(`0xC0000005`). 그러면 `TempOut`의 드롭이 돌지 않아 그 프로세스에
   > **그때 살아 있던 `TempOut` 전부**가 `%TEMP%`에 남는다. 단언 패닉은 드롭이 돌아 **증가분 0**이다
   > — 즉 **어떤 종류의 실패를 심었느냐가 갈린다.**
   >
   > **개수는 상수가 아니다** — 죽은 프로세스가 그때 몇 개를 들고 있었느냐다. `string_concat`에서
   > 쟀을 때가 **10개**이고, 그것은 그 파일에서 모듈을 만드는 테스트의 수다. 다른 파일은 다른 수가
   > 나온다. **검증이 이 과잉일반화를 잡았다** — 처음엔 *"한 번에 10개"* 를 비용처럼 적었다.
   >
   > **크래시를 확인했다면 `%TEMP%`를 한 번 세라.** §5-5.7.
4. **어서션의 강도를 위험에 맞추지 않았다.** `contains()`는 존재를 증명하지 유효성을 증명하지 않는다.
   하류에 진짜 게이트가 있으면(생성 Rust → cdylib 빌드, `.h` → 수용 D) 약한 어서션도 견딘다.
   **없으면 못 견딘다.** *(2026-09-22 정정: 이 줄이 그 자리를 `.pas`로 지목하고 있었다. 그때는
   맞았고 지금은 아니다 — `MATHLESS_GATE_FPC`가 생성 유닛 전부를 CI에서 컴파일하고,
   `MATHLESS_GATE_FPC_HOST`가 Pascal 호스트를 빌드·실행하며, `MATHLESS_GATE_DELPHI`가 로컬에서
   진짜 `dcc64`로 같은 일을 한다. §5-5.10이 그 변화를 ✅ 갚음으로 적어 두었는데 이 줄만
   따라가지 않았다. **오늘 하류 게이트가 없는 자리는 C# 바인딩이고, 그것은 아직 존재하지 않는다.**)*

> **그리고 이 교훈은 새 것이 아니다.** §7은 이미 *"텍스트를 고정하는 테스트는 그 텍스트가 유효한지
> 모른다"*(#95, 네 슬라이스 동안 초록)를 적어 두고 있었다. **적어 두는 것으로는 재발을 막지 못했다.**
> 위 네 줄이 규칙으로 쓰인 이유가 그것이다 — 서술이 아니라 **행동**이어야 한다.

### 7-4. ✅ 복기 뒤 정밀 감사 (2026-09-11, E2) — **링크된 호스트는 지문을 하나만 볼 수 있었다**

> **이 절이 연 구멍은 2026-09-12에 닫혔다(#213 SPEC / #215 구현, §9-31).** 아래는 **그날의 기록**이며
> 현재형으로 읽지 않는다 — `compiler/src/codegen.rs`가 오늘 방출하는 것은 모듈로 한정된
> `ml_iface_hash_<모듈>`이고, 이 절이 만든 함정 테스트는 뒤집혀 삭제됐다. 슬라이스는
> `docs/slices/SPEC-qualified-iface-hash.md`다. **§5 부채에는 붙이는 ✅를 이 절만 안 달고 있어서**
> 열린 ABI 구멍처럼 읽혔다(2026-09-23 감사).

§7-3을 쓰고 나서 같은 세션의 산출물을 **더 훑었다.** 문서 결함이 아니라 **ABI의 보호 구멍**이 나왔다.

#### 발견 — 측정값부터

모듈 둘을 링크한 C 호스트에서:

```
ml_iface_hash()        = 05697A6FAFD68344
ML_DISCOUNT_IFACE_HASH = 05697A6FAFD68344  <== 일치
ML_SCHEDULE_IFACE_HASH = 85A56496B143C25C     이름으로 도달 불가
```

모든 모듈이 **한정 없는 같은 이름**(`ml_iface_hash` · `ml_module_abi_version`)을 export하므로,
링커가 **조용히 하나를 고른다**. `cl /W4`가 경고를 한 줄도 내지 않는다.
**즉 링크하는 호스트는 최대 한 모듈의 지문만 검사할 수 있고, 나머지는 지문 검사 없이 호출된다.**

#### 왜 지금까지 안 보였나 — 주장의 범위

**§9-14가 이 함정을 Delphi에서 이미 찾았다**(`uses` 절의 마지막 유닛에 묶였다). 그때 이렇게 적었다:
*"C 호스트는 모듈 핸들마다 해석하므로 이 함정을 만날 수 없다."* **동적 호스트에 대해서는 참이다.**
**링크 호스트에 대해서는 거짓인데, 아무도 모듈 둘을 링크해 본 적이 없었다** — `c-host-link`는
62줄에 스칼라 모듈 하나를 부르고 있었다.

그런데 생성 `.h`는 모든 독자에게 *"both ways a C host can consume it"* 이라고 말한다.
**주장의 범위가 증거보다 넓었다** — §7-3 (5)와 같은 모양이고, 이번에는 문서가 아니라 **출하물**이다.

#### 한 것과 하지 않은 것

- **링크 호스트를 넓혔다.** `schedule`을 링크해 **버퍼 삼총사가 처음으로 링크 경로를 지났다**
  (probe → `malloc(n * sizeof *p)` → 7개 원소, 합 99,995). 단위가 원소라는 것을 **호스트 코드가
  곱셈으로 보여 준다.**
- **함정을 테스트로 고정했다**(`linking_two_modules_binds_one_fingerprint_and_the_linker_chooses`).
  **고치지 않았다** — 고침은 심볼 이름에 대한 ABI 결정이고 테스트가 정할 일이 아니다. 고치면 이
  테스트가 실패하고, 고친 사람이 의도적으로 지운다(AR1의 이음매 테스트와 같은 모양).
- **부수 발견**: 링크 호스트는 모듈이 하나만 없어도 `main` 전에 `0xC0000135`로 죽는다. 드리프트
  검사가 그 때문에 한 번 빨개졌고, 그 사실을 하네스 주석에 적었다.

#### 같은 라운드에서 닫은 다른 공백

**"모듈은 할당하지 않는다"**(D16·Q12의 핵심)가 **배열 슬라이스 두 곳에서 미측정**이었다.
문자열 슬라이스에는 있는 측정이 배열에는 없었다. 재 보니 **추가 import 0**이고(`malloc`·heap 없음),
두 곳에 영구 테스트로 넣었다. 일부러 CRT import를 심어 **7개 테스트가 빨개지는 것**을 확인했다.

> **절대값이 아니라 비교로 적는다**(§7). 기준 모듈도 DllMain 발판 때문에 `memcpy`·`memset`을
> 이미 import한다 — 참인 주장은 *"이 기능이 집합을 늘리지 않는다"* 뿐이다.

### 7-3. 한 세션을 실측으로 복기했다 (2026-09-11) — **네 가지가 반복해서 값을 잃었다**

9 PR(#201~#209) · 40 파일 · +3,024/−298 · 테스트 466 → 497. 잔해는 0이다(NUL 0 · 진단 공백 뭉침 0 ·
`-1` 리터럴 0 · 트리 clean). **아래는 그 세션에서 실제로 실패한 것만 적는다.**

**기존 가드가 내 실수를 12번 잡았다**(오라클 커버리지 4 · 문서 모듈 수 3 · abi 헤더 2 · C 호스트 예제 2 ·
언어 공백 목록 1). 그 밖에 **CI가 1번** 잡았고, 나머지는 내가 잡았다. 의도한 Red 16건은 정상 TDD다.

#### (1) 거부 테스트의 첫 Red는 **개수가 아니라 메시지를 읽는다**

AR1에서 15개 중 **9개가 헛돌며 통과**했다. `result`가 미지의 식별자라 파서 폴백이
`found Ident("result")`로 **소스를 되뱉었고**, needle `"result"`가 그것으로 만족됐다. 규칙은 하나도
강제되지 않은 채 초록이었다.

**잡은 것은 가드가 아니라 `-- --nocapture`로 출력을 읽은 것이다.** 그래서 이것이 규칙이 된다:
**거부 테스트를 처음 빨갛게 만들 때는 실패 개수가 아니라 각 메시지를 본다.**

> **기계적 규칙을 만들려다 두 번 실패했고, 그 실패가 이 항목의 값이다.**
> ① *"모든 거부 테스트가 일반 폴백을 배제한다"* → **기각**(Grok, 코드로 재확인).
> 소스 토큰을 되뱉는 템플릿이 `parser.rs`에 **6개**지 하나가 아니고, `language_gaps.rs`는
> **폴백을 받는 것이 계약**이라 규칙을 넣으면 옳은 테스트가 빨개진다.
> ② 텍스트 스캔 → **못 쓴다.** 후보 76건 중 대부분이 오탐이다(needle `i32`가 `-> i32` 소스에 있는 것은
> 진단이 옳게 말하는 것이다). **이 결함은 값싸게 자동화되지 않는다** — 그래서 절차로 둔다.

#### (2) 소스 편집에 **스크립트를 쓰지 않는다**

이 세션에서 **최소 6번** 실패했다: 문자열 이스케이프가 `\` 연속을 먹어 **#204가 방금 고친 공백 뭉침을
네 번 재현**했고, 잘못된 이스케이프로 테스트 파일에 **실제 NUL 바이트**를 썼다.

**복기 도중에도 같은 실패가 재현됐다.** 복기용으로 쓴 스캐너가 `\s`(백슬래시+s)를 만들어
**0건 매치**였고, 심어 둔 결함 둘을 모두 놓쳤다 — **일부러 깨 보지 않았으면 "깨끗하다"고 보고했을 것이다.**

피할 수 없으면 백슬래시를 `chr(92)`로 구성한다. 그러나 기본은 **편집 도구를 쓰는 것**이다.

#### (3) 배치 편집의 중간 실패는 **앞선 성공을 통째로 버린다**

여러 치환을 한 스크립트에 묶었더니 두 번째 단언이 실패하며 **첫 번째 성공까지 기록되지 않았다.**
그 사실을 **나중 빌드가 실패할 때에야** 알았다. 묶지 않거나, 단언을 전부 먼저 통과시킨 뒤 쓰기를
한 번에 한다.

#### (4) docs 전용 PR도 **관련 가드는 돌린다**

색인 행을 빠뜨린 채 푸시해 CI가 빨개졌다. **전체 스위트를 건너뛴 것 자체는 문제가 아니다**(Grok의
지적이고 동의한다 — 가드가 제 일을 했다). 문제는 **몇 초짜리 확인을 3분짜리 CI 왕복으로 미룬 것**이다:
`cargo test -p ml_oracle --test doc_claims`.

#### (5) 가드의 **범위**도 주장이다 — 그 사각지대로 거짓이 하나 빠져나갔다

복기를 마친 뒤 **그 세션의 산출물 자체를 감사했다.** 살아 있는 거짓 주장이 하나 나왔고,
하필 **가드가 이미 있는 항목**이었다.

`STATUS.md` §1이 게이트하는 모듈을 **15개**라고 적는 동안 `host.c`는 **18개**를 로드했다. 같은 주장을
하는 문서가 셋인데 `doc_claims`의 목록에는 **둘만** 있었다 — 그래서 가드 안의 둘은 그날 함께
고쳐졌고, **밖에 있던 하나만 계속 거짓말을 했다.** 같은 줄의 *"체크 146개"* 도 실측 **176**으로
이미 거짓이었다. **둘 다 같은 날 내 작업이 만든 것이다.**

**가드가 "문서가 `host.c`와 일치한다"고 주장하면서, 그 주장을 하는 문서 셋 중 둘만 보고 있었다.**

닫은 방식이 둘로 갈렸고 그 갈림이 요점이다:

- **모듈 수 → 가드 안으로.** `doc_claims`의 문서 목록에 `STATUS.md`를 넣었다. 심어서 깨뜨려
  확인했다(*"docs/STATUS.md says … gates 15 modules; host.c gates 18"*).
- **체크 수 → 숫자를 지웠다.** 게이트를 돌려야 나오는 값이라 기계로 묶을 수 없다. **묶을 수 없으면
  적지 않는다**(전역 SSOT).

**검토가 두 번째 사각지대를 찾았다**: export *"정확히 3개"* 는 `protection.rs`가 **사실은** 단언하지만
**문서의 숫자는 그 측정에서 유도되지 않았다.** export 집합은 이미 한 번 2 → 3으로 움직였다.
측정이 일어나는 자리에서 문서를 함께 묶었다 — `doc_claims`는 ubuntu에서도 돌아 빌드된 모듈을
읽을 수 없기 때문이다.

> **규칙 (2)를 이 항목을 쓰는 동안 세 번째로 어겼다.** 큰따옴표 안의 백틱을 bash가 명령 치환으로
> 먹어 문단이 망가졌고, `git checkout`으로 되돌리다 **같은 파일의 정당한 수정까지 잃었다.**
> 규칙을 적는 것과 지키는 것은 다른 일이다.

#### 그리고 새 규칙이 필요 없었던 것 하나

`| tail`로 cargo 대신 `tail`의 종료 코드를 읽었다. **§1이 그 함정을 경고해 두었고, 나는 그것을 읽은 뒤에
밟았다.** 규칙은 이미 있다. 필요한 것은 지키는 것이었다.

### 7-2. REVIEW ONLY가 지켜지지 않았다 — 그리고 도구는 그 사실을 보고하지 않았다 (2026-09-05)

`CLAUDE.md`는 verify 프롬프트에 **REVIEW ONLY**를 쓰라면서 이유를 괄호로 달아 두었다:
*"(도구가 파일을 고칠 수 있다)"*. 그 경고가 **실제로 일어났고, 하필 규칙 파일에서 일어났다.**

DP-H3(b) SPEC 작업 중 `grok_build_plan` 1회 + `grok_build_verify` 2회를 돌렸다. 셋 다 프롬프트
첫 줄이 REVIEW ONLY였고, **셋 다 결과에 `filesChanged: []`를 돌려줬다.** 그런데 그 뒤
`git status`가 **`M CLAUDE.md`** 를 보여줬다 — 내가 하지 않은 편집 4곳(문단 압축 3곳 +
`D01~D13` → `D01~D23`)이었다.

**세 가지가 동시에 참이다:**

1. 편집 자체는 **그럴듯했고 하나는 실제로 옳다** — `DECISIONS.md`는 D23까지 있으므로 규칙 1의
   `D01~D13`은 낡았다. **그래서 더 위험하다.** 검토 없이 남겼다면 "내가 쓴 문장"으로 굳었을 것이다.
2. **도구의 보고를 믿을 수 없다.** `filesChanged: []`는 "아무것도 안 고쳤다"를 뜻하지 않았다.
3. 규칙 파일은 **사용자 승인 대상**이다(§9-A A10이 PR #133을 그렇게 처리했다). 승인 없이 들어온
   변경을 조용히 유지하는 것도, 조용히 되돌리는 것도 옳지 않다 — **되돌리고 보고했다.**

> **규칙: Grok 호출 뒤에는 `git status`를 본다.** 도구가 뭐라고 보고하든. 그리고 예상 밖의
> 변경은 **내용이 옳아 보여도** 되돌린 뒤 사용자에게 보고한다. 옳은 변경이라면 정식 PR로 다시
> 올리면 되고, 그 비용은 한 줄이다.
>
> **남은 실측 항목:** `CLAUDE.md` 규칙 1의 **`D01~D13`은 `D01~D23`이어야 한다**(`DECISIONS.md`
> 확인). 규칙 파일이라 이 문서가 고치지 않는다 — 사용자 확인 후 한 줄 PR이다.
