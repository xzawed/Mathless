### 9-55. 우회를 **값으로** 다시 쟀다 (2026-09-15, E2) — 넷은 깨끗했고, **다른 데서 하나 나왔다**

§9-53이 셋째 칸(*모듈 안, 조용히 틀림*)을 찾은 방법은 하나다: **기록된 우회를 실제로 돌려 값을
읽었다.** 그러면 물어야 할 것은 *"같은 방법을 아직 안 쓴 곳이 어디인가"* 다.

#### 9-55.1 질문 — 앞선 두 표본은 **"컴파일된다"** 로 분류했다

§9-38의 문장이 그대로 적고 있다: *"다섯 다 우회가 컴파일된다(실측)."* **컴파일이고 값이 아니다.**
그 다섯 중 셋째 줄이 금액 포맷이고, §9-53이 나중에 재서 **조용히 틀렸다.** §9-46도 같다 — 값을
잰 것은 규칙 쪽이고, R5의 **우회**는 *"round(x) as i32 as string — 모듈 안"* 이라고만 적혔다.

전체 스물셋 중 **값을 읽은 적 없는 우회가 넷**이었다. 넷 다 `mlprobe`로 돌렸다.

| 우회 | 출처 | 결과 |
|---|---|---|
| 세율 상수 → 내부 `fn` | §9-38 #4 | ✅ `total(1000)=1100.0` · `net_of(1100)=949.9999999999999` — 뒤쪽은 **IEEE이지 우회 탓이 아니다**(`const`여도 같다) |
| `break` → 플래그 변수 | §9-38 #5 | ✅ `[3,4,5]→12` · `[3,4,-1,10]→7` · `[-1,100]→0` · `[]→0` |
| `out`을 못 읽음 → 지역 변수 | §9-53 | ✅ **컴파일러가 강제한다** — 아래 |
| `unit` Pascal 예약어 → 개명 | §9-53 | ✅ 목록이 완전하다 — 아래 |

**`out`은 강제되고 있었다.** 최종 대입을 건너뛰는 이른 `return`을 일부러 썼더니 거부한다:

```
`out` parameter 'counted' is not assigned on every path that returns — assign it before
this `return`, or the host reads whatever was in its own variable
```

그리고 `fail` 경로는 요구하지 않으며, 실제로 `out`을 **건드리지 않는다**(측정: `status=1`,
`counted`가 호스트 값 그대로). D17이 말하는 그대로다.

#### 9-55.2 `unit`을 넓혔다 — **예약어가 아니라 지시어** 쪽

Pascal 예약어 목록은 완전하다(표준 65 + `at`·`on`). 그래서 반대쪽을 물었다: **Delphi 지시어는
예약어가 아니라 통과한다.** `cdecl`·`external`·`name`이 파라미터 이름이 되면 생성 `.pas`에
`function mlx_f(cdecl: Double): Double; cdecl; external ML_MODULE;`가 나온다.

지시어 52개를 넣어 봤다. mlc가 39개를 받고 13개를 거부하는데 **거부는 전부 Rust/C 때문**이다
(`static`·`virtual`·`public`·`register`…), Pascal 때문이 아니다. 39개를 한 모듈에 넣어 재면:

- FPC `-Px86_64 -Mdelphi -Sew`(경고=에러)가 **exit 0**
- **FPC 호스트가 로드·호출해 값까지 맞다** — `mlx_f_cdecl(21)=42` · `mlx_f_external(1.5)=3` ·
  `mlx_f_name(-2.5)=-5` · `mlx_f_varargs(100)=200` · `mlx_f_absolute(0.25)=0.5`

**컴파일에서 멈추지 않은 것이 이 절의 요점이다** — 그것이 §9-55.1이 지적한 바로 그 약한 근거다.

#### 9-55.3 그런데 **다른 데서 하나 나왔다** — i32 산술

| 식 | 답 | status |
|---|---|---|
| `2000000000 + 2000000000` | **-294967296** | 0 |
| `100000 * 100000` | **1410065408** | 0 |
| `5000000000 as i32` | 2147483647 (포화) | 0 |

**같은 타입 안에서 두 규칙이 다르고, 하나만 문서에 있다.** `f64 as i32`의 포화는
`LANGUAGE.md`에 **측정된 언어 규칙**으로 적혀 있고, 단항 `-`의 wrap도 적혀 있다. **`+`·`-`·`*`는
어디에도 없었다** — 공백 목록이 *"체크드 오버플로"* 를 공백이라고만 말한다. 그래서
*"i32는 clamp한다"* 로 배운 저자가 산술에서 틀린다. 무한 함수라 **호스트가 들을 채널도 없다**.

**그리고 테스트도 값을 본 적이 없다.** 기존 고정은 전부 **생성 소스의 단어**다 —
`i32_division.rs`의 `rust.contains("}).wrapping_mul(c)")`. **§7-3의 모양이 저장소 자신의 테스트에
있었다**: 방출기가 단어를 썼다는 증명이지, 호스트가 숫자를 받는다는 증명이 아니다.

#### 9-55.4 검증이 내 진단 셋 중 **둘을 뒤집었다** — 그리고 실물이 더 낫다

`grok_build_verify`에 세 주장을 냈고 **FAIL**로 돌아왔다:

| 내 주장 | 판정 |
|---|---|
| `LANGUAGE.md`가 `+`·`-`·`*`를 말하지 않는다 | **CONFIRMED** |
| codegen이 그 셋을 맨 연산자로 낸다 | **DISCREPANCY** — `wrapping_add`/`_sub`/`_mul`로 **명시적으로** 낸다 |
| `overflow-checks = false`가 wrap의 원인이다 | **DISCREPANCY** — 원인이 아니다. 그 핀은 **헬퍼용** 벨트다 |

코드로 재확인했고 검증이 맞다(`codegen.rs` 945~947). **설계가 내가 가정한 것보다 낫다** — wrap이
프로파일에 기대지 않고 방출 식에 박혀 있으며, 이유도 적혀 있다(패닉이 `no_std`에서 호스트를
**죽이는 게 아니라 멈춘다**, §5-4). **참인 것은 첫 줄뿐이었고, 그것이 고칠 것의 전부다.**

#### 9-55.5 고친 것

`i32_arithmetic_wraps_and_these_are_the_values`가 로드된 모듈에서 값을 읽고, 기대값을
`a.wrapping_add(b)`로 **계산하지 않고 숫자로 적는다**(계산하면 의도치 않게 바뀐 lowering도
통과한다). `LANGUAGE.md`가 이제 값과 **포화와의 차이**를 말한다.

**세 팔 각각에 결함을 심어 확인했다** — `saturating_add`·`saturating_sub`·`saturating_mul`,
하나씩. 전부 잡히고 나온 값이 `2147483647`/`-2147483648`, 즉 **저자가 잘못 기대할 바로 그 수**다.

📌 **그리고 검증이 이 테스트의 범위를 잡았다.** 첫 판은 주석이 *"`+`·`-`·`*`"* 라고 써 놓고
**`mlx_add`만 불렀다**. `-`와 `*`는 codegen에서 같은 `match`의 **다른 팔**이므로 *"add가
wrap한다"* 는 둘에 대해 아무 말도 하지 않는다 — **#211이 가드에 대해 적은 것("가드의 범위도
주장이다")이 테스트에도 그대로 적용된다.** 셋을 다 부르도록 넓혔다.

> **남는 것 하나.** 이 넷을 잰 표본은 §9-38·§9-46·§9-53의 **기록된** 우회뿐이다. 기록되지 않은
> 우회 — 누군가 그냥 쓰고 지나간 것 — 는 이 방법으로 닿지 않는다.
