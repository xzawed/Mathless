#### 9-73.2. 구현 중에 잰 대가 — 헬퍼의 `return`도 좁힌다

SPEC §2.6은 `let` 추출만 적었다. 구현 중 같은 산술을 세 가지로 쟀다(46341, 제곱이 i32 밖): 인라인 `x * x / x`는 `46341`,
`let t = x * x  return t / x`와 `sq(x) / x`는 `-3`. 호출 잎은 헬퍼가 **돌려준 i32**를 잎으로 받을 뿐 그 안의 식을 넓히지
않는다 — 헬퍼의 `return`이 좁히는 자리다. §2.6과 `LANGUAGE.md`에 한 줄씩 더했고 `wide_intermediates.rs`가 세 값을 고정한다.

#### 9-73.3. 수용 F와 I, 그리고 크기

- **F — 실제 C 호스트**: 여섯 예제 어디에도 중간값만 넘치는 식이 없었다(본문을 전부 읽음). 그래서 DP-W11대로 한 식을
  바꿨다: `examples/schedule.mls`의 `one_payment`를 **두 누적 몫의 차** `principal * (month + 1) / months -
  principal * month / months`로(본문만 — 골든의 헤더·유닛 0줄, 지문 불변). 1,000,000,000을 12개월로 나누면 `month` 2부터
  `principal * (month + 1)`이 i32 밖이고 답은 든다. `host.c`가 `one_payment(1e9, 12, 2) = 83333334`와 열두 달 합 =
  원금을 받는다. **슬라이스 전 코드젠(8438cf9)으로 같은 `host.c`를 돌리면 새 검사 둘만 FAIL**(`GATE_D_FAILED (2)`),
  도메인 에러 검사는 통과한다.
  - **대가:** 나머지가 첫 달에 몰리지 않고 한 단위씩 퍼진다(100000/7이면 `month` 1·2·4·5·6). 합이 원금이라는 성질은 그대로이고
    어떤 입력에서도 답이 i32에 든다. `array_return.rs`가 새 값을 고정한다.
- **I — 626행**: 머지된 `main`(b077cb9)으로 빌드한 `mlprobe`의 출력이 시험 구현(PURE+CALL 최종)과 **626행 전부 같다**.
  표는 맞음 543 · 조용한 오답 44 · 참값이 드는데 `-3` 20 · 기타 18(판정 불명 0). `main` 대비 **출력**이 바뀐 행은 42이고, 범주 표의 순이동은 39다. §0.3의 무작위
  48,000호출은 시험 구현의 환경 스위치에 기대는 비교라 구현본으로 다시 돌리지 않았다 — **이 수용의 표본은 626행이다.**
- **크기**: 예제 26개 `.text` 합 95,334 → 95,472(+138), 모듈별 −123~+192, 여섯 모듈 — PURE로 잰 §0.4와 **같다**.
  `.text` virtual size를 PE 헤더에서 직접 읽었다. 바꾼 `one_payment`로는 `schedule`이 3640 → 3656.

#### 9-73.4. 결함 심기

커밋된 트리에서 열을 심었고(`--no-fail-fast`) 전부 제 테스트에서 떨어졌다: 배열 읽기를 잎으로(B, `-2`가 `-3`을 앞지름) ·
`while` 호출 허용(B와 C의 10초 기한) · 문자열 인자 검사 제거 · `byte_len`을 잎으로(B — 이 심기 전에는 잡는 단언이 없어
`direct_blen`을 더했다) · `try_from` 대신 `as i32`(다섯 테스트) · 0 제수 보호 제거(`checked_arithmetic`도) · 정확한 비교
제거 · `as f64`를 넓힌 채 변환 · 무한 본문도 넓힘 · `len`을 잎에서 뺌.

- **무한 본문 심기는 처음에 빌드가 깨져 떨어졌다** — `emit_exact`가 자기 bail을 따로 구했기 때문에 한쪽만 바꾼 심기가
  생성 Rust를 컴파일되지 않게 했다. 값이 아니라 빌드로 떨어진 빨강이라 두 곳을 같이 바꿔 다시 심었다(`plain` 100000 ≠ 14100).
- **대입 · 인자 · 인덱스에서 좁히는 단언은 첫 실행부터 초록이었다.** 그 셋만 담은 탐침을 슬라이스 전 코드젠으로 돌려
  `-3`, 지금 코드젠으로 정확한 값을 받아 단언이 둘을 가른다는 것을 보였다.

#### 9-73.5. Grok

- **plan**(SPEC 착수): PURE 대 FULL에 PURE · PURE 안의 재배열 없음 · `as f64`는 먼저 좁힌다(2^53 위의 i64가 반올림돼
  새 조용한 오답이 된다).
- **SPEC verify**: 규칙 서술 CONFIRMED · 건전성 논증 DISCREPANCY 둘(→ `byte_len`과 문자열 인자 호출을 잎에서 뺐고, *"트리
  밖의 무엇보다 먼저"* 를 *"트리보다 뒤에 평가되는 무엇보다 먼저"* 로 좁혔다) · 내부 일관성 DISCREPANCY(수용 I의 범위,
  §1/§2.1 경계, DP-W11의 §6, 표의 기타 열) → 재검증 CONFIRMED.
- **구현 verify** 여덟: 잎 집합 · 문자열 규칙 · `emit_exact`의 순서·0 제수·나머지 · `emit_wide`의 무한 본문 무변경과 비교
  관문 · bail 전달 · 문서 값 ↔ 단언 CONFIRMED. `loop_free_functions`의 DISCREPANCY는 **내 질문의 오류**였다(`If`만
  문장을 품는다고 썼는데 `While`도 품는다 — 코드는 그것을 이미 참으로 센다). 묻지 않은 지적 다섯은 코드로 다시 확인했다:
  `len` 잎과 대입·인자·인덱스 좁힘이 고정되지 않음 → **단언 추가** · `emit_exact`의 `unwrap_or_default` bail → **인자로
  받게 바꿈** · 비교 관문이 `rhs.ty`를 안 봄 → typeck가 양쪽을 한 타입으로 준다(주석) · `Len`이 피연산자를 무시 → `Len`에는
  피연산자가 없다 · 문자열이 아닌 `ConstStr` → 생길 수 없다.
- 타임아웃 1회 — 주장 둘을 한 호출에 묶은 것. 하나씩 다시 보내 닫았다.
