## 1. 목표 — 지금 쓸 수 없는 것 (실측)

표면에 **단항 연산자 층이 아예 없다.** 아래는 추측이 아니라 `mlc build` 실행 결과다(2026-08-29):

| 입력 | 현재 결과 |
|------|-----------|
| `return -5` | **파스 에러** — `expected expression, found Minus` |
| `return -1.5` | 파스 에러 |
| `return -x` | 파스 에러 |
| `if !b { … }` | 파스 에러 (`Bang` 토큰은 있지만 단항 파싱이 없음) |
| `if b == false { … }` | OK — 부정의 우회 수단 |
| `return 0 - x` | OK — 음수화의 우회 수단 |

즉 **음수를 직접 쓸 수 없다.** `0 - x`로 우회는 되지만, 상수 하나 쓰자고 뺄셈을 적는 언어는 곤란하다.

기준 함수(두 연산자를 모두 사용):

```text
export fn negate_if(x: i32, flip: bool) -> i32 {
  if !flip { return x }
  return -x
}
```

## 2. 계약 (Contracts)

### 2.1 문법

기존 사다리에 **단항 층을 하나** 끼운다(곱셈보다 강하게 결합):

```text
mul   := unary (('*'|'/') unary)*
unary := ('-' | '!') unary | primary
```

우결합이므로 `- -x`, `!!b`도 파싱된다(DP-U3). `-a * b`는 `(-a) * b`다.

### 2.2 타입 규칙

- `-e` : `e`가 **`f64` 또는 `i32`** 여야 하고 결과 타입은 같다. `bool`이면 에러.
- `!e` : `e`가 **`bool`** 이어야 하고 결과는 `bool`. 숫자면 에러.
- `-` 의 오버플로는 기존 정수 규칙과 같다 — **wrap**(DP-I4). 즉 `-i32::MIN == i32::MIN`이며,
  이는 §3에서 **측정**한다.

### 2.3 IR · codegen

- `IrExprKind::Unary { op: IrUnOp, operand }`, `IrUnOp::{Neg, Not}`.
- codegen은 Rust `-e` / `!e`로 내린다. Rust의 `!`는 정수에서 비트 반전이므로 **`bool`에만** 허용하는
  타입 규칙이 이 등가성을 지킨다.

### 2.4 `-> T!` 와의 충돌 없음

실패 가능 표식 `!`는 **반환 타입 뒤**에 오고 단항 `!`는 **식 앞**에 온다. 위치가 달라 모호하지 않다.
§3에 두 가지를 한 함수에서 쓰는 케이스를 넣어 회귀를 막는다.

### 2.5 ABI — **변화 없음**

식 수준 변경이다. export 집합·시그니처·헤더/유닛 텍스트는 그대로다.

## 3. 수용 기준 (측정 가능)

- **A. 컴파일:** `examples/negate_if.mls` → `mlc build`.
- **B. 로드·호출(오라클):** `mlx_negate_if(7, false) == 7`, `mlx_negate_if(7, true) == -7`, `abi == 1`.
- **C. 보호:** export = `mlx_negate_if` + `ml_module_abi_version` 2개. strip 유지.
- **D. 수용 D(실제 C 호스트):** `hosts/c-host/host.c`에 추가해 새 구문도 실제 C 호스트에서 호출한다.
- **오버플로 실측:** `-i32::MIN`이 `i32::MIN`으로 **wrap**함을 오라클로 확인한다(DP-I4 정합).
  (`i32::MIN`은 `0 - 2147483647 - 1`로 이미 표현 가능하다 — 실측 확인됨.)
- **부정(타입체크) 케이스:**
  - `-b`(bool) → 에러 · `!x`(i32/f64) → 에러
  - `!` 를 정수에 쓰면 Rust의 비트 반전으로 새지 않고 **타입체크에서** 막힌다
  - `- -x` / `!!b` 는 정상 컴파일(DP-U3)
  - `-> i32!` 함수 본문에서 단항 `!` 사용 정상(§2.4)

## 4. 설계 제안 (DP — **확인됨 2026-08-29**; Grok 권장안 그대로 채택)

| DP | 선택지 | 권장 | 근거 |
|----|--------|------|------|
| **U1 묶음** | `-`와 `!`를 한 슬라이스 vs 둘로 분리 | **한 슬라이스** | 같은 문법 생산 규칙 하나를 공유한다. 나누면 parse/typeck/IR을 두 번 열면서 얻는 게 bool 전용 타입 규칙 한 줄뿐 |
| **U2 리터럴 부호 접기** | `-2147483648`을 리터럴로 접기 vs **접지 않음** | **접지 않는다** | 구멍은 *철자*이지 값이 아니다 — `i32::MIN`은 `0 - 2147483647 - 1`로 **이미 표현된다(실측)**. 접으면 `-2147483648`은 되지만 `-(2147483648)`은 여전히 실패하는 C/Java식 함정이 생기고, "범위 밖 정수 리터럴은 거부"라는 현재 규칙에 특례가 붙는다 |
| **U3 결합성** | 우결합(중첩 허용) vs 중첩 금지 | **우결합, 중첩 허용** | 문법이 자연히 재귀적이다. 금지하려면 규칙을 따로 써야 하는데 얻는 게 없다 |
| **U4 오버플로** | `-i32::MIN` wrap vs 거부 | **wrap** | DP-I4(정수 산술 wrap)와 같은 규칙. 다른 규칙을 두면 설명할 수 없다. 측정해서 문서화한다 |

## 5. 범위 밖 / 미검증

- **`&&` / `||`** — 다음 슬라이스 후보다(§5.1).
- `else`, `break`/`continue`, 복합 대입, 비트 연산자, `~`.
- 어떤 항목도 측정 전까지 "확정/동작"으로 서술하지 않는다.

### 5.1 이 슬라이스를 먼저 하는 이유, 그리고 그에 대한 반론

Grok의 순위: **단항 → `&&`/`||` → `else`**. 단항은 토큰(`Minus`/`Bang`)이 이미 있고 문법 층 하나만
추가하면 되며 제어 흐름·ABI를 건드리지 않는다. `else`는 `block_always_returns`를 처음으로 손대야 해서
위험이 가장 크다.

**가장 강한 반론(Grok):** `&&`/`||`는 **우회 수단이 아예 없는** 유일한 부류다(특히 `while` 조건 안에서는
플래그 변수로 구조를 바꾸지 않는 한 불가능하다). `while`을 막 넣은 지금, 단항을 먼저 하면 복합 루프
조건은 계속 못 쓴다. — 이 SPEC은 그 대신 **단항을 `&&` 슬라이스의 선행으로** 본다: `!`가 있어야
`&&`/`||`가 자연스럽고(`!a && b`), 단항 층 없이 부울 연산자만 넣으면 문법을 두 번 고치게 된다.
