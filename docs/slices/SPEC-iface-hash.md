# Slice SPEC — 로드 시점 인터페이스 지문 `ml_iface_hash`

> **상태: 제안(proposed) — DP-H1~H10 사용자 확인 대기.** 2026-09-02.
> **근거 수준:** §0이 **E2 실측**(이 세션에 새로 측정한 드리프트 실험 — 실제 MSVC 호스트 + 두 개의
> 생성 DLL), §2가 E0 + 확정 결정 인용, §4의 관용구 비교가 **E1**(외부 도구의 문서화된 동작).
> **선행:** D18(예약 export 심볼로 버전을 노출) · #101(export 어댑터) · `hosts/c-host`(수용 D).
> **이 슬라이스는 언어 표면을 넓히지 않는다** — `.mls` 문법은 한 글자도 바뀌지 않는다.
>
> ⚠ **이것은 변조 방지가 아니다.** 드리프트 **감지**이며 `SECURITY.md`의 P1(무결성)과 다른 물건이다.
> §5.4가 그 경계를 적는다. 대외 문구에 "위변조를 막는다"로 쓰지 않는다(규칙 6).

## 0. 왜 — 측정부터

### 0.1 실험: 호스트를 한 번 빌드하고 모듈만 바꿨다 (E2, 2026-09-02)

`ARCHITECTURE.md:68`의 약속은 **"모듈 교체 = 파일 교체 + 재로드. 호스트 재빌드 없음"** 이다.
그 약속을 그대로 실행했다. C11 호스트를 **v1 인터페이스로 한 번만** 컴파일하고, 그다음에는
`module.dll` 파일만 덮어썼다. 호스트 exe는 두 실행에서 **바이트 단위로 같다.**

두 모듈은 오늘의 언어로 쓰였다(배열도 struct도 필요 없다):

```
// v1                                  // v2 — 업무 담당자가 할 법한 두 가지 수정
export fn rate(code: i32) -> f64       export fn rate(code: string) -> f64
export fn boxes(items: i32, per: i32)  export fn boxes(per: i32, items: i32)
     -> i32 { return items / per }          -> i32 { return items / per }
```

측정 결과:

| 호스트가 관측한 것 | 모듈 v1 | 모듈 v2 |
|---|---|---|
| `boxes(items=100, per=3)` | `33` | **`0`** — 크래시 없음, 오류 없음, **그럴듯한 오답** |
| `rate(code=1)` | `0.1000` | **CRASH `0xC0000005`** (정수 `1`을 `const char*`로 역참조) |
| `ml_module_abi_version()` | `1` | **`1`** — 유일한 기존 가드가 **작동하지 않는다** |
| `GetProcAddress` 3개 심볼 | 전부 성공 | **전부 성공** |
| DLL 파일 크기 | 9,728 B | **9,728 B** |

**결론 세 가지.**

1. **이름 기반 링킹은 타입 정보를 전혀 나르지 않는다.** `mlx_rate`는 두 모듈에 다 있고, 두 이름은
   같고, 두 시그니처는 호환되지 않는다. 로더는 그것을 알 수 없다.
2. **오늘 가진 가드는 이 실패를 볼 수 없다.** `ML_MODULE_ABI_VERSION`은
   `compiler/src/abi.rs`의 **상수 `1`** 이고 모듈의 시그니처와 무관하다(Grok 교차 확인 CONFIRMED).
   파일 크기도 신호가 아니다 — 두 DLL이 **정확히 같은 바이트 수**다(§5-5.1이 예고한 함정).
3. **이 위험은 배열을 기다리지 않는다.** `STATUS.md` §9는 이 드리프트 실패 2건을 **"배열 IN"의
   근거**로 적어 뒀지만, 위 실험은 **오늘의 스칼라·문자열 표면만으로** 둘 다 재현한다.

### 0.2 그리고 이것이 가장 중요한 설계 사실이다

D-1(조용한 오답)은 **C ABI 수준에서 v1과 v2가 구별되지 않는다.** 생성 헤더를 나란히 놓으면:

```c
/* v1 */ int32_t mlx_boxes(int32_t items, int32_t per);
/* v2 */ int32_t mlx_boxes(int32_t per, int32_t items);
```

**타입 목록이 같다.** 따라서 **C 타입만으로 만든 지문은 D-1을 잡지 못한다** — 그리고 D-1이 둘 중
**더 나쁜** 실패다(크래시는 즉시 보이지만, `33` 대신 `0`은 청구서에 실린다).

이 한 줄이 DP-H1을 결정한다: 지문은 **ABI 지문이 아니라 계약 지문**이어야 하고, 따라서
**파라미터 이름을 포함해야 한다.**

### 0.3 왜 지금인가 — 그리고 왜 이것이 언어 슬라이스보다 먼저인가

§9의 후보 셋 중 배열·문자열 포맷은 **표현력**을 넓힌다. 표현력을 넓히면 인터페이스가 더 자주
바뀌고, 인터페이스가 자주 바뀔수록 위 실패가 더 자주 난다. **먼저 계기를 달고 넓히는 편이 싸다.**

이 순서는 #101에서 확인된 방식이기도 하다: *"넓은 변경에는 안전망을 먼저 세운다"*(§7).

## 1. 목표

1. 컴파일러가 모듈의 **호스트 가시 인터페이스**로부터 결정론적 **64비트 지문**을 계산한다.
2. 모듈이 그것을 `ml_iface_hash()`로 export하고, 생성 `.h`/`.pas`가 **같은 값을 상수로** 박는다.
3. 참조 호스트(C 호스트 + Rust 오라클)가 로드 직후 **비교하고, 다르면 거부한다** — 호출하지 않는다.
4. §0.1의 두 실패가 **거부로 바뀐다**는 것을 실측으로 보인다.
5. **본문만 바뀐 모듈은 그대로 통과한다** — `ARCHITECTURE.md:68`의 약속을 깨지 않는다(§3-E).

**목표가 아닌 것:** 변조 방지, 서명, 무결성(P1). §5.4.

## 2. 계약 (Contracts)

### 2.1 인터페이스 매니페스트 (`ml-iface/1`)

지문은 바이트열 하나에서 나온다. 그 바이트열은 다음 규칙으로 **정확히** 만들어진다.

```
ml-iface/1\n
abi=<ML_MODULE_ABI_VERSION>\n
fn <name>(<param>[, <param>]*) -> <ret>\n      … export된 함수마다 한 줄
err <NAME>=<code>\n                            … 선언된 에러마다 한 줄
```

- `<param>` = `<이름>:<타입>` 이며, `out` 파라미터는 `out <이름>:<타입>`.
- `<타입>` = 표면 타입 이름 그대로: `f64` · `bool` · `i32` · `string`.
- `<ret>` = 반환 타입, 실패 가능이면 뒤에 `!` (예: `f64!`, `string!`).
- **`fn` 줄은 함수 이름의 바이트 오름차순으로 정렬한다**(DP-H4). `err` 줄도 이름 오름차순.
- **파라미터는 선언 순서 그대로** — 이 순서가 곧 D-1이 깨뜨린 계약이다.
- **내부 `fn`은 들어가지 않는다.** 호스트가 볼 수 없는 것은 계약이 아니다(#101 이후 내부 함수는
  export되지 않는다).
- 매니페스트는 **ASCII 전용**이다(생성 산출물 규칙).

`examples/discount.mls`의 매니페스트는 다음과 같다(예시):

```
ml-iface/1
abi=1
fn discount(price:f64, vip:bool) -> f64
```

### 2.2 지문 함수

**FNV-1a 64비트**를 매니페스트 바이트열에 적용한다(offset basis `0xcbf29ce484222325`,
prime `0x100000001b3`). 구현은 컴파일러 안에 **10줄**이며 **서드파티 의존성을 늘리지 않는다**
(`STATUS.md` §1의 "서드파티 0개"는 이 저장소의 불변량이다).

> **암호학적 해시가 아니다.** 목적은 사고(드리프트) 감지이지 공격 방어가 아니다. §5.4.

### 2.3 모듈이 export하는 것

```c
uint64_t ml_iface_hash(void);
```

`ml_*` 예약 네임스페이스에 속한다(D18). **export 집합이 2개 → 3개가 된다**(§5.2 — 비용을 숨기지 않는다).

### 2.4 생성 `.h`가 박는 것

```c
/* Interface fingerprint (ml-iface/1) for THIS header. Compare it against the module's
 * ml_iface_hash() right after loading and REFUSE the module when they differ: the
 * exported names are identical across incompatible interfaces, so name resolution
 * succeeds and the call is then either a wrong number or an access violation. */
#define ML_DISCOUNT_IFACE_HASH 0x1F2E3D4C5B6A7988ULL

uint64_t ml_iface_hash(void);
```

**상수 이름은 모듈 접두어를 갖는다**(DP-H10): `ML_<MODULE>_IFACE_HASH`. 모듈명을 대문자로 올리고
영숫자가 아닌 문자는 `_`로 바꾼다. 접두어가 없는 `ML_ERR_*`가 **다중 모듈 호스트에서 충돌한다**는 것이
이미 기록된 부채(`STATUS.md` §5-5.4)이며, **새 상수가 같은 결함을 반복하지 않게 한다.**

### 2.5 생성 `.pas`가 박는 것

```pascal
const
  ML_DISCOUNT_IFACE_HASH: UInt64 = $1F2E3D4C5B6A7988;

function ml_iface_hash: UInt64; cdecl; external ML_MODULE;
```

Delphi 쪽은 여전히 **DRAFT**다(`dcc64` 부재, `STATUS.md` §4-8) — 이 슬라이스가 그 상태를 바꾸지 않는다.

### 2.6 호스트 계약

`HOST_ABI.md`의 "버전" 절에 다음을 추가한다:

> 호스트는 로드 직후 `ml_module_abi_version()`과 `ml_iface_hash()`를 조회해, **자신이 컴파일된
> 헤더의 값과 다르면 모듈을 거부한다.** 지문이 다른 모듈을 호출하는 것은 정의되지 않은 동작이다 —
> 심볼 이름이 같아 해석은 성공하고, 결과는 잘못된 값이거나 접근 위반이다(실측, `SPEC-iface-hash.md` §0.1).

**이 계약은 권고가 아니라 이 저장소의 참조 호스트에서 강제된다**(§3-F). 서드파티 호스트에 대해서는
여전히 계약이며, 그 한계를 §5.1에 정직하게 적는다.

## 3. 수용 기준 (측정 가능)

무게중심은 **"무엇을 잡는가"보다 "무엇을 잡지 않는가"** 에 있다 — E가 이 슬라이스의 안전장치다.

| # | 기준 | 측정 |
|---|------|------|
| **A** | 같은 소스를 두 번 빌드하면 지문이 **같다** | 컴파일러 단위 테스트 + 두 DLL의 `ml_iface_hash()` 반환값 비교 |
| **B** | **파라미터 이름만** 바꾼 두 모듈의 지문이 **다르다** | §0.1의 `boxes(items,per)` / `boxes(per,items)` 쌍. **C 타입은 동일하다** — 이 기준이 D-1을 잡는 유일한 근거다 |
| **C** | 파라미터 **타입**을 바꾼 두 모듈의 지문이 **다르다** | §0.1의 `rate(i32)` / `rate(string)` 쌍 |
| **D** | export **선언 순서만** 바꾼 두 모듈의 지문이 **같다** | 거짓 거부 방지(DP-H4) |
| **E** | 함수 **본문만** 바꾼 모듈의 지문이 **같다** | 임계값 `0.10 → 0.12` 수정. **`ARCHITECTURE.md:68`을 깨지 않는다는 증거** |
| **F** | 참조 C 호스트가 드리프트 모듈을 **거부한다** | 수용 D 확장: v1 헤더로 빌드한 호스트에 v2 DLL을 준다 → **호출하지 않고** 거부 메시지 + 비0 종료. `0xC0000005`가 **나오지 않는다** |
| **G** | 오라클도 같은 거부를 한다 | `hosts/rust-oracle`에 드리프트 쌍 테스트 |
| **H** | export 집합 = **정확히 3개** (`mlx_*` + `ml_module_abi_version` + `ml_iface_hash`) | 자체 PE 리더 + `dumpbin /exports` 교차 확인 |
| **I** | `.text` VirtualSize 증가분을 **기록한다**(상한 없음) | #101이 만든 `pe::read_section`. **파일 크기는 쓰지 않는다** — 512바이트 양자화라 신호가 못 된다(§5-5.1, 그리고 §0.1에서 서로 다른 두 인터페이스가 같은 9,728 B였다) |
| **J** | import 집합이 **늘지 않는다** | 대조 모듈과 집합 비교(#89이 정한 방식). 절대 주장을 쓰지 않는다 |

## 4. 설계 결정 (DP — **사용자 확인 대기**)

| DP | 질문 | 권고 | 근거 / 반론 |
|----|------|------|-------------|
| **H1** | 지문에 **파라미터 이름**을 포함하는가? | **포함한다** | §0.2 — 포함하지 않으면 측정된 두 실패 중 **더 나쁜 쪽(조용한 오답)을 못 잡는다.** 반론: 순수 리네이밍이 호스트를 거부시킨다(거짓 거부). 그 비용은 기준 E가 아니라 **호스트 재빌드 한 번**이고, 대안의 비용은 **틀린 청구서**다 |
| **H2** | 지문 폭 | **64비트** (`uint64_t`) | 32비트는 수백 개 인터페이스에서도 충돌 확률이 실질적이다. x64 C ABI에서 `uint64_t` 반환은 레지스터 하나 |
| **H3** | 강제 방식 — export 비교(권고형) vs **심볼 이름에 지문을 박아** 로더가 강제 | **export 비교** | 이름에 박으면(`mlx_boxes__7f3a…`) 검사를 잊은 호스트도 `GetProcAddress`가 NULL을 돌려줘 **강제**된다 — C++ 이름 맹글링·Linux modversions의 관용구(E1). 그러나 D18의 네이밍 규약과 **열려 있는 Q14(export 접두어)** 를 이 슬라이스가 먼저 결정해 버리고, 기존 호스트·테스트·문서의 심볼 이름을 전부 깬다. **범위를 넘는다** |
| **H4** | 함수·에러 목록을 **정렬**하는가? | **정렬한다**(이름 오름차순) | 선언 순서 변경은 호스트에 아무 영향이 없다(이름으로 해석한다). 정렬하지 않으면 무해한 편집이 거짓 거부를 만든다 |
| **H5** | **모듈 이름**을 지문에 넣는가? | **넣지 않는다** | 지문은 **계약**을 증명하지 **신원**을 증명하지 않는다. 파일명은 Q14와 함께 열려 있고, 파일 이름을 바꿨다고 거부하는 것은 §0.1이 측정한 실패와 무관하다 |
| **H6** | **에러 코드 표**를 넣는가? | **넣는다** | `ML_ERR_*`는 생성 `.h`에 박혀 호스트로 들어간다. 코드를 재번호하면 호스트가 **조용히 오해한다** — D-1과 같은 부류다 |
| **H7** | 해시 알고리즘 | **FNV-1a 64** | 10줄, 결정론적, **서드파티 0개를 지킨다**. 암호학적 보증은 목표가 아니다(§5.4) |
| **H8** | `ml_module_abi_version` 불일치도 **거부**로 바꾸는가? | **바꾼다** | `HOST_ABI.md`가 거부 경로를 **⏳ 미구현**으로 적고 있다. 지문 거부 경로를 만드는 김에 같은 자리에서 닫는 것이 싸다. **⏳ 하나가 줄어든다** |
| **H9** | 참조 C 호스트는 **몇 개** 모듈을 검사하는가? | **로드하는 전부** | Grok 검증이 잡아냈고 코드로 재확인했다: 오늘 `hosts/c-host/host.c`는 `discount.dll`·`safe_div.dll` **둘만** 버전을 비교한다(`:177`, `:190`). 나머지는 아무것도 비교하지 않는다 |
| **H10** | 헤더 상수 이름 | **`ML_<MODULE>_IFACE_HASH`** | 접두어 없는 `ML_ERR_*`가 다중 모듈 호스트에서 충돌하는 것이 이미 기록된 부채다(§5-5.4). **새 상수가 그 결함을 반복하지 않는다** |

> **D18 개정이 필요하다(규칙 8 — 사용자 확인 대상).** D18은 예약 export 심볼을 `ml_module_abi_version`
> 하나로 적고 있다. `ml_iface_hash`를 두 번째 예약 심볼로 추가하는 **파생 상세**를 `DECISIONS.md`에
> 덧붙여야 한다. **확인 전에는 `DECISIONS.md`를 건드리지 않는다.**

## 5. 범위 밖 / 위험

### 5.1 가장 큰 위험: 검사하지 않는 호스트는 보호되지 않는다

Grok이 착수 검토에서 지적한 그대로다 — *"호스트가 assert만 하면 또 하나의 죽은 export가 된다."*
`runtime/ml_abi.h`가 **아무도 include하지 않는 채로 살아 있는 것**(§5-5.3)이 이 저장소에 이미 있는 선례다.

완화는 세 가지이고, **그중 어느 것도 서드파티 호스트를 강제하지 못한다**:

1. 참조 호스트 **둘 다**가 실제로 거부한다(§3-F/G) — 그래서 회귀가 테스트로 잡힌다.
2. 생성 `.h`가 **바로 위 줄에** 상수와 사용법 주석을 놓는다(§2.4). 문서가 아니라 헤더가 말한다.
3. `HOST_ABI.md`가 계약으로 적는다(§2.6).

강제까지 원한다면 DP-H3의 (b)가 답이지만 그것은 **Q14를 먼저 닫아야 하는 별도 슬라이스**다.
이 한계를 지우지 말고 `STATUS.md` §5에 부채로 남긴다.

### 5.2 export가 하나 늘어난다 — 보호 프록시 수치가 바뀐다

`SECURITY.md:35`와 `STATUS.md:23`이 **"정확히 2개"** 를 실측으로 적고 있다. 이 슬라이스는 그것을
**3개**로 만든다. 숫자를 조용히 두면 §7이 반복해서 지적한 "이미 열어 본 파일 안에서만 검증된
완전성 주장"이 된다 — **두 곳 다 같은 PR에서 고친다.**

영향 범위는 실측했다: `ml_module_abi_version`을 언급하는 파일 **26개**(테스트 22개 + 골든 3개 +
C 호스트 1개). 대부분이 export 집합을 정확히 고정한다. **골든 파일 diff를 읽고 커밋한다**(#101의 교훈).

### 5.3 거짓 거부는 실제 비용이다

파라미터를 리네이밍한 모듈은 **호스트 재빌드를 요구하게 된다**(DP-H1의 대가). 기준 E가 그 경계를
못박는다: **본문 변경은 통과한다.** 즉 "임계값 조정은 파일 교체로 나간다"는 §3a-5의 측정 결과가
그대로 유지된다. 바뀌는 것은 **케이스 집합·시그니처 확장**뿐이고, 그것은 §3a-5가 이미
"호스트 재빌드를 요구한다"고 측정한 부류다.

### 5.4 이것은 무결성(P1)이 아니다

`SECURITY.md`의 P1은 **변조**를 다룬다. 지문은 공격자를 막지 않는다 — 공격자는 지문 함수도 고친다.
FNV-1a는 암호학적 해시가 아니고, 그럴 필요도 없다. 이 슬라이스가 다루는 위협은 **사람의 실수**다:
호스트를 다시 빌드하지 않은 채 모듈을 교체하는 것. **문서·커밋 메시지에 "위변조 방지"로 쓰지 않는다**(규칙 6).

### 5.5 갚지 않는 부채

- `ML_ERR_*`의 접두어 부재(§5-5.4)는 **그대로 둔다.** 새 상수만 접두어를 갖는다(DP-H10). Q14는 열려 있다.
- `&&` 단락 평가 미측정(§5-1)은 이 슬라이스와 무관하다.
- `runtime/ml_abi.h`(§5-5.3)는 여전히 아무도 include하지 않는다. 이 슬라이스가 손대지 않는다.
