# Slice SPEC — 내부 함수와 호출 (`fn` + 호출식)

> **상태: 확정(accepted) · 구현 완료(shipped)** — 2026-08-29.
> §4의 DP-C1~C5와 **§5.1의 재귀 금지**가 승인·구현되었다. 구현: **WC1~WC6 = PR #57**(SPEC은 PR #56).
> `DECISIONS.md`는 바꾸지 않았다. 이 문서는 이제 **설계 기록**이다.
> **근거 수준:** E2 실측 — `discount4.dll`의 export가 **정확히 2개**이고 내부 헬퍼 `vip_rate`는
> **실제 C 호스트의 `GetProcAddress`에서 NULL**이다(바깥에서 측정한 D04/D05 주장). 재귀는 CLI에서
> `f -> f` / `a -> b -> a` 경로와 함께 거부된다.
> **근거 수준:** E0(문서 정합) + §1의 **E2 실측**. 새 측정값은 구현 후 E2.
> **선행:** `&&`/`||`(#55)까지의 식 표면. 설계 교차검토: Grok.
> **주의:** §5.1이 **재귀 금지**를 제안한다. `while` 때와 달리 여기서는 "문서화만"이 정답이 아니다.

## 1. 목표 — 지금은 로직을 나눌 수단이 없다

실측(2026-08-29):

| 입력 | 현재 결과 |
|------|-----------|
| `fn helper(x: i32) -> i32 { … }` (비-export) | **파스 에러** — `expected 'export', found Fn` |
| `return helper(n)` (export 함수 호출) | **파스 에러** — `(`에서 |

즉 **모든 함수는 `export`여야 하고, 서로 호출할 수 없다.** 모듈은 서로를 모르는 거대 export 함수의
평평한 목록이다. 우회 수단은 **없다** — 로직을 복사해 붙이는 것 말고는.

이 슬라이스는 제품 서사와도 직결된다: 내부 헬퍼는 **export되지 않으므로**, 모듈은 로직을 안에 두면서
export 심볼 수를 그대로 유지한다(D04/D05, 수용 C의 프록시).

기준 예:

```text
fn vip_rate(vip: bool) -> f64 {
  if vip { return 0.9 }
  return 1.0
}

export fn discount4(price: f64, vip: bool) -> f64 {
  return price * vip_rate(vip)
}
```

`vip_rate`는 **export되지 않는다.** export는 여전히 `mlx_discount4` + `ml_module_abi_version` 둘뿐이다.

## 2. 계약 (Contracts)

### 2.1 표면 `.mls`

- **`fn NAME(params) -> TYPE { … }`** — `export` 없는 선언은 **모듈 내부 함수**다.
- **호출식 `NAME(arg, …)`** — 식(expression) 자리에서 쓴다. `primary`에 붙는다.
- 호출 대상은 **모듈 안의 함수**다. 호스트 함수 import는 범위 밖(여전히 미구현).
- **선언 순서 무관**(DP-C4): 이름 해석은 2-패스다. 아래에 선언된 함수도 호출할 수 있다.
- **재귀 금지**(DP-C2, §5.1): 직접·상호 재귀 모두 **타입체크에서 거부**한다.

### 2.2 타입 규칙

- 인자 **개수**와 **각 타입**이 시그니처와 정확히 일치해야 한다(암시적 변환 없음, DP-I2와 같은 태도).
- 호출식의 타입은 피호출 함수의 반환 타입이다.
- **실패 가능 함수(`-> T!`)는 호출할 수 없다**(DP-C1): 그 함수는 값이 아니라 status+out-param으로
  내려가므로 식 자리에 놓을 수 없다. 별도 슬라이스.

### 2.3 codegen — 내부 함수는 export되지 않는다

- 내부 `fn`은 **평범한 Rust `fn`**으로 방출한다 — `#[no_mangle]`도, `pub extern "C"`도 붙이지 않는다.
- 따라서 export 테이블에 나타나지 않는다. **이것은 주장이 아니라 §3-C에서 측정한다**(자체 PE 리더 +
  `dumpbin /exports` 교차 확인).
- 생성 `.h`/`.pas`에도 내부 함수를 넣지 않는다 — 호스트가 부를 수 없는 이름이다.

### 2.4 ABI — **변화 없음**

export 집합·시그니처·헤더/유닛의 export 목록은 그대로다. 내부 함수는 이름 그대로 Rust 안에만 있다.

## 3. 수용 기준 (측정 가능)

- **A. 컴파일:** `examples/discount4.mls` → `mlc build`.
- **B. 로드·호출(오라클):** `mlx_discount4(100.0, true) == 90.0`, `(100.0, false) == 100.0`, `abi == 1`.
- **C. 보호(이 슬라이스의 핵심 측정):** 내부 헬퍼가 있는 모듈의 export가 **정확히 2개**
  (`mlx_discount4` + `ml_module_abi_version`)임을 확인한다. `.h`에 `vip_rate`가 **없음**도 확인한다.
- **D. 수용 D(실제 C 호스트):** `hosts/c-host/host.c`에 추가한다.
- **부정(타입체크) 케이스:**
  - **내부 함수 이름의 안전성**(Grok 검증에서 추가): 내부 이름은 `mlx_` 접두어 없이 **그대로** 방출되므로
    (a) 대상 언어 예약어(`fn type`)와 (b) 예약 접두어 `ml_`/`mlx_`(생성 심볼과 충돌: `fn mlx_foo` +
    `export fn foo`, `fn ml_panic`)를 **타입체크에서** 거부한다. 그 전에는 `cargo build of generated
    crate failed`로 죽어 원인을 알 수 없었다.
  - 직접 재귀 `fn f(x: i32) -> i32 { return f(x) }` → **거부**
  - 상호 재귀 `fn a() … b() …` / `fn b() … a() …` → **거부**(사이클 메시지에 경로 표시)
  - 없는 함수 호출 → 명확한 에러
  - 인자 개수 불일치 / 타입 불일치 → 에러
  - 실패 가능 함수 호출 → 명확한 "아직 지원하지 않음" 에러(DP-C1)
  - 내부 `fn`과 `export fn`의 이름 충돌 → 기존 중복 함수명 검사로 거부

## 4. 설계 제안 (DP — **확인됨 2026-08-29**; Grok 권장안 그대로 채택)

| DP | 선택지 | 권장 | 근거 |
|----|--------|------|------|
| **C1 범위** | 무오류 함수만 vs `-> T!` 피호출자 포함 | **무오류만** | `-> T!`는 값이 아니라 status+out으로 내려간다. 식 자리에 넣으려면 에러 전파 문법(`?` 같은)을 함께 설계해야 한다 — 별도 슬라이스 |
| **C2 재귀** | 허용(문서화) vs **금지** | **금지(직접·상호)** | `while`의 비종료는 **판정 불가**(정지 문제)라 계약 문서화가 최선이었다. 호출 그래프의 사이클은 **판정 가능**하다. 그리고 결과가 더 나쁘다 — 무한 재귀는 **스택 오버플로로 호스트 프로세스를 죽인다**(정지보다 심각). 나중에 허용으로 푸는 것은 **가산적** 변경이다 |
| **C3 export 호출** | export 함수도 호출 가능 vs 내부만 | **둘 다 호출 가능** | export는 "밖에서도 보이는 함수"일 뿐이다. 다만 **헬퍼를 export로 만들지 않는 것**이 요점이다 — 그러면 export 심볼이 새어 나간다(Grok 경고) |
| **C4 선언 순서** | 2-패스(순서 무관) vs 선언 후 사용 | **2-패스** | 상호 참조가 자연스럽고, 사이클 검사는 어차피 전체 그래프를 본다 |
| **C5 내부 함수 이름의 예약어 검사** | 전 대상(Rust/C/Pascal) vs Rust만 | **전 대상 유지** | 내부 이름은 Rust에만 방출되므로 C/Pascal 검사는 **과잉**이다. 그러나 규칙이 하나인 편이 예측 가능하고, 과잉 엄격은 안전한 방향의 오류다. 불편하면 나중에 완화한다(가산적) |

## 5. 범위 밖 / 미검증

- 호스트 함수 import, 함수 포인터/콜백, 재귀(DP-C2), `-> T!` 피호출자, 기본 인자, 오버로드.
- **단락 평가는 이 슬라이스로도 측정되지 않는다**(§5.2).
- 어떤 항목도 측정 전까지 "확정/동작"으로 서술하지 않는다.

### 5.1 재귀를 금지하는 이유 — `while` 때와 다르다

`while`(#49)에서는 비종료를 **문서화된 계약**으로 처리했다. 그 선택의 근거는 *"정적으로 막을 수 없다"*
였다 — 정지 문제. **호출 그래프의 사이클은 다르다: 판정 가능하다.** 게다가 결과가 더 나쁘다:

| | `while` 무한 루프 | 무한 재귀 |
|---|---|---|
| 결과 | 호출 스레드 **정지** | 스택 오버플로 → **프로세스 종료** |
| 정적 판정 | 불가(정지 문제) | **가능**(사이클 검출) |

그러므로 `HOST_ABI.md` §생존성을 복사해 붙이고 "같은 계약"이라고 말하는 것은 **정직하지 않다**(Grok
지적). 막을 수 있는 것은 막는다.

**대가:** 재귀 알고리즘은 MVP에서 표현할 수 없다. 배열도 힙도 없어 명시적 스택으로 우회할 수도 없다.
이는 **감수하는 한계**이며, 호스트를 죽이지 않고 재귀를 다룰 방법이 생기면 그때 푼다(가산적 변경).

### 5.2 이 슬라이스는 `&&` 단락 평가 부채를 갚지 않는다

기대했지만 **아니다**(Grok 교차검토). `false && f()`는 `f`가 실행되든 아니든 결과가 `false`다 —
공유 가변 상태도, 트랩도 없기 때문이다(`f64` 0나눗셈은 inf, `i32` 나눗셈 없음). `false && spin()`으로
"안 멈추는지" 보는 것은 **정지 여부 테스트이지 평가 의미론 테스트가 아니다.**

`SPEC-logical-ops` DP-B2의 부채는 **`i32` 나눗셈**, **식 자리의 `fail`**, 또는 **실제 부작용** 중
하나가 생길 때 갚는다. "Rust `&&`로 내려가니까 증명됐다"는 것은 **백엔드 E1이지 표면 E2가 아니다.**
