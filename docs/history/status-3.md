### 3a-9. ✅ 닫힘 — 문자열 연결과 `i32 as string` (2026-09-02, SPEC #107 / 구현 #108)

**모듈이 처음으로 바이트를 만든다.** [`SPEC-string-concat.md`](slices/SPEC-string-concat.md).
DP-K1~K9 사용자 확인(권고안 그대로).

**다음 세션이 알아야 할 것:**

1. **§9 표의 "6/6"도 과장이었다 — 이번에도 인용하지 않고 다시 재서 알았다.** 실제로는 **5/6**이다.
   R4(등급 라벨)는 #92가 이미 열어 뒀다. **§3a-8에 이어 같은 표에서 두 번째 정정이다.**
   그 표의 나머지 칸(배열·struct)도 **착수 전에 다시 재는 것이 맞다.**
2. **진단이 설계를 정해 줬다.** `let t = a`가 이미 **"모듈에 할당자가 없어 지역 문자열이 있을 곳이
   없다"** 고 말하고 있었다. 그래서 연결은 중간 값을 만들지 않는 방식 — **호스트 버퍼에 조각 단위로
   이어 쓰기** — 로만 가능하다. 숫자 조각의 폭은 **렌더링하지 않고 산술로** 구하므로 2패스(세고 → 쓰기)가
   유지되고, 절단 시 무기록(DP-T2 기각)이 그대로 지켜진다.
3. **f64 포맷은 능력의 벽이 아니었다.** §9가 이 후보의 주의사항으로 적어 둔 것인데,
   `round(x*100.0) as i32` + `/100`·`%100`이 **오늘 되고 값도 맞다**(실제 C 호스트에서 `1234.56 →
   1234·56`, `0.005 → 1센트`). 그래서 `f64 as string`을 **범위에서 뺐다** — `no_std`의 가장 비싼
   부분을 지지 않았다.
4. **`-> string!` 본문이 이제 버퍼를 직접 받는다**(`RetAbi::StringOut`). 어댑터는 **순수 전달**이 되어
   오히려 단순해졌고, **C ABI는 한 줄도 바뀌지 않았다** — 골든의 `.h`·`.pas` 삭제가 **0줄**이다.
5. **위험은 하나다: 패스 1과 패스 2의 길이가 어긋나면 호스트 버퍼를 넘어 쓴다.** 그래서 폭은
   **한 함수(`ml_ilen`)만** 준다 — `ml_wint`이 그것을 불러 쓴다. `i32::MIN`은 부호를 뒤집지 않고
   `u32`로 크기를 잡는다. 실제 C 호스트에서 `-2147483648`까지 확인했다.
6. **덤: §4-2가 야생에서 처음 걸렸다.** R1의 파라미터를 `unit`으로 쓰자 **Pascal 예약어로 거부**됐다.
   이 슬라이스가 고치지 않았다 — 사용자 결정이 선행한다. 다만 §4-2의 근거가 이제 관측이다.

### 3a-8. ✅ 닫힘 — 로드 시점 인터페이스 지문 `ml_iface_hash` (2026-09-02, SPEC #103 / 구현 #105)

호스트가 **자기가 빌드된 인터페이스와 다른 모듈을 거부한다.**
[`SPEC-iface-hash.md`](slices/SPEC-iface-hash.md). DP-H1~H10 사용자 확인(권고안 그대로).

**다음 세션이 알아야 할 것:**

1. **§9 표의 근거 한 칸이 틀렸었다 — 인용하지 않고 재현했더니 드러났다.** 그 표는 드리프트 실패
   2건을 **"배열 IN"의 근거**로 적어 뒀다. 실제로 재현해 보니 **오늘의 스칼라·문자열 표면만으로**
   둘 다 난다: 호스트를 v1로 한 번 빌드하고 모듈 파일만 바꿨더니 `boxes(items=100, per=3)`이
   33 대신 **`0`**(크래시 없음), `rate(code=1)`은 **`0xC0000005`**. 세 심볼 전부 해석되고,
   `ml_module_abi_version`은 양쪽 다 **1**, DLL 크기는 양쪽 다 **9,728 B**였다.
   **배열을 기다릴 이유가 없었다.** §7이 반복해서 말하는 것 그대로다.
2. **조용한 오답은 C ABI 수준에서 구별되지 않는다 — 그래서 지문이 파라미터 이름을 포함한다(DP-H1).**
   `int32_t mlx_boxes(int32_t, int32_t)`가 v1·v2 **양쪽의 선언**이다. 타입만 해싱했다면 둘 중
   **더 나쁜 실패**(크래시가 아니라 청구서에 실리는 오답)를 못 잡는다. 대가는 순수 리네이밍의
   거짓 거부이고, SPEC §5.3이 그것을 값으로 적는다. **지문은 ABI 지문이 아니라 계약 지문이다.**
3. **골든 diff를 읽다가 실제 결함을 잡았다.** 생성 헤더의 사용법 주석 안에 `/* … */`를 중첩해
   넣고 있었다 — C는 **첫 `*/`에서 주석을 닫으므로** 나머지가 코드가 된다(MSVC C4138 + `/WX` 파손).
   `contains()` 어서션은 **전부 초록이었다.** §7의 "텍스트를 고정하는 테스트는 그 텍스트가 유효한지
   모른다"가 그대로 재현됐다. 지금은 **주석 중첩 스캐너**가 고정하고, **그 스캐너가 나쁜 입력을
   실제로 잡는지도** 따로 고정한다(헛도는 가드를 만들지 않으려고).
4. **참조 C 호스트의 검사 대상이 2개 → 13개가 됐다.** `grok_build_verify`가 "`host.c`는
   `discount.dll`·`safe_div.dll`만 버전을 비교한다"를 지적했고 코드로 재확인했다(`:177`, `:190`).
   이제 로드하는 모듈 **전부**가 버전+지문 게이트를 통과해야 하고, 파라미터만 맞바꾼
   `pack_drift.dll`은 **거부된다** — 심볼은 그대로 해석되고 ABI 버전도 같은 채로(수용 D 출력).
   **`HOST_ABI.md`의 ⏳ 하나(버전 불일치 거부 경로)가 해소됐다.**
5. **export가 2개 → 3개다.** `SECURITY.md`의 P0 프록시와 README **두 판본**을 같은 PR에서 고쳤다.
   숫자를 조용히 두지 않는다.
6. **검사하지 않는 서드파티 호스트는 여전히 보호되지 않는다**(SPEC §5.1 — Grok이 착수 검토에서
   지적한 위험). 강제하려면 심볼 이름에 지문을 박아야 하는데(C++ 맹글링·Linux modversions 방식)
   그것은 별도 슬라이스다 — **Q14가 2026-09-03에 닫히며 막는 것은 없어졌고, 2026-09-05에
   하지 않기로 결정됐다**(DP-H3(b), `SPEC-symbol-embedded-hash.md`, #141). **이것은 무결성(P1)이
   아니다.**
   > *(2026-09-22 정정: 이 줄이 결정 뒤에도 **미결로** 적고 있었다. 절의 날짜는 2026-09-02지만
   > 이 문장은 09-03 사실을 인용하므로 **그 뒤에 손본 살아 있는 문장**이고, 날짜로 얼린 기록이
   > 아니었다.)*

### 3a-7. ✅ 닫힘 — "한 이름, 한 본문" export 래퍼 (2026-09-02, SPEC #100 / 구현 #101)

모든 함수를 `ml_fn_<name>` 본문 + export에 얇은 C ABI 어댑터로 쪼갰다.
[`SPEC-export-wrappers.md`](slices/SPEC-export-wrappers.md). DP-W1~W5 사용자 확인.

**다음 세션이 알아야 할 것:**

1. **안전망을 리팩터 전에 세운 것이 이 슬라이스에서 가장 값을 했다.** 착수 전 적대적 분석이
   **SPEC 자신의 기준 두 개를 반증**했다 — 파일 크기는 512바이트 양자화라 어댑터 결함을 못 잡고
   (실패 경로에 쓰는 잘못된 어댑터가 코드 16B를 더하고 크기는 **0B** 움직였다), `.h`/`.pas`
   동일성은 `header.rs`가 `codegen.rs`를 안 보므로 백엔드를 증명하지 않는다.
   **리팩터 뒤에 쓴 하네스는 "변경이 안전했다"를 말해 줄 수 없다.**
2. **`.text` VirtualSize가 이 저장소의 리팩터 계측기다.** 전후가 **동일**했다(discount 3432 ·
   quote 3480 · pack 3512 · deduction 4088 · vat 3624 · carrier 3768) — 어댑터가 완전히 인라인된다.
   `pe.rs`에 `read_section`이 생겼으니 다음 리팩터도 이것을 쓴다. **파일 크기는 쓰지 마라.**
3. **골든 파일이 "가장 넓은 변경"을 한 번 읽는 diff로 바꿨다.** 생성 Rust 202/94줄이 움직이고
   `.h`·`.pas`는 바이트 동일 — 예측 그대로였다. `MATHLESS_BLESS=1`로 재생성하되 **diff를 읽고**
   커밋할 것.
4. **제한이 두 개 줄었다**(DP-W4): `fn match`·`fn type`·`fn ml_panic`이 이제 합법이다.
   파라미터·지역 변수는 그대로 — 여전히 raw로 방출되고 #85의 `__d` 결함이 거기서 나왔다.

### 3a-6. ✅ 닫힘 — 실패 가능 함수 호출 `try` (2026-09-01, SPEC #96 / 구현 #97~#99)

모든 `-> T!` 함수가 **잎**이던 제한을 풀었다. [`SPEC-fallible-calls.md`](slices/SPEC-fallible-calls.md).
DP-F1~F10 전부 확인·구현 완료. **DP-F9(중복 `error` 값 거부)와 DP-F10(헤더 에러 출처 주석)은
WF8에서 닫혔다**(#99).

**다음 세션이 알아야 할 것:**

1. **근거는 수요가 아니라 §0.1이다.** 막히던 프로그램 6개의 우회책이 **전부 빌드된다**(줄 수 차이
   −3~+6). 진짜 비용은 헤더에 있다 — 규칙을 export로 승격하면 **호출자가 non-fallible이 되어**
   검증이 권고 사항으로 격하되고 ABI가 강제하지 않는다. 크기 차이는 **0바이트**였다.
2. **위치 제한이 이 슬라이스의 안전장치다.** `try`가 식 안에 못 들어가므로 `i32` 나눗셈의
   **오른쪽-먼저 평가**(#76이 넣었다)와 `&&` 단락 위험이 **도달 불가능**하다. 식 위치를 여는 날
   그 평가 순서를 **먼저 고쳐야 한다**(§5.3).
3. **단락 평가 부채는 갚지 못했다 — 초안은 갚겠다고 썼다가 정정했다.** 재려면 조건 안에 `try`가
   있어야 하는데 DP-F2가 그것을 금지한다. §5-1은 그대로 열려 있다.
4. **C ABI 무변경을 테스트로 못박았다**(§3-F). 기존 예제 다섯 개의 생성 선언을 문자열로 고정했고,
   그 테스트가 실제로 **제 잘못된 기대값을 잡아냈다**(파라미터명이 `sales`가 아니라 `amount`).

### 3a-5. ✅ 닫힘 — 문자열 **반환** (2026-09-01, SPEC #91 / 구현 #92)

Q12 caller-allocates 프로토콜의 **첫 사용자**. [`SPEC-string-return.md`](slices/SPEC-string-return.md).
DP-T0~T8 전부 사용자 확인. `-> string!` → `int32_t mlx_f(…, char* ml_buf, int32_t ml_cap, int32_t* ml_needed)`.

**다음 세션이 알아야 할 것:**

1. **이 슬라이스는 수요로 정당화하지 않았다 — §7 방식이 정당화를 뒤집었기 때문이다.**
   업무 규칙 6개를 오늘의 언어로 써서 빌드했더니 **4개가 i32 코드로 이미 됐다**(측정, 옳은 값).
   남은 2개는 이 슬라이스가 **해결하지 못한다**(반환값이 리터럴·파라미터 echo뿐이다).
   진짜 근거는 **드리프트**였다: 호스트를 한 번 빌드해 두고 모듈에 한 줄(`DHLE -> 4`)을 더했더니
   **그 호스트가 모르는 코드를 출력**했다 — `ARCHITECTURE.md:68`("호스트 재빌드 없음")과 정면 충돌.
   **임계값 변경은 파일 교체로 나가고, 케이스 집합 확장은 호스트 재빌드를 요구한다.**
   규칙별이 아니라 **변경별**로 갈린다.
2. **Q12 프로토콜을 실제로 써 봤고 결함이 나오지 않았다.** 그것이 배열보다 문자열을 먼저 둔 이유였고
   (SPEC §0.2), 목적은 달성됐다. **배열은 이제 검증된 프로토콜을 물려받는다.**
3. **canary 버퍼가 이 슬라이스의 도구였다.** 0xAA로 채운 64바이트 + `cap` 뒤 canary 하나로
   절단·딱 맞음·도메인 에러·음수 용량을 **한 번의 바이트 비교**로 잡는다. §7이 지적한
   "싼 측정과 비싼 측정의 비대칭"에 대한 곱셈기다. **다음 슬라이스에서도 이 도구를 먼저 만들 것.**
4. **DP-T2 — 확정된 표를 바꾸지 않기로 했다.** Annex K식 `buf[0]=0` 안전장치는 status를 무시한
   호스트를 지켜 주지만 Q12 표를 고치는 일이라 **기각**했다(규칙 8). 대가는 숨기지 않고
   `HOST_ABI.md`와 SPEC §2.8에 적었고, C 호스트 예제는 **호출 전에 버퍼를 반드시 초기화한다**(보통 `0`,
   바이트가 쓰였는지/안 쓰였는지를 봐야 하는 곳은 `0xAA`) —
   문서가 아니라 예제 코드가 습관을 보여 준다.

### 3a-4. ✅ 닫힘 — 문자열 **입력** 파라미터 (2026-08-31, SPEC #88 / 구현 #89)

`string` 파라미터 + `==`/`!=`. [`SPEC-string-input.md`](slices/SPEC-string-input.md).
DP-S1 = NUL 종료 `const char*`, DP-S2 = 불투명 바이트(둘 다 사용자 승인 = 권고안 그대로).

**§7을 또 돌려서 고른 것이 아니다** — Q12가 닫히며 열린 세 슬라이스 중 하나였고, 문자열이 필요한
방향을 다시 재 보니 **갈렸다**: 측정한 세 규칙(국가별 부가세율·카드 BIN·수출품 판정)이 **전부
문자열 IN · 스칼라 OUT**이었다. 그 방향은 **Q12를 쓰지 않는다**(빌린 인자라 할당이 없다).
문자열 **반환**이 Q12 프로토콜의 첫 사용자가 될 슬라이스이며, SPEC §5.1에서 분리했다.

**다음 세션이 알아야 할 것:**

1. **"import 집합 불변"을 처음으로 실제 측정했다.** 그러려면 PE 리더에 **import 테이블 읽기**가
   필요했고(`hosts/rust-oracle/src/pe.rs`), 그것도 `dumpbin /imports`와 교차 확인한다(11개 모듈).
   측정해 보니 **절대값으로는 주장할 수 없다**: 모든 cdylib이 DllMain 발판 때문에 CRT 시동 함수와
   `vcruntime140!memcpy`/`memset`을 이미 import한다(총 25개). 그래서 수용 C는 **문자열 없는 모듈을
   같은 방식으로 빌드해 집합이 정확히 같은지**를 본다. 앞으로 "import가 늘지 않는다"류 주장은
   이 비교 방식으로만 쓸 것.
2. **조용한 오답 후보가 하나 더 생겼고, 이번엔 막지 못한다.** Delphi `UnicodeString`을 `PAnsiChar`
   자리에 넘기면 **컴파일되고 크래시도 없고 아무 코드에도 맞지 않는다.** 모듈 쪽에서 막을 방법이
   없어(바이트만 보인다) 생성 `.pas` 주석과 `HOST_ABI.md`에 계약으로 적었다. `dcc64`가 없어
   **E1이며 E2로 확인할 수 없다** — Delphi가 붙는 날 가장 먼저 확인할 항목이다.
3. **codegen에서 `==`를 그냥 두면 포인터 주소를 비교한다.** `*const u8 == *const u8`은 Rust에서
   컴파일되고 주소를 비교한다 — 같은 바이트를 담은 호스트 문자열에 대해 조용히 `false`다.
   같은 모양이 다섯 번째다(§7). 여기서는 typeck이 아니라 **codegen이 가로챈다.**

### 3a-3. ✅ 닫힘 — 반올림 내장 함수 (2026-08-31, SPEC #82 / 구현 #83)

`floor`·`ceil`·`round`·`trunc`. [`SPEC-rounding.md`](slices/SPEC-rounding.md).

**§7을 세 라운드 더 돌린 결과다**(급여·주문·상환). 스칼라 로직은 **전부 컴파일됐고**, 벽은 둘이었다:
**배열**(두 번)과 **반올림**. 배열이 더 크지만 힙과 **Q12가 선행**하므로, 그동안 막을 수 있는 오답을
먼저 막았다.

**다음 세션이 알아야 할 것:**

1. **같은 모양이 세 번째였다.** `boxes(17,0)`(#76) · 죽은 out 파라미터(#80) · 반올림 포화(#83).
   셋 다 **컴파일되고 그럴듯한 숫자를 내고 틀렸다**, 그리고 셋 다 원인이 **`as`의 포화**였다.
   **비슷한 것이 또 있는지 볼 때 이 모양을 찾으면 된다.**
2. **`no_std`가 표준 라이브러리를 막는다.** `f64::floor`는 `std`에 있다. 앞으로 수학 연산을 더
   넣는다면 매번 같은 벽을 만나고, `libm`을 넣는 순간 **서드파티 0개**가 끝난다(§1).

### 3a-2. ✅ 닫힘 — 명시적 `out` 파라미터 (2026-08-31, SPEC #79 / 구현 #80)

값을 두 개 돌려줄 수단이 생겼다. [`SPEC-out-params.md`](slices/SPEC-out-params.md).

**§7의 방법이 §3b의 목록과 다른 답을 냈다 — 그게 이 항목의 요점이다.** 다음 슬라이스를 고르려고
업무 규칙 넷을 오늘의 언어로 써 봤더니 `else`·`break`·복합 대입은 **하나도 아프지 않았다**:
계층 수수료·등급 할인 + 공통 후처리·연체 상한·분할 납부가 전부 조기 `return`과 `let mut`로
자연스럽게 컴파일된다. 정작 막힌 것은 **값 두 개**였고, 그것도 **컴파일되면서** 막혔다 —
`out_tier: i32`가 값으로 받는 입력이라 아무 일도 하지 않았다.

**§3b의 목록을 다음 후보로 그냥 믿지 말 것.** 그 넷은 오늘도 목록에 있지만, 실제로 써 보면
우선순위가 아니다.

### 3a. ✅ 닫힘 — `i32` 나눗셈·나머지 (2026-08-31, SPEC #75 / 구현 #76)

`/`와 `%`가 들어왔고 **둘 다 전역(total)** 이다(DP-D1 = (b), 사용자 승인).
`x / 0` = `x % 0` = `0`, `i32::MIN / -1`은 wrap. 자세한 것은
[`SPEC-i32-division.md`](slices/SPEC-i32-division.md).

**다음 세션이 알아야 할 것 두 가지:**

1. **이 항목이 원래 적어 둔 정당화는 틀렸었다.** "정수 산술이 안 된다"고 했지만 실제로는
   `(a as f64 / b as f64) as i32`로 **되었고, 정상 값에서는 정확했다.** 진짜 구멍은 그 경로가
   `b == 0`을 **`2147483647`로** 바꾼다는 것이었다(측정). 표현력이 아니라 **실패의 소재**가 문제였다.
   → 교훈은 §7 그대로다: **후보를 나열하지 말고 업무 규칙을 실제로 써 볼 것.** 써 보지 않았다면
   이 슬라이스는 잘못된 근거로 설계됐을 것이다.
2. **`&&` 단락 평가 부채(§5-1)는 갚지 못했다.** 이 항목이 "트랩 가능한 첫 연산"을 기대했지만
   DP-D1이 전역으로 결정돼 **관측할 트랩이 없다.** §5-1은 그대로 열려 있다.

### 3b. 다음 후보

> ⚠ **이 절은 이력이다. 오늘의 근거는 §9-1이다(2026-09-02 재측정).** 아래 서술은 여러 세션에 걸쳐
> 쌓였고, 문자열 연결(§3a-9)처럼 이미 닫힌 항목을 아직 후보로 부르는 문장이 섞여 있다.
> **남은 두 후보(배열 IN · 고정 레이아웃 struct)의 판단은 §9-1을 보고 하라** — 그 표의 근거가
> 두 번 연속 틀렸기 때문에 다시 잰 것이다.

**§3a-2에서 실측했다 — 아래 첫 줄은 우선순위가 아니다.** `else`(`if c { } if !c { }`로 우회) ·
`break`/`continue`(플래그) · 복합 대입(`i = i + 1`) · `for`. 업무 규칙 넷을 오늘의 언어로 써 봤을 때
**하나도 이것들 때문에 막히지 않았다.** 목록에 남겨 두지만, 근거 없이 위에서부터 집지 말 것.

**실제로 남은 벽은 데이터다:** 문자열 · 배열 · struct. **(2026-09-01 정정)** 여기 오래 적혀 있던
"두 번의 3라운드에서 배열이 **네 번** 벽"은 과장이었다 — 추적 가능한 것은 §3a-3의 **두 번**뿐이고,
§3a-2의 벽은 배열이 아니라 `out` 파라미터였다. 같은 수치가 `DECISIONS.md` D16 안에도 들어가 있었고,
사용자 승인으로 함께 정정했다(D16의 **결론은 그대로**다 — 근거 문장의 과장만 걷어냈다).

그리고 **2026-09-01 실측이 배열의 성격을 바꿨다:** 업무 규칙 6개가 **전부 오늘 컴파일되고 옳은 값을
낸다.** 배열은 능력의 벽이 아니라 **결합도의 문제**이며, 수요는 대부분 **IN 방향**(4/6)이고 IN은
빌린 포인터+길이라 **Q12를 쓰지 않는다.**

✅ **그것을 막던 Q12는 2026-08-31에 닫혔다**(§4-11): **caller-allocates**, 절단은 **D17 음수 status**,
**모듈은 할당하지 않는다.** 규약은 `HOST_ABI.md`의 "가변 길이 데이터". **이제 막는 것이 없다.**

그리고 결정하면서 **범위가 갈렸다**: 셋 다 힙이 필요한 것이 아니었다. **고정 레이아웃 struct(스칼라
필드만)는 힙이 필요 없어 Q12 밖**이고 — `out` 파라미터와 같은 기계장치에 타입만 복합이다 —
Q12가 지배하는 것은 **가변 길이**(문자열·배열·문자열을 품은 struct)뿐이다.

그 밖의 큰 것들: **D16의 나머지**(context handle — 모듈 수명 상태) · **1단계 콜백**(호스트 함수
등록이 선행) · **두 번째 호스트(C#)**. ROADMAP Phase 2의 내용이며, 각각 자체 SPEC이 필요하다.

> 이번 세션에 **세 번** 그렇게 했고 세 번 다 값을 했다 — §3a는 전제가 틀렸고, §3a-2는 순서가
> 틀렸고, §3a-3은 **목록에 아예 없던 것**을 찾아냈다 — 그때까지 내장 함수가 하나도 **없었다**는
> 사실(#83이 넷을 넣었다).
>
> **다만 다음 후보는 §7을 또 돌리지 않아도 안다.** 네 번의 벽이 이미 가리키고 있고, Q12도 닫혔다.
> 셋이 열려 있다: ① **고정 레이아웃 struct** — 가장 작다(`out` 파라미터의 타입만 복합으로 넓히는

> ✅✅ **②가 완전히 닫혔다(§3a-4 입력 #89, §3a-5 반환 #92).** 반환이 Q12 프로토콜을 실제로 썼고

> ✅ **②가 닫혔다(§3a-4, #89) — 그리고 위 한 줄은 틀렸었다.** 문자열이 통째로 Q12를 쓰는 게
> 아니라, **입력은 빌린 인자라 Q12 밖**이고 **반환만 Q12를 쓴다.** 실측한 세 규칙이 전부 입력
> 쪽이어서 입력만 먼저 닫았다. **남은 것은 셋이다:** ① 고정 레이아웃 struct(Q12 밖, 실측 수요 거의 0)
> · ③ 배열(실측 수요 최대) · ④ **문자열 반환** — ③과 ④가 Q12 프로토콜의 첫 사용자 자리를 다툰다.
> **더 작은 ④에서 프로토콜의 결함을 찾는 편이 싸다**(SPEC-string-input §1.3과 같은 논리).
