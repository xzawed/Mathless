# Slice SPEC — 문자열 연결과 `i32 as string`

> **상태: 확정(accepted) — DP-K1~K9 사용자 확인 완료(권고안 그대로), 2026-09-02.**
>
> | DP | 결정 |
> |----|------|
> | **K1** | `string + i32`는 **거부** — `n as string`을 쓴다. 암시적 변환 금지 규칙에 예외를 만들지 않는다 |
> | **K2** | 연결 연산자는 **`+`** |
> | **K3** | **`-> string!`의 `return` 식에서만** — 지역 변수·인자 위치는 여전히 없다 |
> | **K4** | **2패스 + 조각 목록**, 중간 버퍼 없음 |
> | **K5** | **`f64 as string`은 범위 밖** — 정수 센트로 환원되고 값을 실측했다(§0.3) |
> | **K6** | `bool as string`도 범위 밖 |
> | **K7** | 조각 개수 상한 없음 |
> | **K8** | 각 조각은 자기 NUL에서 끝난다. 결과의 NUL은 마지막에 한 번 |
> | **K9** | 모듈이 만드는 바이트는 **ASCII `-`·`0`–`9`뿐** |
>
> **K3의 대가를 지우지 않는다** — 이름 붙은 중간값이 필요한 규칙은 여전히 막힌다(§5.1).
> 그것은 D16의 귀결이며, 여는 길은 **호스트 스크래치 버퍼**로서 별도 슬라이스이자 별도 결정이다.
> **근거 수준:** §0이 **E2 실측**(오늘의 언어로 쓴 업무 규칙 6개 + 실제 C 호스트로 잰 값),
> §2가 E0 + 확정 결정 인용(Q12·D16·D17·DP-S2·DP-T2·DP-T4).
> **선행:** 문자열 반환 #92(Q12 프로토콜) · 문자열 입력 #89 · `as` #59 · `i32` 나눗셈 #76.
> **C ABI는 바뀌지 않는다** — 생성 `.h`·`.pas`가 기존 예제에서 **바이트 단위로 같아야 한다**(§3-G).
>
> ⚠ **이 슬라이스는 할당자를 도입하지 않는다.** 결과는 **호스트가 준 Q12 버퍼에 직접 이어 쓴다.**
> 그래서 문자열 **지역 변수는 여전히 없다**(§5.1) — 그 제한이 이 설계를 성립시킨다.

## 0. 왜 — 측정부터

### 0.1 업무 규칙 6개를 오늘의 언어로 썼다 (E2, 2026-09-02)

`STATUS.md` §9는 이 후보를 "6/6 전부 막힌다"로 적어 뒀다. **인용하지 않고 다시 썼다.**
(§3a-8이 바로 이 표의 다른 칸을 실측으로 뒤집었기 때문이다.)

| 규칙 | 오늘의 결과 |
|---|---|
| R1 영수증 줄 `"WIDGET x 3 = 45000"` | ❌ `operator Add expects two f64 or two i32 operands, found string and string` |
| R2 성명 결합 `last + " " + first` | ❌ 같은 에러 |
| R3 송장 번호 `"INV-" + 000123` | ❌ 자릿수 채우기를 쓸 수단이 없다 |
| R4 등급 라벨 `"GOLD"` | ✅ **컴파일된다** — #92의 리터럴 선택 |
| R5 주소 한 줄 `city + " " + district` | ❌ 같은 에러 |
| R6 금액 표기 `"1,234,567 KRW"` | ❌ 자릿수 그룹화를 쓸 수단이 없다 |

**5/6이 막힌다.** §9의 "6/6"은 과장이었다 — R4는 #92가 이미 열었다. 숫자를 정정하고 간다.

### 0.2 막는 것은 정확히 세 가지다 (원시 연산 단위로 분리해 측정)

| 시도 | 결과 |
|---|---|
| `a + b` (string, string) | ❌ `operator Add expects two f64 or two i32 operands` |
| `a + n` (string, i32) | ❌ `… found string and i32` |
| `n as string` | ❌ `cannot cast i32 to string — as converts between f64 and i32 only` |
| `let t = a` (string 지역 변수) | ❌ **`the module has no allocator — there is nowhere for a local to live`** |

**마지막 줄이 이 슬라이스의 설계를 결정한다.** 진단이 이미 옳은 이유를 말하고 있다: 할당자가 없다.
따라서 연결은 **중간 값을 만들지 않는 방식**으로만 가능하다 — 호스트 버퍼에 **이어 쓰기**다.

### 0.3 f64 포맷은 능력의 벽이 아니다 (§9의 주의사항에 대한 답, 실측)

§9는 "`no_std`에서 f64 포맷이 비싸다"를 이 후보의 주의사항으로 적었다. **맞는 말이지만
이 슬라이스는 그것을 필요로 하지 않는다.** 소수 금액은 **정수 센트로 환원되고, 그 환원은 오늘 된다**:

```
export fn cents(amount: f64) -> i32 { return round(amount * 100.0) as i32 }
export fn whole(c: i32) -> i32 { return c / 100 }
export fn frac(c: i32) -> i32 { return c % 100 }
```

실제 C 호스트로 **값을 쟀다**(컴파일 여부가 아니라 — §7):

```
    1234.560 -> cents=123456  whole=1234  frac=56
       0.050 -> cents=5       whole=0     frac=05
      99.990 -> cents=9999    whole=99    frac=99
 1000000.000 -> cents=100000000 whole=1000000 frac=00
       0.005 -> cents=1       whole=0     frac=01
```

그러므로 **f64 → string은 범위 밖**이다(DP-K5). 편의의 문제이지 능력의 문제가 아니며,
`no_std`에서 가장 비싼 부분(shortest-round-trip)을 이 슬라이스가 짊어질 이유가 없다.

### 0.4 덤으로 관측된 것 — §4-2가 야생에서 처음 걸렸다

R1을 처음 쓸 때 파라미터 이름을 `unit`으로 했더니 **`parameter 'unit' is a reserved word in Pascal`**
로 거부됐다. `STATUS.md` §4-2가 예고한 바로 그 상황이며, **실제 업무 규칙을 쓰다가 걸린 첫 사례**다.
이 슬라이스가 고치는 항목은 아니지만, §4-2의 근거가 이제 가설이 아니라 관측이다.

## 1. 목표

1. `string + string`으로 **연결**할 수 있다.
2. `i32 as string`으로 **숫자를 문자열로** 만들 수 있다.
3. 둘의 결과는 **호스트가 준 Q12 버퍼에 직접** 만들어진다 — 할당자도, 중간 버퍼도 없다.
4. **절단은 지금과 똑같이 실패**이고, 그때 버퍼는 **한 바이트도 쓰이지 않는다**(DP-T2는 기각됐다).
5. **C ABI는 한 바이트도 바뀌지 않는다.**

**목표가 아닌 것:** f64 포맷, 문자열 지역 변수, 부분 문자열·길이·순서 비교, 할당자.

## 2. 계약 (Contracts)

### 2.1 표면 문법

```
return "INV-" + (seq as string)
return last + " " + first
return item + " x " + (qty as string) + " = " + (qty * price as string)
```

- `+`의 양변이 **둘 다 `string`**이면 연결이다. 한쪽만 `string`이면 **에러**다(DP-K1) —
  이 언어는 `f64 + i32`도 거부한다. 섞으려면 `as`를 쓴다. 규칙이 하나로 유지된다.
- `as string`은 **`i32`에만** 붙는다(DP-K5: `f64 as string`·`bool as string`은 범위 밖).

### 2.2 어디에 쓸 수 있나 (DP-K3)

**`-> string!` 함수의 `return` 식 안에서만.** 지역 변수에 담을 수 없고, 인자로 넘길 수 없다.

근거는 §0.2다: 담을 곳이 없다. 이것은 임시 제한이 아니라 **할당자 없음의 직접적 귀결**이며,
`try`가 문장 자리로 제한된 것과 같은 성격이다(SPEC-fallible-calls DP-F2).

### 2.3 lowering — 이어 쓰기, 2패스 (DP-K4)

연결식은 codegen에서 **조각 목록**으로 평탄화된다. 각 조각은 둘 중 하나다:

| 조각 | 무엇 | 길이를 아는 법 |
|---|---|---|
| **빌린 바이트** | 문자열 리터럴 · `string` 파라미터 | NUL까지 센다(기존 `ml_strout` 1패스와 같다) |
| **십진 숫자** | `<i32 식> as string` | **산술로 센다** — 렌더링하지 않고 자릿수만 구한다 |

그다음 **기존 프로토콜 그대로**:

1. **패스 1** — 모든 조각의 길이를 더하고 `+1`(NUL). `*ml_needed`에 넣는다.
2. `cap < needed`면 **`-1`을 돌려주고 끝**. `buf`는 **건드리지 않는다**.
3. **패스 2** — 조각을 순서대로 `buf`에 쓴다. 숫자 조각은 패스 1에서 폭을 알고 있으므로
   자기 칸에 **오른쪽부터** 채운다. 마지막에 NUL.

**중간 버퍼가 없다.** 숫자를 미리 렌더링해 둘 곳이 필요 없기 때문에 할당자도 필요 없다 —
이것이 이 설계의 전부다.

> **`i32::MIN`.** `-2147483648`은 부호를 뒤집으면 넘친다. 크기는 **부호 없는 값으로** 다룬다
> (`(n as u32).wrapping_neg()`). §3-D가 이 값을 고정한다.

### 2.4 바이트 의미 (DP-S2의 확장, 정직하게)

지금까지 모듈은 문자열을 **비교만** 했다 — DP-S2의 "불투명 바이트"가 문자 그대로 참이었다.
이 슬라이스는 처음으로 모듈이 **바이트를 만든다**(숫자). 그래서 규약이 한 줄 늘어난다:

> 모듈이 만드는 바이트는 **ASCII `-` 와 `0`–`9` 뿐**이다. 빌린 조각은 여전히 불투명하게
> 그대로 복사되며, 모듈은 그 내용을 해석하지 않는다.

ASCII 숫자는 모든 후보 인코딩(UTF-8·CP949·Latin-1)에서 같은 바이트이므로, **DP-S2의
"인코딩을 확정하지 않는다"는 그대로 유지된다.** 이 문장이 없으면 DP-S2가 조용히 거짓이 된다.

### 2.5 C ABI

**변경 없음.** `-> string!`의 선언은 지금과 같다:

```c
int32_t mlx_f(<params>, char* ml_buf, int32_t ml_cap, int32_t* ml_needed);
```

호스트가 하는 일도 같다: probe(`ml_cap = 0`) → 할당 → 재호출. §3-G가 이것을 테스트로 못박는다.

## 4. 설계 결정 (DP — **전부 확인 완료 2026-09-02**, 근거는 남긴다)

| DP | 질문 | 권고 | 근거 / 반론 |
|----|------|------|-------------|
| **K1** | `"x" + n`(string+i32)을 허용하는가? | **거부한다** — `n as string`을 쓰게 한다 | 이 언어는 `f64 + i32`도 거부한다. 허용하면 **암시적 변환 금지 규칙에 예외가 하나 생긴다.** 반론: 타이핑이 늘고 C#에서는 되므로 낯설다 |
| **K2** | 연결 연산자 | **`+`** | D15가 C 계열이고 C#/Java가 `+`다. 반론: `+`가 산술과 겹쳐 실수를 부른다 — 그러나 타입이 갈라 주고, K1이 섞임을 막는다 |
| **K3** | 어디에 쓸 수 있나 | **`-> string!`의 `return` 식만** | §0.2 — 담을 곳이 없다. `try`의 위치 제한과 같은 성격. 반론(Grok): **`let`에 못 담는 값은 진짜 값이 아니다** — 이름 붙은 중간값이 필요한 규칙은 여전히 막힌다. 사실이며 §5.1에 남긴다 |
| **K4** | lowering | **2패스 + 조각 목록, 중간 버퍼 없음** | 할당자가 없다. 1패스로 `buf`에 바로 쓰면 **DP-T2를 위반한다**(절단 시 무기록) — Grok이 지적했고 코드로 확인했다(`codegen.rs:501`) |
| **K5** | `f64 as string` | **범위 밖** | §0.3 실측 — 정수 센트로 환원되고 값이 맞는다. `no_std`의 가장 비싼 부분을 지금 지지 않는다 |
| **K6** | `bool as string` | **범위 밖** | 측정된 수요가 없다. `if b { return "true" }`로 오늘 된다 |
| **K7** | 조각 개수 상한 | **없음** | 평탄화된 목록이라 깊이가 비용이 아니다. 상한을 두면 그 숫자를 정당화할 근거가 없다 |
| **K8** | 빈 문자열·NUL | **각 조각은 자기 NUL에서 끝난다** | 빈 조각은 길이 0을 더한다. 결과의 NUL은 마지막에 한 번 |
| **K9** | 생성 바이트의 의미 | **ASCII `-`·`0`–`9`만** | §2.4 — 이 한 줄이 없으면 DP-S2가 조용히 거짓이 된다 |

## 5. 범위 밖 / 위험

### 5.1 가장 큰 제한: 이름 붙은 중간값은 여전히 없다

Grok이 착수 검토에서 지적했다 — *"`let`에 담을 수 없는 연결은 진짜 값이 아니다."* 맞다.
`let line = a + b` 다음에 `line`을 두 번 쓰는 규칙은 **이 슬라이스로도 막힌다.**

지금 그것을 여는 값은 **할당자**이고, 할당자는 D16이 금지한다(모듈은 할당하지 않는다).
따라서 이 제한은 **미완성이 아니라 결정의 귀결**이다. 여는 길이 있다면 그것은
"호스트가 준 스크래치 버퍼"이며 **별도 슬라이스이자 별도 사용자 결정**이다.
§0.1의 5개는 이 제한 안에서 전부 표현된다 — 그래서 이 슬라이스가 값을 한다.

### 5.2 위험: 패스 1과 패스 2가 어긋나면 버퍼 오버런이다

길이를 **두 번 계산**한다(한 번은 세고, 한 번은 쓴다). 두 계산이 어긋나면 호스트 메모리를 넘어
쓴다 — 이 저장소에서 가장 나쁜 실패다. §3-E가 그것을 직접 겨눈다: `needed`와 실제 기록 바이트를
**같은 테스트에서** 비교한다. 특히 `i32::MIN`의 부호 처리가 자릿수 계산과 렌더링에서
**서로 다른 코드**가 되지 않게 한다 — 한 함수가 폭을 주고, 같은 함수가 쓴다.

### 5.3 위험: "보호된 DLL 안의 printf 템플릿"

§9가 적어 둔 위험이다. R2·R5처럼 **규칙이 곧 포맷**인 경우, 모듈이 하는 일이 문자열 조립뿐이라면
보호할 알고리즘이 없다(D04). **이 슬라이스는 그것을 막지 않으며, 막을 수도 없다.**
다만 §0.1의 R1·R3·R6은 계산(`qty * price`, 자릿수 채우기, 그룹화)을 포함하므로 그 부류가 아니다.
**대외 문구에서 "포맷 기능"을 보호 이야기와 섞지 않는다.**

### 5.4 갚지 않는 부채

- `&&` 단락 평가 미측정(§5-1)은 그대로다. 연결식은 부작용이 없어 관측 수단이 되지 못한다.
- §4-2(예약어 검사 범위)는 §0.4에서 관측만 하고 **고치지 않는다** — 사용자 결정이 선행한다.
- 문자열 **입력**의 인코딩 미확정(DP-S2)은 그대로다. §2.4가 생성 바이트만 좁힌다.
