# SPEC — 배열 **반환**

- **상태: 초안. 사용자 확인 전이며 코드는 한 줄도 쓰지 않았다.**
- 선행: `SPEC-string-return.md`(Q12 프로토콜의 첫 사용자) · `SPEC-array-input.md`(빌린 포인터 + 길이)
- 관련 결정: **D16**(소유권 3층) · **D17**(i32 status + out-param) · **Q12**(caller-allocates, 2026-08-31 확정)
- 정본 규약: `HOST_ABI.md`의 "가변 길이 데이터"

---

## 0. 이 슬라이스의 근거 — **능력이 아니다. 다시 확인했다**

**2026-09-11에 §7 방법을 돌렸다**(후보 표를 인용하지 않고 업무 규칙을 실제로 써서 빌드하고
**값을 쟀다**). 여섯 개를 썼다: 분할 납부 · 주문 합계 · 급여 · 창고 배분 · 등급 산정 · 누적 할인.

**여섯 개 전부 컴파일되고, 여섯 개 전부 값이 맞았다** — 실제 MSVC C 호스트로 링크해 호출한 결과다.
**강제되는 것은 없다. 여섯 번째다**(§9-1 · §9-9가 다섯 번 같은 결론을 냈다).

> **이 SPEC은 "배열 반환이 있어야 이 규칙을 쓸 수 있다"고 주장하지 않는다.**
> `SPEC-array-input`이 §1에서 같은 정직함을 지켰고, 이 문서도 지킨다.

### 0.1 그런데 수요의 분포가 문서와 달랐다 (E2, 2026-09-11)

| 원한 것 | 6개 중 | 오늘의 우회 |
|---|---|---|
| **배열 반환** | **2** (분할 납부 · 창고 배분) | 인덱스마다 1회 호출 |
| context handle | 1 (누적 할인) | 호스트가 상태를 매번 넘긴다 |
| **고정 레이아웃 struct** | **0** | `out` 파라미터가 전부 덮었다 |

**§9-25는 "다음은 배열 반환이 아니다 … 고정 레이아웃 struct"라고 적었다. 실측은 반대를 가리킨다.**
struct는 §9-1이 이미 "실측 수요 거의 0"으로 적었고, 이번 라운드에서 **정확히 0**이었다.
사용자가 이 실측을 보고 배열 반환을 골랐다(2026-09-11).

### 0.2 우회의 모양이 진짜 논거다 — 결합도

§9-9가 요구한 대로 근거를 **능력이 아니라 결합도**로 쓴다. 두 규칙의 우회를 실제로 써 보니 갈렸다:

- **분할 납부(R1)**: `installment(principal, months, month)` — 호스트가 달마다 부른다.
  값은 맞다. 대가는 호출 n번이고, **그뿐이다.** 이것은 약한 논거다.
- **창고 배분(R4)**: `allocate(stock, want, w)` — 창고 w의 배분량은 **앞 창고들이 얼마를
  가져갔는지에 의존한다.** 그래서 호출마다 **앞 구간을 처음부터 다시 걷는다.**
  값은 맞다(측정: `[10,15,0]`, 합 25). 그러나 **규칙을 n등분해 호스트가 조립하게 만들었고**,
  "w번째 답"이라는 개념은 **원래 규칙에 없던 것**이다 — 우리가 ABI 제약 때문에 발명했다.

**후자가 이 슬라이스의 근거다.** 순차 의존이 있는 규칙은 배열 반환이 없으면
**규칙의 모양 자체가 호스트에 맞춰 바뀐다.**

### 0.3 정직한 반론 (기록)

- 호스트가 n번 부르는 것은 **작동하고 값이 맞다.** 성능은 재지 않았고, 이 SPEC은
  성능을 근거로 삼지 않는다(규칙 7 · E2 없는 제품 속성 주장 금지).
- R4의 재계산은 **n이 작으면 무시할 만하다.** 논거는 비용이 아니라 **규칙의 모양**이다.
- **수요 2/6은 압도적이지 않다.** "아무것도 안 함"이 여전히 방어 가능한 선택이었고,
  §9-25가 그것을 1순위로 적었다. 연 것은 **사용자 결정**이다.

## 1. 목표

`export fn`이 **스칼라 배열을 반환**할 수 있게 한다. 메모리는 **호스트가 준다**(Q12).
모듈은 **할당하지 않는다**(D16).

```
export fn schedule(principal: i32, months: i32) -> [i32]! { … }
```

```c
int32_t mlx_schedule(int32_t principal, int32_t months,
                     int32_t* ml_buf, int32_t ml_cap, int32_t* ml_needed);
```

## 2. 계약 (Contracts)

### 2.1 ABI — **Q12를 물려받는다. 새로 정하지 않는다**

`SPEC-string-return` §2.1의 표가 그대로 적용된다:

| status | 뜻 | `ml_buf` | `*ml_needed` |
|---|---|---|---|
| `0` | 성공 | 채워짐 | 쓴 **원소 개수** |
| **음수** | **용량 부족 = 절단** | **건드리지 않음** | 필요한 **원소 개수** |
| 양수 | 모듈 정의 도메인 에러(D17) | 건드리지 않음 | 건드리지 않음 |

**문자열 반환이 이 프로토콜을 실제로 썼고 결함이 나오지 않았다**(§3a-5). 이 슬라이스는
그것을 물려받으며, **표를 바꾸지 않는다.**

### 2.2 단위 — **원소 개수다. 바이트가 아니다** (DP-R1)

**이 슬라이스에서 가장 틀리기 쉬운 자리다.** 문자열 반환의 `ml_cap`은 **바이트**이고,
배열 입력의 동반 길이는 **원소 개수**다. 둘이 이미 다르다.

**배열 반환은 원소 개수를 쓴다.** 근거:

- **배열 입력과 같은 단위여야 한다.** 같은 프로그램 안에서 `[i32]`가 들어올 때는 원소,
  나갈 때는 바이트라면 **저자가 매번 환산해야 한다.**
- 문자열이 바이트인 것은 **NUL 종료가 바이트 개념**이기 때문이며, 배열에는 종료자가 없다.

> ⚠ **이 절의 첫 판은 근거를 정반대로 적었다(2026-09-11, 착수 검토가 잡았다).**
> *"바이트 단위면 호스트가 `malloc(n)` + `cap = n`으로 8배 넘겨 쓴다"* 고 썼는데 **틀렸다**:
> `cap`이 바이트면 모듈은 `needed(8n 바이트) > cap(n 바이트)`를 보고 **절단으로 실패한다.**
> 바이트 단위는 이 실수에 대해 **안전한 쪽**이다.
>
> **진짜 위험은 원소 단위를 고른 이 결정이 만든다.** 호스트가 문자열 반환의 probe 관용구를
> 그대로 베끼면 — `malloc(*needed)` 하고 `cap = *needed` — **`[f64]`에서 8n 바이트가
> 필요한데 n 바이트만 잡고 "n개 원소 들어갈 자리가 있다"고 약속한다.** 모듈은 그 말을
> 믿고 쓰고, **8배 넘겨 쓴다.** 크래시 없이 조용할 수도 있다.
>
> 그래도 원소 단위를 고르는 이유는 **배열 입력과의 일관성**이고, **대가를 숨기지 않고
> 여기 적는다.** 그래서 수용 기준 G가 주석에 요구하는 것이 두 가지로 늘어난다:
> 단위가 원소라는 것, 그리고 **`malloc(n * sizeof(T))`** 라는 것. 생성 헤더의 사용법
> 주석과 두 예제 호스트가 **그 곱셈을 실제로 보여 준다** — 문서가 아니라 코드가 습관을
> 보여 준다(`SPEC-string-return` §2.8과 같은 태도).

### 2.3 표면 문법 — **`-> [T]!` 만** (DP-R2)

- 반환 타입은 `[i32]` · `[f64]` · `[bool]`, **반드시 `!`** 를 단다.
  절단이 모든 호출에서 가능하므로 언제나 status를 반환하고, `-> string!`과 **같은 규칙**이다
  (`!` ⟺ C에서 `int32_t` 반환).
- 맨 `-> [T]`는 **거부**하되 메시지가 `-> [T]!`를 가리킨다.
- **`export fn` 전용.** 내부 `fn`은 거부한다(DP-O5 · DP-T1과 같은 이유).
- 선언된 스칼라 `out`과 공존하며 **DP-O1이 그대로 산다**: 선언된 out이 먼저, **반환 삼총사가 마지막.**

### 2.4 본문이 원소를 만드는 방법 — **`result` 문** (DP-R3, **이 슬라이스의 핵심**)

**문제부터 적는다.** Q12는 *"절단이면 한 바이트도 쓰지 않는다"* 를 요구한다. 문자열 반환은
**2패스**(세고 → 쓰기)로 그것을 지켰다 — 소스 바이트를 두 번 훑을 수 있었기 때문이다.
**배열 원소는 계산해야 나오므로 두 번 훑을 수 없다.** 쓰면서 길이를 알게 되면 절단 시
이미 쓴 것이 남고, **프로토콜이 깨진다.**

**해법: 길이를 먼저 선언하게 한다.**

```
export fn schedule(principal: i32, months: i32) -> [i32]! {
    result months               // ① 길이 선언. 여기서 cap 검사가 일어난다
    let mut i = 0
    while i < months {
        result[i] = principal / months
        i = i + 1
    }
}
```

- **`result <expr>`** — 결과의 길이를 선언하는 **문장**이다. 컴파일러가 이 자리에서
  `*ml_needed = n`을 쓰고 **`n > ml_cap`이면 즉시 음수 status로 반환**한다.
  **그 시점까지 버퍼에는 아무것도 쓰이지 않았다** — Q12가 그대로 지켜진다.
- **`result[i] = e`** — 원소 대입. `0 <= i < n`으로 **경계 검사**되며, 벗어나면
  `ML_ST_INDEX_OUT_OF_RANGE = -2`다(배열 입력과 **같은 상수**).
- 본문에 `result` 문이 **정확히 하나** 있어야 하고, **모든 `result[i] = …`를 지배(dominate)**
  해야 한다 — 즉 **함수의 최상위 블록에만** 놓을 수 있고 `if`·`while` 안에는 놓을 수 없다.

  > ⚠ **첫 판은 "먼저 와야 한다"고만 적었고, 그것으로는 부족하다(착수 검토가 잡았다).**
  > `if b { result n }  result[0] = 1` 은 *"정확히 하나 + 소스 순서상 먼저"* 를 만족하지만
  > **`b`가 거짓이면 cap 검사가 아예 돌지 않는다** — 그러면 모듈이 호스트 버퍼에
  > 용량 확인 없이 쓴다. 소스 순서가 아니라 **지배 관계**여야 하고, 최상위 블록 제한이
  > 그것을 간단하게 만든다(데이터 흐름 분석 없이 파서·typeck에서 판정된다).
- `result`는 **키워드가 아니라 이 반환 타입에서만 보이는 이름**이다 — `len`이 내장 시그니처인
  것과 같은 방식이라 `let result = 0`은 계속 합법이다(DP-R7에서 다시 다룬다).

**왜 이 모양인가 (기각한 대안):**

| 대안 | 왜 기각했나 |
|---|---|
| 쓰면서 넘치면 실패 | **Q12 표를 바꾼다.** 절단 시 버퍼가 부분적으로 더럽혀진다. `SPEC-string-return` §2.1이 그 표를 바꾸지 않는다고 못박았고, DP-T2가 같은 이유로 기각됐다 |
| 람다/클로저(`fill n with i -> e`) | 언어에 함수 값이 없다. 슬라이스 하나가 **프로토콜과 새 값 종류**를 겹치게 된다 |
| `out xs: [i32]` (쓰기 가능 out 배열) | 길이를 선언할 자리가 없어 같은 부분 쓰기 문제로 돌아온다. 게다가 **`out`의 "쓰기 전용" 의미와 배열의 인덱스 읽기가 충돌**한다 |
| `for` 도입 후 진행 | `for`는 별개 슬라이스다(§5.3). `while`+`let mut`로 충분함이 실측됐다(§3a-2) |

### 2.4b `result` **이후의 실패** — 이 설계가 Q12에서 갈리는 유일한 자리 (DP-R9, **결정 필요**)

**착수 검토가 찾은 구멍이고, 이 SPEC에서 가장 중요한 미결이다.**

`result n`이 성공하는 순간 **되돌릴 수 없는 것 둘**이 일어난다: `*ml_needed = n`이 쓰이고,
버퍼가 0으로 채워진다(§2.5). 그 **뒤에** 실패하면 — `result[5] = v`가 범위를 벗어나거나
저자가 `fail E_X`를 부르면 — **버퍼는 이미 더럽혀져 있다.**

그런데 Q12 표는 음수·양수 status **양쪽에서 "건드리지 않음"** 이라고 적는다.
**즉 이 설계는 "절단(음수)"은 완벽히 지키지만, "성공을 시작한 뒤의 실패"라는 새 경우를 만든다.**

> **이 SPEC의 첫 판은 그 사실을 모른 채 수용 기준 B6·B7에 "버퍼 무기록"을 적었다.**
> **제 설계로는 불가능한 것을 제 수용 기준이 요구하고 있었다.** 구현에 들어갔다면 B6·B7이
> 빨간 채로 남고, 가장 나쁜 경우 **테스트를 약하게 고쳐서** 통과시켰을 것이다.

**선택지 (사용자 결정):**

| 안 | 내용 | 대가 |
|---|---|---|
| **(a)** | 범위를 벗어난 `result[i] = e`를 **조용히 무시**(no-op)해 실패 자체를 없앤다 | **기각.** 이 저장소가 네 번 데인 바로 그 모양이다 — 컴파일되고, 그럴듯하고, 틀린다 |
| **(a′) — 권고** | `result` 이후 **`fail`·`try`를 정적으로 거부**한다. 남는 유일한 런타임 실패는 `result[i]` 범위 이탈이고, 그때는 **`-2`를 반환하되 "버퍼는 정의되지 않는다"** 를 계약으로 적는다. Q12 표의 음수 행에 **배열 전용 각주**를 단다 | Q12 표에 **각주가 하나 붙는다**. `SPEC-string-return` §2.1이 "표를 바꾸지 않는다"고 했으므로, 이것은 **확장이지 위반이 아님을 사용자가 확인해야 한다** |
| **(b)** | 0 채우기를 **마지막으로 미룬다**: 원소를 임시로 모았다가 끝에 한 번에 쓴다 | **모듈에 할당자가 없다.** 임시 공간이 없다. **불가능** |
| **(c)** | `result[i]` 범위 이탈을 **컴파일 에러로만** 만든다(인덱스가 정적으로 증명 가능할 때만 허용) | 오늘의 언어로는 `while i < n`의 `i`를 증명할 수 없다. **사실상 배열 반환을 못 쓰게 한다** |

**권고는 (a′)다.** 근거: 절단(Q12가 실제로 겨냥하는 실패)은 **완벽히 지켜지고**, 남는 경우는
**저자의 버그**(자기가 선언한 길이 밖에 쓰는 것)이며, 그것을 조용히 넘기지 않고 `-2`로 시끄럽게
만든다. **대신 그 대가를 표에 각주로 적고 호스트 계약(`status != 0`이면 읽지 마라)에 기댄다** —
`SPEC-string-return` §2.8이 이미 같은 자리에서 같은 선택을 했다.

### 2.5 쓰이지 않은 원소 — **0으로 채운다** (DP-R4)

`result n` 뒤 **모든 인덱스가 대입되는지는 정적으로 알 수 없다**(루프 조건이 임의다).
따라서 컴파일러는 **cap 검사를 통과한 직후 `ml_buf[0..n]`을 0으로 채운다.**

- `f64` → `0.0`, `bool` → `false`, `i32` → `0`.
- 대가: 성공 경로에 한 번의 채우기. **이 비용은 재지 않았고, 근거로 삼지도 않는다.**
- 얻는 것: **반환 계약이 전역(total)이다.** 호스트는 status `0`이면 `n`개 원소가 전부
  정의된 값임을 안다. 이 저장소가 **"컴파일되고, 그럴듯하고, 틀린"** 결함을 네 번 겪은 자리가
  정확히 이런 미정의 구멍이다.
- **실패 경로에서는 채우지 않는다.** 절단이면 버퍼는 호스트의 것 그대로다(§2.7).

### 2.6 원소 타입 — `i32` · `f64` · `bool` (DP-R5)

배열 입력(DP-A5)과 **같은 집합**이다. 갈라지면 저자가 두 표를 외워야 한다.

> ⚠ **`[bool]`의 폭이 §9-25가 예고한 문제다.** 배열 입력에서 Pascal `PBoolean`은
> **1바이트 `Boolean`**을 가리킨다(실측·고정됨). 반환에서는 **모듈이 쓰는 쪽**이므로 같은 폭을
> 반대 방향으로 지켜야 한다 — 모듈이 1바이트를 쓰고 호스트가 4바이트 `LongBool`로 읽으면
> **조용한 오답**이다. 수용 기준 E가 Delphi 호스트에서 이것을 **일부러 밟아 측정**한다.

### 2.7 NULL · 음수 `cap` — **문자열 반환 그대로** (DP-R6)

- `ml_buf`는 **`ml_cap == 0`일 때에 한해 NULL일 수 있다**(probe 관용구). 그 밖의 NULL은
  정의되지 않은 동작이다. `ml_needed`는 **절대 NULL일 수 없다.**
- `ml_cap`이 음수면 **`0`으로 본다.** 부호 없는 거대한 값으로 해석하지 않는다.
- **probe는 항상 2회에 수렴한다**: `ml_cap = 0`으로 한 번 불러 `*ml_needed`를 받고,
  그만큼 할당해 다시 부른다. 단위가 원소이므로 `malloc(n * sizeof(T))` + `cap = n`이다.
- 실패 시 버퍼 무기록의 대가는 `SPEC-string-return` §2.8과 **같은 문장**이다:
  **`status != 0`이면 읽지 마라.**

### 2.8 지문 (`ml_iface_hash`)

반환 타입이 매니페스트에 표면 철자 `[i32]`로 들어간다 — 배열 입력(§2.7)과 같은 기존 동작이다.
**동반 삼총사(`ml_buf`·`ml_cap`·`ml_needed`)는 매니페스트에 나타나지 않는다**: 표면에 없고,
붙이는 규칙을 컴파일러가 고정하므로 지문이 따로 지킬 것이 없다. 문자열 반환과 같은 취급이다.

## 3. 수용 기준 (측정 가능)

- **A. 컴파일.** `examples/schedule.mls`(분할 납부)와 `examples/allocate.mls`(창고 배분) —
  §0에서 실제로 막혔던 **바로 그 두 규칙**을 예제로 넣는다.
- **B. 값.** Rust 오라클이 산출 `.dll`을 로드해 확인한다:
  - **B1** 성공: `schedule(100000, 7)` → 7개 원소, **합이 정확히 `100000`**, `*needed == 7`.
  - **B2** **절단**: `cap = 3`으로 부르면 **음수 status**, `*needed == 7`,
    **버퍼는 canary 그대로**(0xAA로 채워 바이트 비교 — 문자열 반환이 만든 도구를 재사용한다).
  - **B3** **probe**: `cap = 0`, `buf = NULL` → 음수 status, `*needed == 7`. **2회에 수렴**.
  - **B4** **딱 맞음**: `cap == *needed`는 **성공**이다.
  - **B5** **0으로 채움**(§2.5): 일부 인덱스만 대입하는 모듈이 나머지를 **0**으로 준다.
  - **B6** **도메인 에러**(양수 status)에서 버퍼·`*needed` **둘 다 무기록** — `fail`이
    `result` **앞**에 있는 함수로 잰다. `result` 뒤의 `fail`은 §2.4b(a′)가 **컴파일 에러**로
    막으므로, 그 거부도 함께 고정한다.
  - **B7** `result[i]`의 범위 이탈 → **`-2`**. **버퍼 무기록을 요구하지 않는다**(§2.4b):
    이미 0으로 채워졌기 때문이다. 대신 **`*needed`가 선언된 `n` 그대로**임과, 호스트가
    status를 보고 읽지 않는 계약을 고정한다. **이 케이스가 §2.4b의 대가를 측정으로 만든다.**
  - **B8** `cap`이 **음수**면 `0`과 같게 동작한다.
- **C. 순차 의존 규칙이 한 번에 답한다.** `allocate(stock=[10,20,5], want=25)` → `[10,15,0]`,
  **한 번의 호출로**. §0.2가 적은 우회(창고마다 호출 + 앞 구간 재계산)가 사라졌음을 보인다.
- **D. 실제 C 호스트**(MSVC)가 생성 `.h`를 컴파일하고 두 예제를 호출한다.
  **동반 삼총사를 빼면 인자가 밀리는 게 아니라 컴파일이 안 된다** — 배열 입력에서 확인된 성질이다.
- **E. Delphi 호스트**(`MATHLESS_GATE_DELPHI`)가 같은 것을 호출하고, **`[bool]` 반환에서
  1바이트 폭을 일부러 밟아 잰다**(§2.6). `LongBool`로 선언하면 어떤 값이 나오는지 기록한다.
- **F. 지문.** 반환 원소 타입을 `[i32]` → `[f64]`로 바꾸면 `ml_iface_hash`가 **바뀐다**.
- **G. 단위 주석.** 생성 `.h`·`.pas`가 **`ml_cap`이 원소 개수임**을 적고,
  **문자열의 바이트 단위와 다르다는 것**을 함께 적는다(§2.2).
- **H. C ABI 무변경 증명.** 기존 예제들의 생성 선언이 **한 글자도 바뀌지 않는다**(골든).

### 3.1 반드시 **거부**되는 것 — 전부 이유를 이름으로 말한다

| 거부 | 메시지가 말해야 하는 것 |
|---|---|
| `-> [i32]` (`!` 없음) | `-> [i32]!`를 쓰라 — 절단이 언제나 가능하다 |
| 내부 `fn`의 `-> [T]!` | `export fn` 전용 |
| `result` 문이 **없음** | 길이를 선언해야 한다 |
| `result` 문이 **둘 이상** | 정확히 하나 |
| `result[i] = …`가 `result` 문보다 **먼저** | 순서 |
| 배열 아닌 반환에서 `result` 사용 | `-> [T]!`에서만 보인다 |
| `result` 자체를 **읽기**(`let a = result`) | 쓰기 전용 — 호스트 버퍼다 |
| `[string]` · `[[T]]` 반환 | 배열 입력과 **같은 메시지** |
| `out xs: [T]` | 여전히 거부(§2.4 표) |
| `result`가 `if`/`while` **안에** 있음 | 최상위 블록에만 — 조건부면 cap 검사를 건너뛴다(§2.4) |
| `result` **뒤**의 `fail` 또는 `try` | §2.4b(a′) — 길이를 선언한 뒤에는 실패할 수 없다 |

## 4. 설계 제안 (DP — **미확정, 사용자 확인 필요**)

| ID | 질문 | 권고 | 근거 |
|---|---|---|---|
| **DP-R1** | `ml_cap`·`*ml_needed` 단위 = 원소 / 바이트 | **원소** | 배열 입력과 같은 단위. 바이트면 `[f64]`에서 **8배 오버런**을 조용히 만든다(§2.2) |
| **DP-R2** | `-> [T]!`에서 `!` 필수 / 선택 | **필수** | `!` ⟺ `int32_t` 반환 규칙이 갈라지지 않는다. `-> string!`과 같다 |
| **DP-R3** | 본문이 원소를 만드는 방법 | **`result n` 문 + `result[i] = e`** | Q12의 "절단이면 무기록"을 **깨지 않고** 지킬 수 있는 유일한 모양(§2.4의 기각 표) |
| **DP-R4** | 쓰이지 않은 원소 = 0으로 채움 / 미정의 | **0으로 채움** | 반환 계약이 전역이 된다. 미정의 구멍은 이 저장소가 네 번 데인 모양이다(§2.5) |
| **DP-R5** | 원소 타입 = `i32`·`f64`·`bool` / 일부 | **셋 다** | 배열 입력(DP-A5)과 갈라지지 않는다. 대가는 `[bool]` 1바이트 폭(§2.6) |
| **DP-R6** | NULL·음수 `cap` 규칙 | **문자열 반환 그대로** | 이미 실측된 규칙을 복제하지 않고 물려받는다 |
| **DP-R7** | `result`가 키워드인가 | **아니다 — 반환 타입에서만 보이는 이름** | `len`·`floor`와 같은 방식. `let result = 0`이 계속 합법이다. **대가: 같은 이름의 지역 변수가 있으면 가린다** — 그때는 거부하고 이름을 바꾸라고 말한다 |
| **DP-R8** | 범위 이탈 status | **`ML_ST_INDEX_OUT_OF_RANGE = -2`** | 배열 입력과 **같은 상수**. 새 음수를 만들지 않는다 |
| **DP-R9** | `result` 이후의 실패에서 버퍼 상태 (**§2.4b**) | **(a′)** — `result` 뒤 `fail`·`try`는 **컴파일 에러**, 범위 이탈은 `-2`이고 **버퍼는 정의되지 않음**(Q12 표에 배열 전용 각주) | 절단은 완벽히 지켜진다. 남는 것은 저자의 버그이고, 조용히 넘기지 않고 시끄럽게 만든다. **Q12 표에 각주를 다는 일이므로 사용자 확인이 필요하다** |

## 5. 범위 밖 / 위험

### 5.1 이 슬라이스가 하지 않는 것

- **배열 입력과 반환의 조합을 넘어서는 것**: 지역 배열 변수 · 배열 리터럴 · 중첩 배열 ·
  배열을 품은 struct. 전부 그대로 거부된다.
- **`for`·`break`·`continue`**: `while`+`let mut`로 충분함이 §3a-2에서 실측됐다.
- **문자열 배열**(`[string]`): 가변 길이의 가변 길이다. 별도 슬라이스이고, 오늘 거부 메시지가 있다.
- **성능 주장**: §0.3대로 재지 않았고 근거로 쓰지 않는다.

### 5.2 이 슬라이스가 만드는 새 위험

1. **한 헤더에 두 단위가 공존한다**(문자열=바이트, 배열=원소). §2.2가 고른 결과이고
   수용 기준 G가 주석으로 고정하지만, **주석은 컴파일러가 강제하지 않는다.**
2. **`[bool]` 반환의 폭**(§2.6). 호스트가 `LongBool` 배열로 받으면 조용한 오답이다.
   모듈은 막을 수 없다 — 바이트만 보인다. **수용 기준 E가 측정으로 바꾼다.**
3. **`result n`의 `n`이 음수면?** `cap` 규칙과 같게 **`0`으로 본다**(빈 결과, 성공).
   이것을 §3-B에 케이스로 넣는다 — 적고 지나가지 않는다.

### 5.3 갚지 않는 부채

- §5-1(단락 평가 미측정)은 이 슬라이스가 갚지 못한다. 관측 수단이 생기지 않는다.
- `f64 as string` · 문자열 길이 — 무관하다.
