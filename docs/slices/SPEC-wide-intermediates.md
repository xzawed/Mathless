## 0. 왜 — 측정부터

### 0.1 참값이 드는데 `-3` (E2)

체크드 산술은 **연산자마다** 검사한다. 그래서 `qty * price / 100`처럼 중간곱만 넘치고 답은 i32에 드는 식이 `-3`이 된다 —
업무 규칙 표본에서 헬퍼 체크 전파 뒤로 **59행**(§9-72.3). 틀린 답은 아니지만, 맞는 답을 줄 수 있는 입력을 거절한다.

### 0.2 네 변형을 시험 구현해 쟀다 (E2, 로컬 브랜치 `exp/wide2-local`, 머지 안 함)

현재 `main`(헬퍼 체크 전파 포함) 위에 스위치로 넷을 구현했다:

- **FULL** — `!` 본문(과 검사된 사본)의 모든 i32 산술 트리를 i64로 재고, 값이 i32로 가야 하는 자리에서만 검사한다.
- **PURE** — 잎이 **실패하지도 코드를 실행하지도 않는** 트리만: 변수 · i32 상수 · `len(xs)`(측정 때는 변수의 `byte_len`도 — 아래).
  호출과 배열 읽기가 들어간 트리는 오늘처럼 연산자마다 검사한다.
- **PURE+CALL** — PURE에 **`while`이 없는 무한 함수의 호출**을 잎으로 더한 것(그 함수가 부르는 함수들에도 `while`이 없고,
  인자도 허용되는 잎). 그런 호출은 반드시 끝나고, 헬퍼 체크 전파 아래에서 낼 수 있는 실패는 `-3`뿐이다(§0.3).
- **PURE+INDEX** — PURE에 배열 읽기 잎을 더한 것.

| 625행(메모 1 제외) | 맞음 | 조용한 오답 | 참값이 드는데 `-3` | 기타 |
|---|---|---|---|---|
| 오늘 | 505 | 44 | 59 | 17 |
| FULL | 546 | 44 | **17** | 18 |
| PURE | 540 | 44 | 23 | 18 |
| **PURE+CALL** | 543 | 44 | **20** | 18 |
| PURE+INDEX | 543 | 44 | 20 | 18 |

기타의 +1은 규칙 불변식 밖 입력의 거절이 `-3`에서 도메인 에러 `3`으로 바뀐 한 행이다(stateful R1-oob, §9-71.3).

- **어느 변형도 맞던 status 0 답을 바꾸지 않았다.** 바뀐 행은 전부 §9-71에서 한 줄씩 판정한 답과 같다(모르는 행 0).
- PURE+CALL과 PURE+INDEX는 3행씩 더 얻지만 **다른 행**이다: 호출 잎이 든 식(`gross * grade_rate(grade) / 100`, records R1)과
  배열 읽기 잎이 든 식(stateful R4).
- 위 변형들은 변수의 `byte_len`과 문자열 인자를 받는 호출도 잎으로 받았다. 둘을 뺀 PURE+CALL(§2.1이 권고하는 잎)도 626행
  **전부 같은 답**이다(측정).
- **무작위 48,000 호출**(함수 200 × 입력 80 × 시드 3, 정확한 정수 모델과 대조): 네 변형 모두 오늘 `-3`이 아니던 26,476 호출에서
  차이 0. **넷 다 `-3`이 아닌 답은 전부 정확한 모델과 같다** — 새 오답을 만들지 않고, 모델보다 `-3`을 더 자주 낼 뿐이다
  (FULL 1,687 · PURE 7,814). 이 생성기에는 호출 잎이 없어 PURE+CALL은 PURE와, PURE+INDEX는 FULL과 같은 수를 낸다.

### 0.3 FULL의 위험을 PURE(+CALL)는 구조로 피한다 (E2)

§9-71.4가 FULL에서 잰 위험과, 같은 입력에서 PURE·PURE+CALL이 내는 답:

| 위험 | FULL | PURE · PURE+CALL |
|---|---|---|
| 빨리 실패하던 입력이 **멈춘다** — `a*b + spin(n)`(`spin`은 끝나지 않는 `while`) | 20초 타임아웃에 죽였다 | 즉시 `-3`(오늘과 같다) — `spin`에는 `while`이 있어 잎이 아니다 |
| 뒤 피연산자의 실패가 앞의 진짜 오버플로를 **앞지른다** — `a*b + xs[5]` | `-2` | `-3`(오늘과 같다) |
| i64도 넘친다 — `a*b*c/(b*c)`, `b = c = i32::MAX` | `-3` | `-3` |
| `let` 추출이 답을 바꾼다 — `return a*b/b` 대 `let t = a*b  return t/b` | 값 대 `-3` | 값 대 `-3` |

**왜 구조로 피하는가.** PURE 트리의 잎은 실패하지도 코드를 실행하지도 않고, PURE+CALL이 더하는 호출 잎은 반드시 끝나며
`-3`으로만 실패한다. 그래서 트리 안에서 검사를 미뤄도 **관측되는 차이가 없다**: 트리의 정확한 값이 i32에 들지 않는 진짜
오버플로는 트리의 뿌리에서, **트리보다 뒤에 평가되는** 어떤 것보다 먼저 `-3`이다(잎의 실패가 먼저 와도 같은 `-3`이다).
트리보다 앞에서 평가되는 것은 오늘도 먼저 돈다 — `xs[5] + a*b`는 오늘도 PURE+CALL에서도 `-2`다(왼쪽부터). Grok plan도 PURE에
대해 같은 판정이다(Q2 NO).

**`-3`이 다른 답으로 바뀌는 것은 정확한 값이 존재할 때뿐이다.** 트리가 더는 실패하지 않으므로 그다음에 실제로 실패하는 연산이
답이 된다 — `xs[a*b/b]`의 범위 밖 인덱스나 `a*b/b + xs[5]`의 `xs[5]`(`-2`), `if a*b/b > K { fail E }`의 도메인 에러.
무작위 호출에서 그런 `-2`·도메인 답은 전부 정확한 모델과 같았다. 제수가 런타임에 0인 `a*b/d`도 이 부류다 — 정확한
`a*b`가 있으므로 DP-N4대로 `0`이다(측정: 오늘 `-3`, PURE+CALL `0`).

### 0.4 크기 (E2)

PURE로 잰 값: 예제 26개 `.text` 합 95,334 → 95,472바이트(+138), 모듈별 −123~+192, 6개 모듈만 바뀐다. PURE+CALL은 잎만
늘어나므로 같은 방식으로 다시 잰다(§6 작업 1).

## 1. 범위

**포함** — fallible 문맥(`!` 본문과 검사된 사본)에서:

1. **순수 산술 트리**(§2.1)를 정확히(i64) 계산하고, 그 뿌리에서 한 번 i32로 좁힌다 — 들지 않으면 `-3`.
2. 두 쪽이 순수 트리인 i32 **비교**는 정확한 값끼리 비교한다.
3. `LANGUAGE.md`(평가 규칙 · DP-O9 · 중간값의 대가) · `HOST_ABI.md` · 테스트 · 실제 C 호스트.
4. §0.2의 626행을 구현본으로 다시 재어 시험 구현과 대조한다(기록이지 가드가 아니다).

**미포함 (명시)**

- 무한 본문 — 오늘처럼 연산자마다 wrap(§9-71: 넓히면 status 0 값이 바뀐다 — `(2147483647 + 1) / 2`).
- §2.1의 잎이 아닌 것(배열 읽기 · `while`이 있는 함수의 호출 등)을 넘어 넓히는 것 — 그런 것이 든 식에서도 그 안의 순수한
  부분 트리는 넓힌다(DP-W2) · 지역 변수의 폭(`let`은 i32로 좁힌다) · i64 타입 · C 백엔드 구현.
- `DECISIONS.md` — 바뀌는 것은 슬라이스 결정(체크드 산술 §2.1의 검사 자리, DP-O9의 서술)뿐이다.

## 2. 계약

### 2.1 순수 산술 트리 (DP-W1, DP-W2)

i32 `+ - * / %`와 단항 `-`로만 이어진 식 중, **잎이 모두 아래인 것**:

- 변수(파라미터 · 지역) · i32 상수(리터럴과 `const`) · `len(xs)`
- **`while`이 없는 무한 함수의 호출** — 그 함수가 (직접이든 여러 단계로든) 부르는 함수에도 `while`이 없고, 인자가 모두
  이 목록의 잎이거나 순수 트리이거나 `bool`·`f64` 변수·상수이며 **문자열 인자가 없을 때**(DP-W2). 문자열을 받는 함수의
  `==`·`byte_len`은 NUL까지 돌아 호스트의 NUL 계약에 기대기 때문이다(아래 `byte_len`과 같은 이유). 배열 인자는 된다 —
  무한 본문은 원소를 읽을 수 없고 `len`은 길이를 읽을 뿐이다. 재귀는 금지이므로 그런 호출은 끝난다. 헬퍼 체크
  전파 아래에서 그 호출이 낼 수 있는 실패는 `-3`뿐이다 — 무한 본문은 `fail`·`try`·인덱스·스팬 비교를 쓸 수 없다.

`while`이 있는 함수의 호출 · `byte_len`을 포함한 내장 함수 호출 · 배열 읽기 · `f64 as i32` · 스팬은 잎이 될 수 없다 — 그런 것이 섞인 트리는 오늘처럼
연산자마다 검사하고, 그 안의 **순수한 부분 트리**가 각자 넓게 계산된다. `byte_len`은 NUL까지 도는 반복이라 끝나는 것이
호스트의 NUL 계약에만 기댄다 — 검사를 미루면 오늘은 돌지 않던 입력에서 돌게 되므로 뺀다(빼도 표본의 답은 같다, §0.2).

### 2.2 계산과 좁힘 (DP-W3, DP-W5)

- 트리는 i64로, 왼쪽부터 계산한다. `/`·`%`의 0 제수는 `0`(DP-N4), `%`는 참 나머지(DP-O5).
- **i64 자체가 넘치면 `-3`** — "정확한 값"의 한계는 i64다(DP-W5). 코퍼스의 산술 뿌리 588개 중 정적 한계가 63비트를 넘는 것은 4개다
  (§9-71.4의 위험 검토가 컴파일러 IR로 센 값).
- 트리의 **뿌리**에서, 값을 받는 자리가 무엇이든(`let`·대입·`return`·인자·인덱스·`result`·`as string`·순수하지 않은 부모
  연산) 한 번 i32로 좁힌다. 들지 않으면 `-3`.

### 2.3 비교 (DP-W4)

두 피연산자가 모두 순수 트리(적어도 한쪽은 산술)인 `< > <= >= == !=`는 정확한 값끼리 비교하고 좁히지 않는다 —
`a + b > 0`이 `a = i32::MAX, b = 1`에서 `true`(측정). 한쪽이 순수하지 않으면 오늘처럼.

### 2.4 `as f64` — 먼저 좁힌다 (DP-W6)

`(tree) as f64`는 트리를 **i32로 좁힌 뒤** 변환한다 — 들지 않으면 `-3`. 넓은 값을 그대로 f64로 바꾸면 2^53 위에서 반올림돼
**새 조용한 오답**이 된다(Grok plan Q3). `(a*b/b) as f64`는 값, `(a*b) as f64`는 `-3`(측정).

### 2.5 리터럴과 상수 — DP-O9를 다시 쓴다 (DP-W7)

리터럴·상수만의 트리도 순수 트리다: `2147483647 + 1 - 1`은 `2147483647`, `2147483647 + 1`은 `-3`(측정). 체크드 산술의
DP-O9(*"리터럴만의 오버플로는 실행 시 `-3`"*)는 *"정확한 값이 i32에 들지 않는 리터럴 식은 실행 시 `-3`"* 이 된다.
그 슬라이스 §5가 후보로 둔 **상수식 오버플로 진단**도 같은 의미를 따라야 한다.

### 2.6 알려진 대가 (기록)

- **`let` 추출이 답을 바꾼다** — `let`은 좁히는 자리다. `return a*b/b`는 값, `let t = a*b  return t/b`는 `-3`. 지역 변수의
  폭은 i32로 둔다(넓히면 언어 모델이 바뀐다).
- **헬퍼로 빼도 답이 바뀐다** — 헬퍼의 `return`도 좁히는 자리다. `x*x/x`는 `46341`에서 `46341`, `sq(x)/x`는 `-3`
  (구현 중 측정, `wide_intermediates.rs`). 호출 잎은 헬퍼가 **돌려준 i32**를 잎으로 받을 뿐 그 안의 식을 넓히지 않는다.
- **같은 식이 문맥에 따라 다르다** — 무한 본문에서는 연산자마다 wrap한다. 체크드 산술이 이미 만든 차이가 넓어진다.
- **배열 읽기가 든 식은 좋아지지 않는다** — 표본에서 3행(PURE+CALL과 FULL의 차이, stateful R4). 배열 읽기를 잎으로 받으면
  (PURE+INDEX) 되찾지만 §0.3의 두 번째 위험 — 뒤의 `-2`가 진짜 오버플로를 앞지르는 것 — 을 다시 연다.
- **`while`이 있는 헬퍼를 부르는 식도 그대로다** — 멈춤 위험을 여는 유일한 잎이기 때문이다.

### 2.7 바인딩 · 지문 · ABI (DP-W8)

- `ML_ST_OVERFLOW` 선언 술어는 그대로다 — 순수 트리도 `-3`에 닿을 수 있다(과다 선언은 있어도 누락은 없다).
- 지문과 `ML_MODULE_ABI_VERSION`은 바뀌지 않는다(DP-O4와 같은 근거). 같은 소스를 다시 컴파일하면 `-3`이던 입력이 값이
  될 수 있다 — 표시 없이, 문서에 적는다(DP-O8처럼).

### 2.8 C 백엔드 (D19) — 요구만 적는다 (DP-W9)

C로 내릴 때 순수 트리는 부호 있는 int64를 **넘침 검사와 함께** 계산해야 한다. C의 부호 있는 넘침은 미정의 동작이고,
MSVC 19.44는 `<stdckdint.h>`·`__builtin_mul_overflow`를 받지 않는다(§9-71.4). 두 i32의 곱은 int64를 넘지 않으므로 대부분의
트리는 정적 한계로 검사를 없앨 수 있다. C 백엔드는 없으므로 이 슬라이스는 요구만 `LANGUAGE.md`에 적는다.
