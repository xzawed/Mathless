# SPEC — 모듈 이름 길이 계약

- **상태: 초안. 사용자 확인 전이며 제품 코드는 한 줄도 쓰지 않았다.**
- 선행: **`SPEC-qualified-iface-hash.md`(#215)** — 이 결함을 만든 슬라이스다
- 관련 결정: **D18**(예약 export 이름) · #42(모듈 이름 검증)
- 발단: **2026-09-12 감사**(`STATUS.md` §9-33)

---

## 0. 왜 — 측정부터

### 0.1 실측 (2026-09-12, E2)

| 무엇 | 실측 |
|---|---|
| 참조 **동적** C 호스트가 게이트할 수 있는 가장 긴 모듈 이름 | **65자** |
| 거부하기 시작하는 길이 | **66자** |
| `mlc build`가 70자 이름을 받는가 | **받는다. exit 0, 산출물 4종 전부 생성** |

즉 **컴파일러가 참조 호스트가 소비할 수 없는 모듈을 만든다.**

`hosts/c-host/host.c`의 `gate()`가 지문 심볼을 `char symbol[80]`에 만든다. 접두어 `ml_iface_hash_`가
14자이므로 남는 것은 `80 - 14 - 1 = 65`자다. 넘으면 `snprintf`의 반환값으로 **거부**한다:

```
refuse <name>: module name too long to form its fingerprint symbol
```

`compiler/src/emit.rs`의 `check_module_name`은 **길이 상한이 없다**(식별자 모양·예약어·Windows 장치명만 본다).

### 0.2 이 결함은 **#215가 만들었다**

지문 심볼에 모듈 이름을 붙이기 전에는 `gate()`가 `"ml_iface_hash"` 문자열 리터럴을 조회했고 길이 문제가
없었다. 한정한 뒤 호스트가 이름을 **만들어야** 했고, 거기서 버퍼가 생겼다. **내가 넣은 한계다.**

### 0.3 실패는 조용하지 않다 — 그런데 그것이 변명이 되지 않는다

호스트는 **거부한다**. 조용한 오답이 아니다. 그런데 셋이 나쁘다:

1. **원인에서 멀다.** 컴파일러는 exit 0으로 만족스럽게 끝났고, 실패는 호스트 실행 시점에 나타난다.
2. **호스트마다 다르다.** **링크** C 호스트는 버퍼가 없어 그냥 링크되고, **Delphi** 호스트도 유닛이
   식별자를 선언할 뿐이라 한계가 없다. 같은 모듈이 **호스트에 따라 되기도 하고 안 되기도 한다.**
3. **어디에도 적혀 있지 않다.** 컴파일러·문서·생성 헤더 중 65라는 수를 말하는 곳이 없다.

## 1. 목표

**컴파일러가 받는 이름과 참조 호스트가 게이트할 수 있는 이름을 하나의 계약으로 묶는다.**

---

## 2. 선택지 (DP-N1)

| 안 | 내용 | 대가 |
|---|---|---|
| **A** | **컴파일러가 먼저 거부한다** — `check_module_name`에 상한을 두고, 호스트 버퍼를 그 상한에서 **유도**한다 | 컴파일러가 예전에 받던 이름을 거부한다(플래그 데이, 아래) |
| **B** | 호스트 버퍼만 키운다 | 고정 크기는 언제나 경계가 있다. 다음 경계에서 같은 일이 반복된다 |
| **C** | 적기만 한다 | 호스트마다 다른 동작이 그대로 남는다 |

### 2.1 권고 — **A**

**진단이 좋은 곳에서 실패하게 한다.** `check_module_name`은 이미 *"`if`는 크레이트 이름이 될 수 없다"*,
*"`nul`은 Windows 장치명이다"* 를 **이유까지 말하며** 거부한다(#42). 길이도 같은 자리에 속한다.

그리고 **방향이 중요하다**: 상한을 정하는 것은 **컴파일러**이고, **호스트 버퍼가 그것을 따라간다.**
반대로 하면(B) 호스트의 구현 세부가 언어의 계약이 된다.

### 2.2 플래그 데이의 크기 — **측정해서 적는다**

상한을 넘는 모듈 이름이 **오늘 이 저장소에 있는가**: `examples/*.mls`의 가장 긴 stem은
`count_bounded`(13자)다. **0개가 영향을 받는다.** 사용자 코드는 알 수 없으나, 64자를 넘는 파일 stem은
드물다 — 그리고 **오늘도 참조 동적 호스트에서 이미 쓸 수 없다.**

## 3. 계약 (A를 고를 경우)

- **DP-N2 — 상한 값.** `compiler/src/abi.rs`에 상수 하나(`ML_MAX_MODULE_NAME`)로 두고, `emit.rs`와
  테스트가 **그것을 읽는다.** 문서에 숫자를 적지 않는다(전역 SSOT 규칙).
  - **권고: 64.** 65가 아니라 64인 이유는 근거가 있어서가 아니라 **호스트 버퍼가 컴파일러를 따라가야지
    그 반대가 아니기 때문**이다 — 64는 호스트가 오늘 감당하는 65 안에 들고, 둥근 수여서 버퍼 산식을
    읽기 쉽다. **이 숫자 자체는 임의이며, 그렇게 적는다.**
- **DP-N3 — 호스트 버퍼는 유도한다.** `hosts/c-host/host.c`의 `symbol[]` 크기를 상수 산식으로 적고
  (`sizeof "ml_iface_hash_" + ML_MAX_MODULE_NAME`), **테스트가 호스트 버퍼 ≥ 컴파일러 상한 + 접두어 + 1**
  임을 확인한다. 두 수가 갈라지면 **빨개진다.**
- **DP-N4 — 거부 메시지는 이유를 말한다.** 기존 거부들과 같은 모양:
  *"모듈 이름은 크레이트 이름·C 헤더 가드·Delphi 유닛 이름·예약 export 심볼이 된다"*.

---

## 4. 수용 기준 (측정 가능)

- **A. 컴파일러가 거부한다.** 상한 + 1자 이름의 `mlc build`가 **exit ≠ 0**이고, 메시지가 길이와 이유를
  말한다. 상한 자체는 통과한다(경계 양쪽을 잰다).
- **B. 호스트 버퍼가 유도된다.** 테스트가 `hosts/c-host/host.c`의 버퍼 산식과 `ML_MAX_MODULE_NAME`을
  **읽어 비교**한다. 상수를 키우고 버퍼를 안 키우면 **빨개진다** — 일부러 깨서 확인한다.
- **C. 경계가 실측된다.** 상한 길이 모듈을 실제로 만들어 **참조 동적 호스트가 게이트한다**(거부가 아니라).
- **D. 무변경 증명.** 기존 예제 전부의 산출물이 **한 글자도 바뀌지 않는다**(골든).
- **E. 문서.** `HOST_ABI.md`가 상한의 **존재**를 적는다(**값은 적지 않는다** — 원천은 `abi.rs`).

---

## 5. 범위 밖

- **링크 호스트·Delphi 호스트의 한계는 건드리지 않는다.** 둘은 오늘 더 긴 이름도 받는다. 상한을 두면
  **셋 다 같은 집합을 받게 되므로**, 좁히는 쪽으로 맞춰지는 것이지 넓히는 일이 아니다.
- **파일 경로 길이(`MAX_PATH`)는 다른 문제다.** 이 슬라이스가 다루지 않는다.
