### 9-69. §7을 열두 도메인으로 돌렸다 (2026-09-26, E2) — **가장 강한 근거는 체크드 산술이고, 그것은 설계 결정 하나에 걸려 있다**

사용자가 *"후속작업도 Grok과 함께"* 를 요청했다. 다음 슬라이스를 고르기 전의 §7을 워크플로 세 번으로 넓게 돌렸고,
그 과정에서 나온 결함들을 PR 셋으로 고쳤다(#329 · #330 · #331). 슬라이스는 고르지 않았다 — 사용자 결정이다.

#### 9-69.1. 방법 — 두 라운드와 잣대

- **1라운드**: 이전 표본이 안 쓴 여덟 도메인(누진 과금 · 체크섬 · 근태 · 쿠폰 · 구간표 · 호출 간 상태 · 호스트 데이터 ·
  다필드 레코드), 도메인당 규칙 여섯, 도메인마다 적대적 검증자. 48규칙.
- **1라운드 비평이 방법의 결함을 짚었다**: 조용한 오답을 가르는 기준이 작성자마다 달랐고(신중한 가드판을 판정한
  작성자가 있었다), 오답을 기능에 귀속할 **대조군**이 없었고, 도메인 다섯이 빠졌다.
- **2라운드**: 같은 48규칙을 **한 기준**으로 다시 판정했다 — 가드를 넣지 않은 가장 직접적인 형태를 재고, 오답은
  **그 기능이 있으면 같은 실수가 막히는지** 대조를 통과할 때만 기능에 귀속한다. 도메인 넷(텍스트 포맷 · 작업 메모리 ·
  금융 수학 · 비ASCII 입력)을 더해 72규칙.

| 열(2라운드, 통일 기준) | 건수 |
|---|---|
| 모듈 안, 조용히 틀림 | 26 |
| 우회가 모듈 안에서 맞음 | 37 |
| 우회가 호스트로 밂 | 5 |
| 경계에 안 나감 | 4 |
| 그대로 맞음 · 막힘 | 0 · 0 |

**대조가 1라운드 주장 여럿을 내렸다**: struct(다필드 레코드 도메인에서도 귀속 0 — §9-1 재확인), `else`(조용한 함정
6건 중 4건이 *"else가 있어도 똑같이 쉽다"*), decimal, `min`/`max`, 바이트→숫자 파싱, 배열 상수.

#### 9-69.2. 가장 강한 근거 — 체크드 정수 산술, 그러나 설계 결정 하나에 걸려 있다

2라운드에서 i32 wrap이 7개 도메인에서 status 0의 그럴듯한 오답을 냈다(예: 총급여 20억 → 공제 9,800,328, 정답
20,000,000). 그런데 귀속 대조는 **"`!` 본문에서 기본으로 체크드"(설계 A)** 일 때만 통과한다 — 옵트인 도구(체크드
내장 함수)라면 저자가 가드를 빠뜨리듯 옵트인도 빠뜨린다.

**그래서 A를 버리는 로컬 브랜치에서 구현해 쟀다(E2, 머지하지 않음).** 실험 스위치 하나로 `!` 본문(스칼라 · 문자열 ·
배열 반환 모두)의 `+ - *` · 단항 `-` · `MIN / -1`을 체크드로 바꾸고, 선택적으로 `f64 as i32`도 — 넘치면 `-3`. 첫
시험은 문자열·배열 반환 본문을 빠뜨렸고, 측정 에이전트가 그것을 짚어 고친 뒤 다시 쟀다.

| 626행(규칙 × 입력) | A | A + `as i32` |
|---|---|---|
| 조용한 오답 161행 중 status가 됨 | **84** | **101** |
| 여전히 조용함 | 77 | 60 |
| 맞던 답이 `-3`이 됨(오탐) | 8 — 현실적 입력은 1(22억 주문 부분취소) | 9 |
| 참값이 i32에 드는데 실패가 됨 | 41 | 43 |
| 기존 오라클 테스트의 동작 변화 | **0**(236 중 235 통과, 1은 방출 텍스트를 고정한 가드) | **0** |

A+as에도 남는 60행: 무한(`-> i32`) 헬퍼 16 · 무한 export 본문 4(설계 A2가 아니면 채널이 없다) · f64 절삭·NaN 14 ·
산술이 아닌 것 25 · 하류 저장 상태 1.

**결정 전에 정해야 할 것**(사용자): ① 기본 체크드(A/A2) vs 옵트인(내장 함수) vs i64 vs 문서만 · ② `as i32` 포함 ·
③ status 값(새 음수 vs `fixed`의 DP-M4처럼 `-2` 재사용) · ④ `result` 뒤의 실패(DP-R9) · ⑤ 같은 지문에서 재컴파일만으로
답이 바뀌는 이주. 뒤집히는 것은 슬라이스 DP뿐이다 — SPEC-i32 DP-I4, SPEC-unary DP-U4, SPEC-i32-division의 D2 행
(:101은 `/`의 wrap을 `+ - *`의 wrap에 기대 적는다). **`DECISIONS.md`는 바뀌지 않는다** — D17이 음수를 이미 예약해
두었다(Grok 확인).

#### 9-69.3. 둘째 근거 — 입력 문자열의 인코딩 계약(DP-S2)

비ASCII 입력 도메인에서 검증자가 한국어 ANSI 기계(`GetACP() = 949`)의 ctypes 호스트로 CP949 바이트를 넣어 쟀다:
가×34가 UTF-8로는 102바이트인데 CP949로 68바이트가 되어 길이 제한을 통과하고, 인사말에 이은 이름이 모지바케가 된다
(모듈 결과는 E2, PAnsiChar 변환 단계는 E1). **DP-S2는 2026-08-31에 사용자 확인으로 닫힌 결정**이고 기록된 재개
조건은 *대소문자 무시·정규화*다 — 이번 근거는 그 조건과 다르므로, 재개하려면 그 사실부터 적어야 한다. 또 *UTF-8 전용*
으로 정하면 EUC-KR 바이트 단위 규칙(SMS 길이)이 모든 준수 호스트에서 틀린다는 반례가 같은 도메인에서 나왔다.

규칙과 잰 값(Q17 (A)가 `HOST_ABI.md` 문자열 파라미터 계약 4번에 옮긴 것의 근거 — 같은 날 덧붙였다):

| 규칙 | UTF-8 입력(mlprobe) | CP949 입력(ctypes, `GetACP() = 949`) |
|---|---|---|
| NA-R1 상세주소 — **UTF-8 100바이트** 이하면 바이트 수, 넘으면 `E_TOO_LONG` | 가×33(99B) → 99 · 가×34(102B) → status 1 | 가×34(68B) → **status 0** |
| NA-R3 SMS/LMS — **EUC-KR 90바이트**(한글 45자) 이하 SMS, 2000바이트 이하 LMS | 가×45 → LMS(**틀림**) | 가×45 → SMS · 가×46 → LMS · 가×1001 → `E_TOO_LONG`(전부 맞음) |
| NA-R5 인사말 = 이름 + 반환 리터럴 `" 고객님"` | 홍길동 → 맞음 | 출력 = CP949 이름 바이트 + UTF-8 리터럴 바이트 — UTF-8로 읽으면 이름이, CP949로 읽으면 리터럴이 깨진다 |

#### 9-69.5. Grok

- 워크플로 안의 Grok 호출은 여러 번 240~300초 타임아웃이었다(1라운드 hostdata·비평, 2라운드 hostdata·실현성 조사). 그래서
  결론에 들어가는 사실 주장은 **밖에서 다시** 보냈다: 결정표의 사실 여섯(DP-I4·DP-U4·D2 행·D17·DP-M4 · DP-S2 재개 조건 ·
  PAnsiChar "CORRECT"가 ASCII로만 잰 것 · DP-U1) — 5/6 CONFIRMED, 나머지 하나는 라벨 오류(`DP-D2`가 아니라 표의 `D2` 행)였다.
- 결함 수정 PR 셋은 각각 verify를 거쳤고, #330의 첫 라운드가 FAIL로 셋째 결함을 찾았다.

#### 9-69.6. 표본이 덮지 않은 것

동시성·재진입(스레드별 D16 핸들) · 호스트 쪽 후보(C# · D13) · 실제 C·Delphi 호스트 실행(측정은 `mlprobe`와 ctypes) ·
콜백의 함수 포인터 절반 · 통째로 넘길 수 없는 규모의 표 · 성능 열(O(n²) 재스캔, 비교 40번짜리 숫자 파싱도 "맞음"으로 셌다).
또 도메인 다섯은 특정 후보를 겨냥해 골랐다 — 체크드 산술의 근거는 그것을 겨냥하지 않은 7개 도메인에서 나왔다.
