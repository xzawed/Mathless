### 9-57. 짝 표를 끝냈다 (2026-09-15, E2) — 그리고 **한 줄이 두 가지 일을 하고 있었다**

§9-56.1이 표를 시작했다: *"고정된 각 구성에 값 짝이 있나."* 끝냈다. 방법은 `contains`를 세는
것이 아니라 **방출되는 가드를 전부 뽑는 것**이다 — 헬퍼 안 18개, 함수 본문에 인라인 9개.

| 가드 | 짝 |
|---|---|
| `__d == 0`(0 제수) · `__i < 0 \|\| __i >= len` · `__l{i} < 0` · `ml_cap < __n` · `!__ok{i}` | ✅ 있다 |
| `off + i >= cap - 1` | ❌ 없었다 → **§9-56에서 닫았다** |
| **`if __n < 0 { 0 }`**(선언된 길이) | ❌ **없었다 — 컴파일만 확인돼 있었다** |
| **`if ml_cap < 0 { 0 }`**(배열 쪽) | ❌ **없었다 — 문자열 쪽만 측정돼 있었다** |

#### 9-57.1 `result -1`은 **SPEC이 정하고 아무도 부르지 않았다**

`SPEC-array-return` §5.2-3이 *"음수 길이는 빈 결과"* 로 정했고 #232가 그 근거로 그대로 뒀다.
고정한 것은 `compiler/tests/array_input.rs`인데 **그 크레이트에는 로더가 없다** — 컴파일되는지만
물을 수 있다. 불러 봤다:

| 호출 | status | `*ml_needed` | 버퍼 |
|---|---|---|---|
| `result -1`, cap 8 | 0 | **0** | 무기록 |
| `result 3`, cap **-1** | -1 | 3 | 무기록 |
| `result -1`, cap **-1** | **0** | 0 | 무기록 |

**클램프 둘 다 일을 한다**(각각 심어 확인): 길이 클램프를 빼면 **`*ml_needed = -1`이 status 0과
함께 호스트에 도달한다**(`malloc(-1)`이 그 다음이다). cap 클램프를 빼면 **셋째 줄만** `-1`이 된다
— 둘째 줄은 `3 > -1`이 부호 있는 비교로 이미 거부하므로 클램프가 없어도 같다. **즉 위 표에서
cap 클램프를 재는 칸은 셋째 줄 하나뿐이다**(검증이 짚었고, 심은 결과도 그 줄에서 깨졌다).

> **검증이 두 클램프의 *이유*를 정정했다.** 주석이 MSVC의 `_snprintf(count < 0)`(unsigned 거인)을
> 댄다. **방출되는 Rust는 `ml_cap`을 unsigned로 읽는 곳이 없다** — `__n > __cap`도
> `off + i >= cap - 1`도 부호 있는 i32 비교다. 클램프는 옳지만 **막는 것은 그 위험이 아니다**.
> 실제 효과는 *"빈 결과 + 음수 cap"* 한 칸과 `*ml_needed`의 부호다. E1 유추와 E2 효과가 다르다.

#### 9-57.2 음수 cap은 **문자열 경로 둘 중 하나만** 측정돼 있었다

`string_return.rs`가 `-1`과 `i32::MIN`을 이미 넘긴다 — 그런데 `carrier_name`은 리터럴을 돌려주므로
**`ml_strout` 경로**다. `emit_concat_return`은 다른 방출기이고 writer가 셋이다. #211의 규칙이
또 걸린다: *"음수 cap은 거부된다"* 가 **둘 중 하나에 대해서만** 측정돼 있었다.

네 조각 종류를 한 함수에 담아(`s + " " + n as string + " " + byte_slice + " " + fixed`) 네 개의
음수 cap으로 불렀다. 전부 `-1`, `*ml_needed = 19`, 버퍼 무기록.

> **검증이 여기서 내 주장을 깎았다.** 나는 *"조각 넷이라 가드가 네 writer 앞에 있음을 잰다"* 고
> 적었는데 **틀렸다** — 가드는 **한 줄이고 모든 writer보다 앞**이라 첫 조각만으로 거부가 결정된다.
> 넷은 **성공 호출** 쪽에서 값을 한다. 같은 이유로 거부 경로의 `*ml_needed = 19`도 가드의 증거가
> 아니다(그 줄보다 **먼저** 쓰인다) — Q12 속성이지 가드 측정이 아니다. 주석을 그렇게 고쳤다.

#### 9-57.3 그리고 그 한 줄이 **두 가지 일**을 하고 있었다

`if ml_cap < __n { return -1; }`을 빼고 같은 테스트를 돌렸더니 **오답이 아니라 프로세스가 죽었다**:

```
process didn't exit successfully: ... (exit code: 0xc0000005, STATUS_ACCESS_VIOLATION)
```

탐침 호출이 **`ml_buf = NULL`에 `ml_cap = 0`** 이고, DP-T7이 그것을 **명시적으로 허용한다.**
`__n`은 1 미만이 될 수 없으므로 그 줄이 **모든 writer보다 먼저 돌아간다** — 즉 **용량 검사와
NULL 탐침 계약이 같은 한 줄**이다. `SPEC-string-return`도 방출기 주석도 그 말을 한 적이 없다.
이제 둘 다 적는다.

> **심은 결함이 오답 대신 크래시를 냈다.** 이 저장소의 결함은 대개 조용한데, 이번엔 반대다 —
> 그래서 *"이 줄이 없으면 무슨 일이 나는가"* 의 답이 **"호스트가 죽는다"** 이고, 그 사실 자체가
> 그 줄에 붙일 주석이었다.
