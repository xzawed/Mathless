## 확정 상세 (D14~D22)

2026-08-28, Q1~Q5를 닫으며 사용자 승인. 각 결정의 범위와 기각 대안.

- **D14 호스트.** Delphi=플래그십 데모/1급 호스트, C=ABI 기준 경계(C/C++ 직결, 모든 래퍼의 바닥). 공식 지원 쌍=Delphi+C, Phase 1 수직 슬라이스는 Delphi부터. 기각: C 단독(데모·서사 약함). 이연: Delphi+C#(C#은 여전히 C ABI 경유 → Phase 4).
- **D15 표면 문법.** 중괄호 기반 정적 타입, 값 타입 우선. MVP 부분집합 = struct + 자유 함수 + 모듈. 예시(`export fn … -> f64`)에 가깝다. "C#-like"는 개발자층·친숙도 라벨일 뿐 class 상속/GC/제네릭/async 불포함. 기각: 정통 C#(상속 baggage), TS-like(웹 정체성 혼동·구조적 타이핑), 독자 문법(AI 품질 불리). 계열/방향만 확정, 세부 문법 미정.
- **D16 메모리.** (1) 인자 포인터=호출 기간만 유효(빌림), (2) 반환 데이터=caller-allocates out-buffer(MVP는 스칼라 반환 우선), (3) 모듈 상태=명시적 context handle(생성~파괴 생존). 모듈 힙과 호스트 힙 분리, 할당자 넘는 소유권 이전 금지. 기각: 모듈 단위 RC(경계 증감 주체 모호, 내부 구현으로만), 순수 arena(호출 넘는 상태 불가 → handle로 흡수).
  - **반환 데이터 규약(Q12 확정, 2026-08-31 사용자 승인)**: **caller-allocates out-buffer.** 가변 길이
    데이터는 호스트가 **버퍼와 용량**을 넘기고, 모듈이 채우고, **필요한 길이**를 out-param으로 돌려준다.
    용량이 모자라면 **D17의 음수 예약 status**로 보고하고 버퍼는 건드리지 않는다 — 절단은 성공이 아니라
    실패다. 모듈은 **할당하지 않는다**(`no_std`, 할당자 없음 유지).
    - **범위 정정:** Q12는 두 질문을 묶고 있었다. **고정 레이아웃 struct(스칼라 필드만)는 힙이 필요
      없어 이 결정 밖이다** — `out` 파라미터와 같은 기계장치다. 이 결정이 지배하는 것은 **가변 길이**
      (문자열·배열·문자열을 품은 struct)뿐이다.
    - 기각: **모듈 소유 + 명시 free** — 빌드는 된다(`no_std`에서 CRT `malloc`/`free` 직접 선언,
      의존성·크기 불변, 실측). 그러나 모듈은 **UCRT 힙**을 쓰고(import `api-ms-win-crt-heap` 추가, 실측)
      이는 D16 본문의 **"할당자 넘는 소유권 이전 금지"** 그 자체다. D14의 플래그십 Delphi는 자기 메모리
      매니저를 쓰므로 호스트가 습관대로 해제하면 **조용히 손상**된다.
      **스칼라만 유지** — 배열이 업무 규칙 라운드에서 반복해서 벽이었다.
      **(2026-09-01 정정, 사용자 승인: 원문은 "두 번의 3라운드에서 네 번"이었으나 추적 가능한 것은
      §3a-3의 두 번뿐이다 — §3a-2의 벽은 배열이 아니라 `out` 파라미터였다. D16의 결론은 그대로다;
      근거 문장의 과장만 걷어낸다.)**
    - 감수: 길이 미지 시 호스트 재호출 1회. 그리고 호스트가 status를 무시하면 꼬리가 조용히 잘리므로,
      **절단을 음수 status로 두는 것이 결정의 일부다.**
- **D17 에러.** ABI 유일 규약 = 정수 상태코드 + out-parameter. 표면 Result/명시적 에러는 그 위 sugar로 lowering. 실패 가능 함수만 대상(순수 함수는 값 직접 반환). 모듈 내부 예외는 후속. 기각: 예외 ABI 통과(언어별 unwinding 비호환), errno 전역(재진입 취약).
  - **status 체계(Q13 확정, 2026-08-28 사용자 승인)**: **평탄 i32** — `0`=성공 / **양수**=모듈 정의 도메인 에러 / **음수**=예약(런타임·ABI). 실패 가능성은 **명시적 `!` 표식**(`-> T!`)으로 시그니처에 고정. 도메인 코드 = `error NAME = N`(양수) 선언 + `fail NAME` 문. 실패 시 out-param **미변경**(호스트는 status≠0이면 out 미판독). 기각: HRESULT식(무겁·Windows 중심), 0/음수 무구조(의미 비트 부족). D17 에러-경로 슬라이스로 구현·실측(SPEC #14 / 구현 #15; 오라클 로드로 status/out-param 검증).
- **D18 모듈 포맷.** 플랫폼 표준 DLL/SO. ABI 버전은 파일 선두 헤더가 아니라 예약 export 심볼 `ml_module_abi_version`으로 노출(로더가 GetProcAddress/dlsym 조회). 사용자 모듈 export는 런타임 `ml_*`와 충돌하지 않는 별도 접두어(예: `mlx_`). 암호화/서명 컨테이너는 P1. 기각: 파일 선두 커스텀 헤더(PE/ELF 매직 필요, 로드 불가), 컨테이너 MVP 내재화(R05·범위 위반).
  - **현재 산출은 `.dll`뿐이다(2026-09-02 추가, 사용자 승인).** 결정 자체는 바뀌지 않는다 — "표준 DLL/SO"는 **포맷 선택**이지 오늘 나오는 산출물 목록이 아니다. `mlc build`는 `.dll`·`.h`·`.pas`를 낸다. `.so`/ELF 개시는 **미결**이고(`STATUS.md` §4-7), `ubuntu-latest` CI 잡은 프런트엔드 보험이지 D22가 아니다. `dlsym` 경로도 ⏳ 미구현이다(`HOST_ABI.md` "버전"). 이 줄은 저장소가 공개된 뒤 이 결정이 **"`.so`가 이미 나온다"로 읽히는 것**을 막기 위한 것이다.

Phase 1 툴체인(2026-08-28, 실측 근거로 사용자 승인). 근거: rustc/cargo 설치·동작, C 컴파일러·Delphi CLI 미설치, cdylib 빌드+kernel32 로드·호출 스모크 E2 통과.

- **D19 코드젠(잠정).** 비-Rust 독립 IR → `no_std`+`extern "C"`+`repr(C)` Rust → `cargo build --crate-type cdylib`. **Q6를 닫지 않는다** — C-emit 슬롯 유지, LLVM 이연. IR은 Rust가 아님(Q11 불변). 보호(D04/D05)는 rustc가 자동 보장하지 않으므로 export/심볼을 **측정**한다(Phase 1 SPEC 수용 C).
- **D20 컴파일러 언어.** Rust. 기각: C++(미설치·무거움), Python(별도 런타임·타입 약함).
- **D21 Phase 1 호스트.** Rust kernel32 오라클 = **CI 검증 수단**일 뿐. 원문(2026-08-28)은 D14 done-gate(Delphi 플래그십/C)를 "이 머신에 dcc64/cl/gcc 없어 BLOCKED"로 적고 사용자 승인으로 잠정 보류했다. 그 상태로 W0~W6을 오라클로 진행했다.
  - **갱신(2026-08-29, 사용자 확인 후): done-gate의 C 쪽은 닫혔다.** MSVC `cl`(19.44)로 빌드한 C11 호스트가 산출 DLL을 `LoadLibrary`/`GetProcAddress`로 로드·호출해 스칼라·D17 에러 경로를 검증한다(수용 D, `hosts/c-host/host.c`, PR #43). 이 개발 머신과 GitHub `windows-latest` 러너 두 곳에서 통과.
  - **원래의 "툴체인 없음"은 오진이었다.** MSVC Build Tools 2022는 이미 설치돼 있었고 **PATH에만 없었다**(`vswhere`로 확인, `vcvars64.bat`으로 사용 가능). 판단이 `where cl` 한 번에 멈춰 있었다.
  - **Delphi는 여전히 미확보 — 이번엔 실측으로 확인했다.** `dcc64`/`fpc`가 PATH에 없고, 레지스트리의 `Embarcadero\Studio\15.0` 항목은 **제거된 설치의 잔재**이며(`BDS` 키 비어 있음, `C:\Program Files (x86)\Embarcadero` 부재), 디스크 탐색에도 Pascal 컴파일러가 없다. 따라서 생성 `.pas`는 **아무도 컴파일한 적이 없고** DRAFT를 유지한다.
  - 결론: **D14의 공식 지원 쌍(Delphi+C) 중 C만 증명됐다.** 오라클 그린도, C 호스트 그린도 "Delphi에서 됐다"로 말하지 않는다.
- **D22 타깃.** Windows x64 우선. **"msvc"를 D18에 못박지 않는다**(빌드 설정). export 집합·CRT/unwind는 측정.
