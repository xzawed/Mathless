### 9-29. 배열 반환 슬라이스 (2026-09-11, E2) — **Q12의 가장 어려운 약속이 계산된 값에서도 지켜졌다**

`-> [T]!`가 Q12 caller-allocates를 물려받는다. **호스트가 버퍼를 주고 모듈이 채운다.**

**설계의 전부는 하나의 충돌을 푸는 것이었다.** Q12는 *"절단이면 한 바이트도 쓰지 않는다"* 를 요구하고,
문자열 반환은 **2패스**(세고 → 쓰기)로 그것을 지켰다 — 소스 바이트를 두 번 훑을 수 있었기 때문이다.
**배열 원소는 계산해야 나오므로 두 번 훑을 수 없다.** 쓰면서 길이를 알게 되면 절단 시 이미 쓴 것이 남는다.

해법은 **`result <n>` 문**이다: 길이를 **먼저 선언**하게 해서 **용량 검사를 첫 쓰기 앞으로** 옮긴다.
`*ml_needed`를 쓰고, 안 들어가면 즉시 반환하고, 그제야 0으로 채우고 원소를 쓴다. **순서가 곧 계약이다.**

**실측(E2).** 절단 시 **canary 전 바이트 보존** — 오라클과 실제 C 호스트 양쪽에서 바이트 단위 비교.
probe는 2회에 수렴, 딱 맞음은 성공, 음수 cap은 0, 빈 결과 + NULL은 성공.
**§0.2가 근거로 든 창고 배분이 한 번의 호출로 `[10,15,0]`을 답한다** — 그전에는 창고마다 호출하며
앞 구간을 다시 걸었다.

**착수 검토가 SPEC에서 세 곳을 고쳤고, 셋 다 제 잘못이었다:**

1. **수용 기준 B6·B7이 제 설계로 불가능한 것을 요구**했다 — `result` 뒤에는 이미 `*ml_needed`가 쓰이고
   버퍼가 채워져 있는데 "무기록"을 요구했다. 구현에 들어갔으면 빨간 채로 남거나 **제가 테스트를 약하게
   고쳐** 통과시켰을 것이다. DP-R9로 열어 사용자 확인을 받았다.
2. **단위 근거가 정반대**였다. 바이트 `cap`은 오히려 **절단**시켜 안전하고, **원소 단위인 결정이
   8배 오버런을 만든다**. 결론은 유지하되 대가를 헤더·유닛·두 호스트에 **곱셈으로** 싣게 했다.
3. **`if b { result n }`** 이 "정확히 하나 + 먼저"를 만족하며 **용량 검사를 건너뛴다.** 소스 순서가
   아니라 **지배**여야 했고, 최상위 블록 전용으로 좁혔다.

**첫 Red가 가짜였다 (AR1).** 15개 중 9개가 즉시 "통과"했는데, `result`가 미지의 식별자라 파서 폴백이
`found Ident("result")`로 **소스를 되뱉었고** needle `"result"`가 그걸로 만족됐다. **#203에서 지적한
결함을 제 테스트가 저질렀다.** 폴백을 이름 붙여 거부하니 12개가 빨개졌다.

**가드가 세 번 값을 했다.** ① #204의 공백 가드가 제 회귀를 **네 번** 잡았다(스크립트로 메시지를 고치다
같은 결함을 재현). ② 색인 가드가 SPEC 등록 누락을 잡았다. ③ N1의 예제 헤더 가드가 새 예제 둘을 잡아
**AR5를 선택이 아니라 강제로** 만들었다.

**부수로 소스 텍스트 가드 하나를 산출물 가드로 바꿨다.** `doc_claims`가 `header.rs`의 **소스**에서
`#define ML_ST_INSUFFICIENT_BUFFER (-1)` 리터럴을 찾고 있었는데, 그 값을 `abi.rs` 상수로 올리자
**가드가 실패했다 — 방출되는 헤더는 그대로이고 오히려 더 정확해졌는데도.** §7이 적은 그대로다:
**가드는 산출물을 지켜야 한다.** 이제 방출기를 불러 나온 텍스트를 본다. `-1` 리터럴은 0개다.
