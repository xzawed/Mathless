# SECURITY

## 보호 대상

배포된 **스크립트/알고리즘 구현**이 외부에서 쉽게 읽히지 않게 하는 것.  
소스 유출과 손쉬운 디컴파일·재현을 어렵게 만든다.

대상이 아닌 것(1차):

- 브라우저 XSS 모델
- 완전한 샌드박스 OS
- “리버싱 불가능”

## 위협 (우선)

1. 배포물에서 소스에 가까운 형태로 로직 복원
2. 심볼/문자열로 알고리즘 파악
3. 모듈 변조 후 재로드
4. 호스트가 의도하지 않은 API 호출 (과도한 노출)

## 단계

### P0 — MVP

- 소스 미배포
- 심볼 strip
- 최소 export만 남김
- ABI 버전 검사

### P1

- 모듈 무결성 해시/서명 검증
- 개발/배포 빌드 분리
- 호스트 함수 화이트리스트(명시적 등록만)

### P2

- 난독화, 제어흐름 변환
- 암호화 로딩
- 필요 시 상용 보호 도구 연동

P2를 언어 핵심에 처음부터 넣지 않는다.

## 보안과 DX

개발 중에는 디버그가 되어야 한다.  
배포물에 강한 보호를 걸수록 현장 진단은 로그·버전·제한된 텔레메트리로 대체한다.

## 능력 모델

이전 대화의 capability 아이디어는 유효하다.  
네이티브 모듈이라도 호스트가 등록한 함수만 보이게 하면 된다.

MVP: 언어에 파일/네트워크 표준 API를 넣지 않는다.  
필요하면 호스트가 준다.

## 대외 표현

사용: “분석과 변조 비용을 높인다.”  
사용 금지: “리버싱이 불가능하다.”
