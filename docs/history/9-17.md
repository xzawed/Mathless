### 9-17. Pascal 호스트를 고유 축으로 키웠다 (2026-09-07, E2) — **두 건, 둘 다 주장에 가드가 없었다**

§9-16이 정한 축이다: **개수가 아니라 Pascal만 물을 수 있는 것.** 두 건이 나왔고, **둘 다 파일이
자기 자신에 대해 하던 주장인데 재는 것이 없었다.**

**(1) 로드 시점 결합 — "`begin`에 도달조차 못 한다"**

`host.dpr` 머리말이 두 공식 호스트의 차이를 적는다: C 호스트는 `LoadLibrary`라 **없는 모듈이
보고할 수 있는 데이터**이고, 이 호스트는 `external`이 로드 시점에 묶여 보고할 기회조차 없다.
**양쪽 다 쟀다** — `carrier.dll`을 치우고 각각 돌렸다:

```
C 호스트    검사 78줄을 마친 뒤  FAIL LoadLibraryA(...) -> error 126,  exit 1
이 호스트   출력 0바이트                                              exit 0xC0000135
```

> ⚠ **첫 판은 C 호스트를 기억으로 서술했고 틀렸다.** *"`LOAD_FAIL`을 찍고 2를 돌려준다"* 고
> 적었는데 `host.c`에 그 문자열은 없고 `return 2`는 usage 오류다 — **내 스크래치패드 호스트**를
> 보고 다른 파일을 서술한 것이다. Grok verify가 잡았고, 읽어서 고치는 대신 **C 호스트를 실제로
> 빌드해 돌려** 교체했다. 이 저장소가 반복해서 걷어내는 모양이 정확히 이것이다.

주장의 요지는 맞았다. 이제 게이트가 `.dll` 하나를 옆으로 치우고 **출력이 비어 있을 것**을 요구한다 —
"`begin`에 도달 못 한다"가 바로 그 뜻이기 때문이다. **상태 코드는 찍기만 하고 고정하지 않는다**:
Windows의 것이지 우리 것이 아니어서, 바뀌면 주장과 무관한 이유로 빨개진다.

**(2) 1바이트 `Boolean` — "LongBool을 쓰지 마라"**

생성 유닛의 머리말이 그렇게 적어 두고 **한 번도 재지 않았다.** 재 봤더니 장식이 아니었다.
선언만 `LongBool`로 바꿔서 측정:

```
              모듈이 쓴 바이트        호스트가 읽은 값
Boolean       0 AA AA AA (1바이트)    FALSE   ← 맞다
LongBool      0 AA AA AA (1바이트)    TRUE    ← 모듈은 false라고 했다
```

**모듈은 false라고 했고 호스트는 true로 읽었다. 크래시 없음.** 이 프로젝트가 막으려는 조용한
오답 그 자체다.

> **검사가 둘인 이유가 여기 있다.** **값** 검사가 잘못된 선언을 잡고(LongBool은 여기서 실패),
> **canary**가 모듈이 한 바이트를 넘겨 쓰는 것을 잡는다(LongBool은 canary를 **통과한다**).
> 어느 하나로도 충분하지 않다. C 헤더는 `bool`이라 적고 크기는 C가 정하므로, **이 질문은 Pascal
> 호스트만 물을 수 있다.**

**깨뜨림 확인**(§7-1 규칙 3): `header.rs`가 `LongBool`을 방출하게 바꾸면 게이트가 빨개진다.
그리고 `shapes`가 `uses`에 들어오면서 **§9-14의 충돌 표면도 넓어졌다** — 유닛 넷이 같은 예약
심볼을 선언하고, 넷 다 한정된 이름으로 게이트된다.

체크 14개 → **17개**. 늘어난 셋은 전부 **C 호스트가 물을 수 없는 것**이다.
