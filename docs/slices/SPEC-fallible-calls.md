# Slice SPEC — 실패 가능 함수 호출 (`try`)

> **상태: 확정(accepted) · 구현 대기** — 2026-09-01.
> **DP-F1~F8·F10 사용자 확인 완료(권고안 그대로).** 결정:
>
> | DP | 결정 |
> |----|------|
> | **F1** | **`try` 접두 키워드** |
> | **F2** | **세 문장 위치**(`let [mut]` · 대입 · `return`), 식 안에는 불가 |
> | **F3** | **#67 내부 `-> T!` 금지 해제** |
> | **F4** | non-fallible 호출자 **거부**(추론도 기본값도 아님) |
> | **F5** | v1은 **내부 피호출자만** — export는 §5.2 래퍼 리팩터 뒤에 가산적으로 |
> | **F6** | 내부 표현 **`Result<T, i32>`**, `match`로 해체(Rust `?`·`unwrap` 금지) |
> | **F7** | **`-> string!` 피호출자 제외**(v1) |
> | **F8** | 기본값/복구 형태 **연기** → `OPEN_QUESTIONS.md`에 새 Q |
> | **F10** | 헤더에 **에러 출처 주석**, 시그니처는 바이트 불변 |
>

> 받지 않았다. **WF1~WF7은 F9에 의존하지 않으므로 그대로 진행하고, WF8에서 다시 여쭌다.**
>
> **근거 수준:** §0·§1이 **E2 실측**(오늘의 언어로 쓴 프로그램 6개 + 우회책 6개 + export 표면 덤프),
> §2가 E0 + 확정 결정 인용, §4의 내부 표현 비교가 **E2**(`no_std` 프로브로 실제 빌드).
> **선행:** #95(export 호출 수정) · SPEC-calls(DP-C1) · D17 · SPEC-out-params.
> **이 슬라이스는 C ABI를 바꾸지 않는다.** 생성 `.h`·`.pas`가 바이트 단위로 같아야 한다(§3-F).

## 0. 정직하게 — 이 슬라이스의 근거는 "불편함"이 아니다

**측정한 것:** 잎(leaf) 제한에 막히는 프로그램 6개를 쓰고, 각각의 우회책을 써서 **여섯 개 전부
빌드에 성공했다.** 줄 수 차이는 **−3 ~ +6줄**이다. 헬퍼가 불가능한 것이 아니다.

그러니 **"헬퍼를 못 만든다"를 헤드라인 근거로 쓰지 않는다.** 실측이 가리키는 진짜 비용은 셋이다.

### 0.1 우회책이 검증을 **권고 사항으로 격하**시킨다 (E2, 측정)

규칙 하나(`check_qty`)를 세 가지로 써서 전부 빌드하고 헤더를 비교했다:

| 변형 | export 심볼 | `.dll` 크기 | `.text` |
|---|---|---|---|
| A. 두 export에 **복붙** | 3 | 9,728 B | 3,480 |
| B. 규칙을 **자체 export로 승격** | 4 | 9,728 B | 3,448 |

**파일 크기 차이는 0바이트다.** 심볼은 +1(3→4). 여기까지는 싸다. **진짜 비용은 헤더에 있다:**

```c
A: int32_t mlx_line_total(int32_t qty, double price, double* out_value);
B: double  mlx_line_total(int32_t qty, double price);   // status가 아예 없다
   int32_t mlx_check_qty (int32_t qty, int32_t* out_value);
```

규칙을 export로 승격하면 **호출자가 non-fallible이 된다.** 검증은 호스트가 순서를 지켜 불러 주기를
바라는 **권고 사항**이 되고, **ABI가 그것을 강제하지 않는다.** 호스트가 `mlx_check_qty`를 건너뛰고
`mlx_line_total`을 불러도 아무것도 막지 않는다. 이것이 이 슬라이스가 사는 이유다.

### 0.2 오늘의 거부 메시지가 **틀린 조언**을 한다 (E2, 측정)

내부 `-> T!` 거부문은 *"a fallible function must be `export`ed"* 라고 말한다. 그대로 따라
`export`를 붙이면 **다른 규칙에 걸린다**(DP-C1의 호출부 거부). 측정으로 확인했다. 컴파일러가
막다른 길을 가리키고 있다.

### 0.3 근거가 **순환**이다 — 그리고 어느 쪽도 ABI 장애를 대지 않는다

- 내부 `-> T!` 금지(#67)의 근거: *"DP-C1이 fallible 피호출자 호출을 금지하므로 내부 `-> T!`는
  **도달 불가능**하다"*.
- DP-C1의 근거: *"식 자리에 넣으려면 **에러 전파 문법을 함께 설계**해야 한다 — 별도 슬라이스"*.

**이 슬라이스가 그 문법이다.** `SPEC-calls.md` §5.3이 이미 *"이 제한은 '실패 가능 함수 호출'
슬라이스가 생기면 **가산적으로** 풀린다"* 라고 약속해 뒀다.

### 0.4 이 슬라이스가 **고치지 못하는 것** (기록)

측정에서 가장 뚜렷한 조용한 오답은 **P6**이었다 — non-fallible `ratio_or_zero`가 fallible
`safe_div`를 부르려다 막히고, 우회책이 `if b == 0.0 { return 0.0 }`이 되면서 **`0.0`이 "0으로
나눔"과 "비율이 0"을 구분하지 못하게** 된다. **이 슬라이스는 그것을 고치지 않는다** — DP-F4대로
non-fallible 호출자를 거부하고 시그니처를 바꾸라고 말할 뿐이며, 그것은 오늘도 할 수 있다.

### 0.5 단락 평가 부채 — **이 슬라이스도 갚지 못한다** (초안에서 정정)

`SPEC-logical-ops.md`가 이 슬라이스를 지목해 뒀다:

> **단락 평가의 실측 — 관측 수단이 없다(§2.3). 호출 또는 실패 가능 연산 슬라이스에서 측정한다.**

초안은 이것을 갚겠다고 적었다. **틀렸다.** 실패 가능 호출이 관측 도구인 것은 맞지만, 그러려면
`a() && try b()`처럼 **조건 안에 `try`가 들어가야** 하고 **DP-F2가 정확히 그것을 금지한다.**
부작용도, 관측 가능한 상태 변화도 여전히 없으므로 **v1에는 관측 수단이 없다.**

**부채는 열린 채로 남는다**(`STATUS.md` §5-1). 갚는 것은 조건 위치를 여는 후속(§5.1의 `while try`)
이며, 그 SPEC에 이 문장을 인계한다. **이 슬라이스의 수용 기준에서 뺐다** — 잴 수 없는 것을
수용 기준으로 두지 않는다(§7 "없는 측정을 테스트로 만들지 않는다").

## 1. 목표

```mathless
error E_BAD_QTY = 1
error E_DIV0    = 2

// 새로 허용: 내부 함수가 실패 가능해질 수 있다(#67 금지 해제)
fn check_qty(qty: i32) -> i32! {
  if qty < 1 { fail E_BAD_QTY }
  return qty
}

fn safe_div(a: f64, b: f64) -> f64! {
  if b == 0.0 { fail E_DIV0 }
  return a / b
}

// 새 문법: `try` — 실패 가능 함수를 부르는 유일한 방법
export fn unit_price(total: f64, qty: i32) -> f64! {
  let q = try check_qty(qty)            // 실패하면 여기서 E_BAD_QTY로 즉시 반환
  return try safe_div(total, q as f64)
}
```

생성 헤더는 **오늘과 완전히 같다**:
```c
int32_t mlx_unit_price(double total, int32_t qty, double* out_value);
```

## 2. 계약 (Contracts)

### 2.1 `try`는 **이른 반환**이다 (DP-F1·DP-F2)

`try f(args)`는 정확히 두 가지 중 하나다:

- **성공** — `f`가 값을 냈다. 그 값이 감싸는 문장에 묶인다. 다음 문장으로 간다.
- **실패** — `f`가 `fail E`를 실행했다. **호출자가 그 자리에서 즉시 반환**하며, status는
  `E`의 양수 코드 **그대로**다. 재번호도 오프셋도 없다(에러 표는 모듈 스코프라 호출자와 피호출자가
  같은 표를 공유한다). 호출자의 나머지는 실행되지 않는다.

### 2.2 세 위치에서만 쓸 수 있다 (DP-F2)

```mathless
let x = try f(a)          // let (mut 가능)
x = try f(a)              // 대입 (out 파라미터 포함)
return try f(a)           // return
```

**식 안에는 절대 들어갈 수 없다.** `1.0 + try f(x)`도, `try f(try g(x))`도, `g(try f(x))`도,
`if try f(x) { }`도 **파서가 거부**한다 — AST에 try-호출 **식 노드를 만들지 않는다.**

이 제한이 지키는 것(전부 실측된 위험이다):

- **`i32` 나눗셈의 평가 순서.** `codegen.rs`의 가드는 `{ let __d = <rhs>; … (<lhs>) … }`로
  **오른쪽을 먼저** 평가한다(#76이 넣었다, 실측). 피연산자에 `try`가 들어가면 그 순서가 **관측
  가능해진다.** 위치 제한이 이것을 **도달 불가능**하게 만든다.
- **`&&`/`||` 단락 평가.** 조건 안에 `try`를 허용하면 lowering이 prelude를 끌어올려 오른쪽을
  **무조건 평가**하게 되기 쉽다. 값은 같지만 **실패하는 오른쪽이 단락됐어야 할 호출을 중단시킨다** —
  소스에서 보이지 않는 조용한 오답이다.
- **`while` 조건.** 같은 이유이고 결과는 더 나쁘다(중단 대신 정지).

> 이 셋은 나중에 **가산적으로** 열 수 있다. §5.1에 `while try`의 정확한 lowering을 적어 둔다.

### 2.3 호출자는 **반드시 `-> T!`** 여야 한다 (DP-F4)

non-fallible 함수는 나갈 **status 채널이 없다.** 거부한다.

대안 둘을 모두 기각한다: **본문에서 `!`를 추론**하는 것은 소스 변경 없이 **export ABI를 바꾸므로**
D17이 이미 기각했다(DP-E1). **기본값으로 삼키는 것**은 P6의 `0.0` 그 자체 — 이 저장소가 일곱 번
만난 모양이다.

### 2.4 v1은 **내부 함수만** 부를 수 있다 (DP-F5)

`try`의 피호출자는 `export` 없는 `fn`이어야 한다. **이유는 "export 호출이 깨져 있어서"가 아니다 —
그건 #95가 고쳤다.** 진짜 이유는 lowering이 갈리기 때문이다:

- export된 fallible 함수의 본문은 **C ABI로** 방출된다(`out_value`에 쓰고 status 반환).
- `try`로 불리는 피호출자는 **`Result<T, i32>`를 반환해야 한다**(§2.5).

둘 다 지원하려면 본문을 두 번 방출하거나 **"한 이름, 한 본문" 리팩터**(모든 함수를 평범한
`fn <name>`으로 방출하고 export마다 얇은 `#[no_mangle] extern "C" fn mlx_<name>` 래퍼를 붙이는 것)가
필요하다. 그 리팩터는 **옳은 방향이지만 모든 export의 방출을 건드린다** — 별도 슬라이스로 두어
회귀를 격리한다. §5.2.

### 2.5 내부 표현은 `Result<T, i32>`다 (DP-F6, 세 설계안 만장일치)

**측정으로 고른 것이다.** `core::result::Result`는 `core` prelude에 있어 `no_std`에서 그대로
쓸 수 있다(프로브로 확인). 후보 비교:

| 후보 | 문제 |
|---|---|
| `(i32, T)` 튜플 | 실패 경로에 **가짜 `T`를 지어내야 한다** — `*const u8`이면 `core::ptr::null()`까지 |
| `Option<T>` | **D17 코드를 잃는다.** Q13은 평탄 양수 i32인데 `None`은 이름 없는 실패 하나뿐이다 |
| `&mut i32` status out-param | 내부 경로에 ABI 기계장치를 다시 짓는 것 |
| **`Result<T, i32>`** | **실패 경로에 값이 필요 없다.** D17에 그대로 맞는다 |

**Rust의 `?`는 쓰지 않고 `match`로 푼다.** `?`는 `Result`를 반환하는 함수 안에서만 동작하는데
export는 맨 `i32`를 반환하므로 export마다 중첩 내부 fn이 필요해진다. `match` 하나면 세 가지 호출자
형태에 모두 같은 모양으로 들어간다. `unwrap`/`expect`는 **금지** — 패닉은 호스트 스레드를 매단다.

### 2.6 `out` 파라미터가 있는 피호출자는 부를 수 없다

이미 **#95에서 닫혔다**(`out`은 포인터이고 호출식에 주소를 넘길 문법이 없다). 여기서는 재확인만 한다.

### 2.7 `-> string!` 피호출자는 v1에서 제외한다 (DP-F7)

반환된 문자열이 **머물 곳이 없다** — 문자열 지역 변수는 거부되고(SPEC-string-return), `return try
name(x)`는 DP-T5(리터럴 또는 파라미터만)를 위반한다. 포함하면 DP-T5와 DP-S2를 함께 다시 연다.
메시지가 그 이유를 말한다.

## 3. 수용 기준 (측정 가능)

- **A. 컴파일:** `examples/quote.mls`(§1의 형태) → `mlc build`.
- **B. 값(오라클):** 성공 경로가 옳은 값을, 실패 경로가 **피호출자의 코드 그대로**를 낸다.
- **B2. 전파 깊이:** 3단계(`export` → `fn` → `fn`)에서 가장 깊은 곳의 코드가 **변형 없이** 나온다.
- **B3. 실패 시 out 미변경:** 실패한 호출 뒤 D17 `out_value`는 **미변경**(canary). 단 `fail` 앞에서
  대입된 **선언된 `out`은 그대로 남는다**(DP-O3, #90에서 측정한 그대로).
- **C. 보호:** export 집합 **불변**. `-> T!` 헬퍼가 export에 **나타나지 않음**을 PE 리더로 측정 —
  §0.1이 잰 "승격 비용"이 실제로 사라졌는지가 이 슬라이스의 핵심 측정이다.
- **D. 수용 D:** C 호스트에 B·B2·B3. 헤더가 **오늘과 바이트 단위로 같음**을 확인.
- **E. 부정 케이스:** `try` 없는 fallible 호출 · infallible에 붙은 `try` · non-fallible 호출자 ·
  식 안의 `try`(4가지) · export 피호출자 · `out` 피호출자 · `-> string!` 피호출자 · 상호 재귀.
- **F. ABI 무변경:** 오늘 컴파일되는 모든 예제의 `.h`·`.pas`가 **바이트 단위로 동일**. 주장이 아니라
  테스트로 못박는다.
- **G. 행 아님:** 전파 경로에 패닉 없음. 타임아웃 테스트.

## 4. 설계 결정 (DP — **F1~F8·F10 확인 완료**, F9만 열림. 근거는 남긴다)

| DP | 선택지 | **결정** | 근거 |
|----|--------|------|------|
| **F1 표식** | `try` 접두 / `f(x)?` 접미 / 표식 없음 | **`try` 접두** | 독립 설계 셋 중 **둘이 `try`를 골랐다**. `?`는 D15가 겨냥한 C#·Delphi 개발자에게 **nullable로 읽히고**, `??`(기본값 삼키기)를 자연스러운 다음 수처럼 부른다 — DP-F8에서 미루려는 바로 그것이다. 접두 키워드는 문장 표식으로 읽혀 §2.2의 위치 제한과 맞는다 |
| **F2 위치** | `let`만 / **`let`·대입·`return`** / 임의 식 | **세 문장 위치** | 식 허용은 `i32` 나눗셈 평가 순서와 `&&` 단락을 **관측 가능하게** 만든다(둘 다 실측). `let`만으로 좁히면 `return try f(x)`가 임시 변수 두 줄이 되는데, 세 위치는 전부 **호출이 RHS 전체**라 중첩 위험이 없다 — 안전은 중첩 금지에서 오지 위치 개수에서 오지 않는다 |
| **F3 #67 금지 해제** | 유지 / **해제** | **해제** | 설계 규칙이 아니었다. `SPEC-calls.md` §5.3이 *"호출할 수 없는 경로에 ABI 기계장치를 짓는 것"*이라 기각했다고 적었고, **이 슬라이스가 그 경로를 호출 가능하게 만든다.** 같은 문서가 "가산적으로 풀린다"고 약속했다 |
| **F4 non-fallible 호출자** | **거부** / 본문에서 `!` 추론 / 기본값 | **거부** | 추론은 **소스 변경 없이 export ABI를 바꾼다** — D17 DP-E1이 이미 기각. 기본값은 P6의 `0.0` 그 자체 |
| **F5 피호출자 범위** | **내부만** / 내부+export | **내부만 (v1)** | export된 fallible의 본문은 C ABI로, `try` 피호출자는 `Result`로 방출된다. 둘 다 지원하려면 **"한 이름, 한 본문" 래퍼 리팩터**가 필요한데, 그건 모든 export의 방출을 건드리므로 **별도 슬라이스**로 격리한다(§5.2). #95 이후 "깨져 있어서"는 더 이상 이유가 아니다 |
| **F6 내부 반환 형태** | `Result<T,i32>` / `(i32,T)` / `Option<T>` / status out-param | **`Result<T,i32>`** | **만장일치.** 실패 경로에 **가짜 `T`가 필요 없는 유일한 형태**다. `Option`은 D17 코드를 잃는다. `core`에 있음을 프로브로 확인. Rust `?`가 아니라 `match`로 푼다(export는 맨 `i32`를 반환하므로) |
| **F7 `-> string!` 피호출자** | 포함 / **제외** | **제외 (v1)** | 반환된 문자열이 머물 곳이 없다(문자열 지역 변수 거부). 포함하면 DP-T5·DP-S2를 다시 연다 |
| **F8 기본값/복구 형태**(`else 0.0`, `??`) | v1에 포함 / **연기** | **연기** | 전파만 두면 "에러는 버릴 수 없다"가 **타입 시스템의 성질**로 남는다. 첫 기본값 형태가 그것을 **관례로 격하**시킨다. `OPEN_QUESTIONS.md`에 새 Q로 기록 |
| **F9 중복 `error` 값** ⚠ | 허용(오늘) / **거부** | **거부 — 별도 승인 요청** | `error A = 1` + `error B = 1`이 **오늘 컴파일되고 `#define` 둘을 방출한다**(실측). 지금은 코드가 함수 경계를 넘지 않아 피해가 갇혀 있다. **전파가 그것을 넘게 만든다** — 호스트가 `1`을 자기 `if`-체인이 먼저 검사한 쪽으로 매핑한다. **동작 변경이라 따로 여쭙는다** |
| **F10 헤더의 에러 출처** | 없음 / **주석으로 방출** | **주석으로** | Q13의 평탄 i32는 출처를 못 담고, 헤더는 지금 **모든 코드를 모든 함수에 대해** 나열한다. 전파가 그것을 악화시킨다(세 단계 아래 헬퍼에서 코드가 온다). `reject_recursion`이 호출 그래프가 비순환임을 이미 증명하므로 고정점 계산이 공짜다. **시그니처는 바이트 단위로 불변** |

## 5. 범위 밖 / 후속

### 5.1 `while try`는 v1에 없다 — lowering만 적어 둔다

재논의를 막기 위해 정확한 형태를 기록한다(옳고, 끌어올림 없고, 가산적이다):

```rust
loop {
    let __c = match cond(i) { Ok(__v) => __v, Err(__e) => return __e, };
    if !__c { break; }
    <body>
}
```

### 5.2 "한 이름, 한 본문" 래퍼 리팩터 (후속 슬라이스)

모든 함수를 평범한 `fn <name>`으로 방출하고, export마다 얇은 `#[no_mangle] extern "C" fn mlx_<name>`
래퍼를 붙인다. 그러면 **DP-F5가 가산적으로 풀리고**(export도 `try` 가능), export와 내부의 구분이
"밖에서도 보이는가"로만 남는다. 모든 export의 방출을 건드리므로 **자체 슬라이스로 격리**한다.

### 5.3 갚지 않는 부채

- **P6**(§0.4): non-fallible 호출자의 에러 소멸. 이 슬라이스는 시그니처를 바꾸라고 말할 뿐이다.
- **단락 평가**(§0.5): 조건 위치를 금지했으므로 관측 수단이 여전히 없다. `STATUS.md` §5-1은 열린 채다.
- **Q14**: `ML_ERR_<NAME>`에 모듈 접두어가 없다. DP-F10의 주석은 완화이지 해결이 아니다.
- **`i32` 나눗셈의 오른쪽-먼저 평가**: §2.2가 **도달 불가능**하게 만들 뿐 고치지는 않는다.
  식 위치를 여는 날 먼저 고쳐야 한다.
